## 二、访谈模式 — 最严格隔离 ✅

### 数据流

```
第1步: 用户发消息 "我遇到过客户..."
     → POST /api/v1/interviews/{sessionId}/chat { message: "..." }
     
第2步: InterviewService.processMessageToWriter()
     → sessionRepository.findById(sessionId)           // 找到当前会话
     → messageRepository.save(userMsg)                  // 持久化用户消息
     
第3步: buildMessagesList(session)
     → messageRepository.findRecentBySessionId(sessionId, 20)
     → SQL: SELECT * FROM (
              SELECT * FROM interview_message 
              WHERE session_id = :sessionId        ← 关键: 只取当前会话
              ORDER BY created_at DESC LIMIT 20
            ) sub ORDER BY created_at ASC
     
第4步: 构造发给 AI 的消息数组
     [
       { role: "system", content: "你是一位资深萃取师..." },
       { role: "user",   content: "我遇到过客户..." },       ← msg1
       { role: "assistant", content: "能详细说说吗..." },     ← msg2
       ...共最多22条(system + 20条历史 + 当前用户消息)
     ]
     
第5步: aiServiceClient.chatStream(messages, sessionContext)
     → POST http://ai-service:8000/internal/chat
     → Python _enhance_with_context() 注入当前阶段状态
     → DeepSeek API 流式返回
     
第6步: AI 回复 → messageRepository.save(aiMsg)            // 持久化AI回复
     → SSE推送给前端
```

### 隔离保证

| 机制 | 实现 | 风险 |
|------|------|------|
| **会话隔离** | `interview_message` 表按 `session_id` 物理隔离 | 无 |
| **上下文窗口** | 最多 20 条，超出自动截断 | 长对话可能丢失早期上下文 |
| **消息持久化** | 每条 user/ai/system 消息都存 DB | 无 |
| **多会话并发** | 每个 session 独立查询，互不干扰 | 无 |

### 会话生命周期

```
created → opening(开场定调) → storytelling(故事深描) 
       → modeling(模型提炼) → closing(收网确认) → completed
       
每个阶段有 6 个采集标记: collectCaseStory, collectSteps, 
collectDecision, collectMindset, collectBoundary, collectChecklist

全部标记为 true 时 → 自动完成 → 生成报告
```

## 三、分身问答模式 — 前端驱动 ⚠️

### 数据流

```
第1步: 用户输入 "周铭你觉得怎么搞定银行客户"
     → POST /api/v1/skills/{skillId}/chat
     {
       message: "周铭你觉得...",
       history: "销售员：你好\n周铭：你好，有什么可以帮你\n...",   ← 前端传
       sessionId: "xxx",                                       ← 后端未使用
       mode: "discuss"
     }

第2步: SkillService.chatToWriter()
     → skillRepository.findById(skillId)         // 找分身
     → grainRepository.findBySpaceId(spaceId)     // 加载所有经验颗粒
     → buildSkillSystemPrompt()                   // 颗粒→system prompt
     → buildChatMessages(systemPrompt, request)
     
第3步: 构造发给 AI 的消息数组
     [
       { role: "system", content: "你是周铭，金融销售..." + 颗粒内容 },
       { role: "user",   content: "[以下是我们的对话历史]\n" + history + "\n[历史结束]" },
       { role: "user",   content: "周铭你觉得怎么搞定银行客户" }
     ]
     
     ⚠️ 注意: history 是前端拼的一个大字符串，作为单条 user 消息注入
```

### 隔离保证 — 薄弱点

| 机制 | 当前状态 | 风险等级 |
|------|----------|----------|
| **会话隔离** | 依赖前端 `history` 字段 | 🔴 高 |
| **消息持久化** | **无**，前端刷新即丢失 | 🔴 高 |
| **上下文窗口** | 前端决定，无后端限制 | 🟡 中 |
| **token 超限** | 无保护，可能超出模型限制 | 🟡 中 |

### 风险场景

```
场景: 用户打开了两个分身页(周铭 + 张三)
     → 浏览器内存中有两个独立的 history 字符串
     → 但如果前端 bug 导致 history 串了：
       周铭的问答上下文被塞进了张三的请求里
       → AI 用周铭的语气回答了张三的问题
       → 用户困惑："我在跟谁聊天？"
```

## 四、对练模式 — 同样前端驱动 ⚠️

### 数据流

```
第1步: 开始对练
     → POST /api/v1/skills/{skillId}/practice/start { scene: "破冰" }
     → SkillService.startPractice()
     → 不调 AI，只返回场景设定 + 客户开场白
     → { practiceId: "a1b2c3d4", scene: { customerLine: "已经有两家在谈..." } }

第2步: 用户回应
     → POST /api/v1/skills/{skillId}/practice/respond
     {
       practiceId: "a1b2c3d4",
       message: "吴总您好我读了您的发言...",
       history: "客户：已经有两家...\n销售员：吴总您好...",
       sceneContext: "..."
     }

第3步: buildPracticeSystemPrompt
     → 加载 skill_practice_customer.md 模板
     → 填入场景+历史+最新消息
     → AI 扮演客户给出回应

第4步: 结束对练
     → POST /api/v1/skills/{skillId}/practice/evaluate
     → 传完整对话 → AI 给出评分+复盘
```

### 隔离保证 — 薄弱点

| 机制 | 当前状态 | 风险等级 |
|------|----------|----------|
| **练习状态** | `practiceId` 存在但**不持久化** | 🔴 高 |
| **历史记录** | 前端传 `history` 字符串 | 🔴 高 |
| **多人并发** | 无任何隔离机制 | 🔴 高 |

## 五、萃取师模式 — 无状态 ✅

每次调 AI 都是独立的 system + user 消息对，不保留对话。

| 操作 | AI 调用 | 上下文 |
|------|---------|--------|
| analyzeMaterials | 解析文件 → 生成报告 | 文档内容 (全量) |
| extractGrains | 从报告拆颗粒 | report.contentJson |
| structureExpertReport | 结构化 AI 输出 | rawContent (截断到2000字) |

**风险：** `structureExpertReport` 截断 rawContent 到 2000 字可能丢失信息。

## 六、线上风险矩阵

### 🔴 致命风险 — 上线前必须修

| # | 风险 | 影响 | 修复方案 |
|---|------|------|----------|
| 1 | **分身问答无消息持久化** | 刷新页面历史丢失，用户体验灾难 | `interview_message` 表复用或新建 `skill_message` 表 |
| 2 | **对练 practiceId 不持久化** | 无法验证对练合法性，可伪造 | 存入 Redis/DB，校验 ownership |
| 3 | **问答 history 完全信任前端** | 前端 bug/恶意可导致上下文污染 | 后端存储历史，前端只传 sessionId |

### 🟡 高风险 — 近期待修

| # | 风险 | 影响 | 修复方案 |
|---|------|------|----------|
| 4 | **无 token 计数保护** | 上下文超出模型限制，API 报错 | 加 tiktoken 计数，超限自动截断 |
| 5 | **对练多开串线** | 同一用户打开多个对练，history 混乱 | 后端存储对练历史 |

### 🟢 低风险 — 持续改进

| # | 风险 | 影响 | 修复方案 |
|---|------|------|----------|
| 6 | 萃取师截断 2000 字 | 长文档信息丢失 | 分段处理或提高限制 |
| 7 | 访谈 20 条限制 | 长对话丢失早期上下文 | 动态窗口或摘要注入 |

## 七、推荐修复优先级

### P0: 问答 + 对练 服务端存储历史

```
当前:  前端维护 history 字符串 → 每次请求传给后端
改为:  后端 DB 存储消息 → 按 sessionId/practiceId 查询 → 构建上下文

改动:
  1. 复用 interview_message 表 或 新建 skill_message 表
  2. SkillService.chatToWriter() 从 DB 加载历史
  3. SkillService.respondPracticeToWriter() 从 DB/Redis 加载对练历史
  4. 前端只传 sessionId/practiceId，不再传 history 字符串

收益: 刷新不丢失、多 tab 隔离、防伪造
```

### P1: Token 计数 + 自动截断

```
当前: 无 token 保护，可能超出 DeepSeek 限制
改为: 发送前统计 token 数，超限时从最旧消息开始截断

实现: 
  1. 引入 tiktoken 或近似计数器
  2. buildMessagesList() 中追加截断逻辑
  3. 日志记录截断事件
```

### P2: 对练状态持久化

```
当前: practiceId 随机生成，不存储
改为: Redis 存储 practiceId → {skillId, userId, scene, createdAt}
      TTL 设为 24 小时
      后端校验 practiceId 合法性
```
