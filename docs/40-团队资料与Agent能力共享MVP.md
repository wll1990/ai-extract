# 团队资料与Agent能力共享：最小方案

2026-11-13，讨论稿；替代39号文档的大范围首版设想。本轮只更新方案。

## 1. 只解决四件事

1. 有价值的资料按统一最低标准收进来，有来源、归属、版本。
2. 团队先从网页查到资料，并看到原始依据；体验稳定后再接一个IM文字查询入口。
3. 本地Skill、工具和提示词作为独立能力资产导入平台，先迁通一个代表能力，再逐项扩展。
4. 用真实历史问题验证找得准、能接手、能复用。

暂不做：IM文件/语音上传、IM审批、自动收集所有聊天、实时多人编辑、全流程项目管理、通用工作流编排、多Agent自治、所有工具远程接管、多IM同时上线。

## 2. 资料收集最低标准

首批四类：知识、成功/失败案例、历史方案/课程、工作方法。客户原始需求资料先标为受限材料，不直接共享。
上传者只需选择类型、填标题、来源/原项目、适用场景、共享范围、内容性质（客户原文/人工整理/AI草稿/经验证成果）。账号自动记录提交人，时间由系统生成。
敏感内容不确定时默认仅本人/管理员可见，审核后才开放团队；文件名不能代替权限。
原件保留，不要求成员先把所有资料改成统一文档。AI建议摘要与标签，人工只核对必要项。
案例需要保留背景、问题、采取行动、结果依据；缺少结果证据就标“待验证”，不能作为成功证据。
历史方案保留客户背景、目标受众、约束、交付物及可复用边界；客户说好不等于已有量化业务收益。
方法保留输入、步骤、提示词/技能文件、依赖、输出示例和检查标准。
不收集账号密码、环境变量秘密或整个个人电脑；Agent聊天只挑对复现有价值且获准共享的内容。

建议首次选3—5个代表项目，保留每项目的原始需求、最终方案、关键知识、复盘和方法，不先全量搬库。

## 3. 如何存

保留三层，不只存一份AI摘要：

| 层 | 内容 | 建议实现 |
|---|---|---|
| 原件 | docx/pdf/pptx/md等文件，不被生成结果覆盖 | 现有文件存储服务接OSS；数据库保存对象键，不保存永久公开URL |
| 资料登记 | 企业、类型、来源、场景、范围、状态、版本、摘要和文件引用 | PostgreSQL；可扩展统一资料表，复用知识/案例业务表 |
| 检索索引 | 解析原文、章节块、出处定位、关键词、embedding | PostgreSQL+pgvector及文本检索 |

引用层级为资料ID→版本→章节/片段，能回到原件；解析不能保留页码时使用章节和原文片段，不编造页码。
分块保留有意义上下文，历史方案要能从命中片段回看整份材料；不能只检索过短的知识摘要。
文件hash用于同企业同范围重复上传提示，不能让其他企业文件存在性泄露；相同文件可有不同授权。
流程：上传→存原件/建记录→异步解析→分块/建议摘要→人工确认共享→索引就绪→可查询。
上传成功和可检索分别显示，失败保留原件并允许重试。
更新创建新版本并标当前有效版；旧引用仍能定位，不直接覆盖历史原件。

## 4. 怎么接入个人Agent能力

先盘点“能完成的工作”，不按工具名称设计平台。每项登记：工具、方法文件、运行依赖、数据权限、输入输出、可重复性、耗时成本。

| 个人资产形态 | 团队化方式 |
|---|---|
| 本地Skill目录（SKILL.md、脚本、模板、参考文件） | 原包保留并登记版本；检测工具/运行时依赖；经过试运行后发布给团队，不降格为知识片段 |
| 提示词、检查清单 | 带输入输出规范的能力，由后端组装上下文并调用企业模型 |
| Python/Node等脚本 | 可复现性验证后封装受控后台任务；依赖、文件目录、权限和超时明确 |
| 有正式API的外部服务 | 核实接口/授权后加服务端适配器，返回统一结果和用量 |
| 只能个人桌面操作的工具 | 先保留人工执行，通过任务包导出与成果回传复用，不假装已自动集成 |

提示词迁到其他模型不保证效果等价，需要用固定历史输入比对输出；工具的搜索/执行/隐式上下文不能仅复制提示词替代。
不能直接共享个人登录态、账号或整段私人历史。Pilot/Bot具体指什么、是否有正式接入方式，后续盘点确认。
首版支持最小能力登记与运行协议，不做复杂工作流和任意工具自治。先导入并迁通一个代表Skill（候选：基于需求与参考方案生成课程大纲草稿），而不是把能力写死成不可替换的页面。
该入口输入明确需求、指定参考资料、能力版本；后台完成检索/组装/执行，保存草稿和引用，可查看/下载。
未确认事实单独列出，不能用AI补全成事实。生成过程记录输入与模型版本，人工判断可用性。

### 4.1 最小能力包契约

保留原Skill目录与相对路径；无需成员先重写，平台导入后补齐登记信息：名称、版本、用途、类型、输入规范、输出规范、入口、工具依赖、运行时、权限和负责人。
SKILL.md主要描述方法，未必是可直接执行的程序。原环境提供的模型、文件工具、命令执行、检索和浏览器能力需要逐项映射。
支持三类运行适配：prompt（模型+指令）、script（受控脚本）、agent_skill（模型遵循Skill步骤并调用已注册工具）。外部API作为注册工具，桌面专属能力先标不兼容/需适配。
导入状态：已导入→待适配/待试运行→试运行通过→已发布；导入成功不等于可执行。
任一缺失依赖在试运行前明确展示，不以空按钮或模拟结果冒充已迁移。

### 4.2 技术边界

知识资产与能力资产分开：知识用于回答依据，Skill用于执行方法；Skill可通过授权检索工具读取共享资料。
能力包与输出文件放文件存储；登记、版本、输入输出Schema和执行记录放PostgreSQL；知识正文/片段进入检索索引。
最少增加Capability/CapabilityVersion/CapabilityRun与Runner接口，不需要首版通用编排引擎。
Java后端负责身份、能力版本、资料权限、任务和记录；独立Worker负责执行。PromptRunner、ScriptRunner、SkillRunner通过同一契约返回文本/文件/引用或明确错误。
试运行锁定能力版本，保留输入、资料引用、日志、产物和模型配置；原工具与平台对同一输入做人工比较。
脚本仅在隔离工作目录运行，限制资源、文件/网络范围和依赖；不在Java服务宿主目录执行任意上传命令。
Skill声明权限不等于授权，工具每次调用校验企业和用户范围；Key通过后端配置注入，不随包上传。
首版只实现真实样本需要的Runner和工具；界面仅展示可以实际执行的能力类型。

## 5. IM只做文字查询与补充背景

用户：“找三个制造业主管辅导的培训案例。”→检索→答案、适用理由和资料链接。
用户：“补充一下，只有半天，都是新任主管。”→当前会话增加条件→重新检索/解释推荐。
这些补充默认仅作用于当前会话，不修改正式案例、需求或团队知识。
回复区分已有资料、模型推断和未找到；没有依据就明确缺失，不编造案例。
首版选一个渠道，优先复用现有飞书文字链路；内部账号绑定后仅查询本人获准共享内容。
优先单聊；若用群聊，仅返回该群批准共享范围的资料，不能把个人私有资料输出群内。
无需首版建设群项目路由、IM上传、审批或主动任务通知。
现有桥聚合正文、忽略source等事件，需补引用摘要/受控链接输出；下载链接访问后端再鉴权。

## 6. 最小页面与后端

网页仅三个入口：资料库（上传、筛选、确认共享、查看原件）、团队问答（提问、补充背景、引用）、能力库（导入Skill/提示词/工具配置、检查依赖、试运行、发布使用）。能力库先迁通一个代表能力，不做大而全市场。
复用现有知识库/案例库页面，补原件与历史方案检索，避免重新造一套库。
后端最少新增/扩展：资料原件登记与索引、统一授权检索、问答引用、能力登记和运行适配；IM真实用户绑定留到对接阶段。
网页与IM共用同一个QueryService，避免两套结果和权限。
已有销售分身提示词需显式换成培训资料查询用途；不能默认用销冠人设回答课程设计问题。

## 7. MVP实施与验收

第一步：用选定历史资料打通原件、登记、全文检索和引用；网页可查。
第二步：导入真实Skill/提示词/工具，检测依赖并迁通一个专家实际使用的能力，针对相同输入比较原工具与平台产物。
第三步：用真实任务打磨资料选择、输入表单、过程反馈、结果修改和下载，先改善输出可用性。
第四步：接飞书文字查询与补充背景，不增加IM写操作。

验收：选20个团队真实问题，由非原作者成员提问，检查正确资料是否被找到、来源能否打开、答案是否忠实；记录无答案和错误。
再选3个历史需求，由另一成员使用共享方法产出大纲草稿，由专家检查目标对应、内容取舍、活动设计、事实依据和人工修改量。
验证未共享资料/其他企业资料无法通过网页、IM、引用链接访问；未审核AI稿不被当作已验证成果。
实际耗时和质量目标用这轮试验建立基线，不预先承诺准确率和工期。

下一步需要的样本：一个代表项目的原始需求、最终方案、关键参考资料，以及当时有效的一套提示词/技能/脚本和一次输入输出示例。
