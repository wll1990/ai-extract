# 创始人分身 · 技术方案

> 本文档是创始人分身的**技术实现总依据**，供开发团队执行。
> 上游依赖：`创始人分身-能力与边界定义.md`（能力模型）、`创始人分身-输入文档标准.md`（素材规范）。
> 核心原则：**复用现有销冠分身骨架，扩展创始人分身**，不重写一套。

---

## 一、概述

创始人分身（`Skill.type = 'founder'`）与销冠分身的本质差异：销冠萃取"话术"，创始人萃取"判断原则"。因此：

- **不复用 `ExperienceGrain`**（它是场景+话术+思路的销售颗粒，语义不匹配）
- **复用 `Skill` 表**（`type`/`companyId`/`domain`/`status` 字段全复用，`type` 新增 `founder` 值）
- **复用对话编排骨架**：`ChatStreamService` 的 setup→stream→post 三段式、`GrainRetriever` 的混合检索、`MaterialCleaningService` 的清洗管道

对话回答三种能力（判断/代笔/百科）通过**意图识别路由**，对应三种回答形态，见能力定义文档。

## 二、数据模型

### 2.1 复用与新建

| 实体 | 操作 | 说明 |
|------|------|------|
| `Skill` | 复用 | `type` 新增 `founder`（varchar 无 CHECK，无需改列） |
| `SkillMaterial` | 复用 | 素材上传/清洗，加 `value_level` 字段（S/A/B/C/D 价值等级） |
| `SkillConversation` / `SkillMessage` | 复用 | 对话持久化，`SkillMessage` 加 `citations JSONB` |
| `SkillProfile` | 复用 | 自由文本画像（personality/speakingStyle），与 PersonaConfig 互补 |
| **`Principle`** | 新建 | 原则层（判断原则，核心资产） |
| **`Stance`** | 新建 | 立场层（具体议题态度） |
| **`FounderChunk`** | 新建 | 事实层（文档 chunk + 制度文档） |
| **`PersonaConfig`** | 新建 | 人格层（结构化可调参数） |
| **`CandidatePrinciple`** | 新建 | 人审工作台（候选原则） |

### 2.2 新增表字段定义

**`Principle`（原则）** — 判断能力的核心检索源

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| founder_skill_id | UUID | 归属 founder skill |
| title | varchar(200) | 原则陈述（短） |
| statement | TEXT | 原则陈述（完整） |
| rationale | TEXT | 原文依据（引用原文） |
| domain | varchar(200) | 领域（战略/销售/组织/产品/资本/文化），领域地图节点 |
| applicable_scenario | TEXT | 适用场景 |
| boundary | TEXT | 边界反例 |
| version | int | 版本号，默认 1 |
| status | varchar(20) | draft / published / deprecated |
| source_chunk_ids | JSONB | 溯源 chunk id 数组 |
| embedding | VECTOR(1024) | 向量，JPA 不管理，走原生 SQL |
| confidence | double | 人审后=1.0，AI 候选=模型置信度 |
| reviewed_by / reviewed_at | UUID / timestamp | 审核人和时间 |
| created_at / updated_at | timestamp | 时间戳 |

**`Stance`（立场）** — 具体议题的态度，独立建表（立场会随决策演进，需独立 version 与议题维度）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| founder_skill_id | UUID | 归属 |
| topic | varchar(200) | 议题（如"是否出海"） |
| stance | TEXT | 立场陈述 |
| stance_type | varchar(20) | support / oppose / conditional / neutral |
| reasoning | TEXT | 判断链/理由 |
| source_chunk_ids | JSONB | 溯源 |
| version / status | int / varchar | 版本 / 状态 |
| embedding | VECTOR(1024) | 向量 |
| reviewed_by / reviewed_at / created_at / updated_at | — | 同 Principle |

**`FounderChunk`（事实层）** — 文档 chunk + 制度文档，百科能力的检索源

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| founder_skill_id | UUID | 归属 |
| material_id | UUID | 来源 SkillMaterial（可空，允许手动补录） |
| chunk_index | int | 文档内顺序，保证完整性可还原 |
| content | TEXT | chunk 原文（不打散语义单元） |
| doc_type | varchar(50) | speech / all_hands / meeting_minutes / interview / **institution**（制度文档） |
| source_meta | JSONB | {fileName, page, startPos, endPos} |
| embedding | VECTOR(1024) | 向量 |
| status | varchar(20) | active / deprecated |
| created_at | timestamp | 时间戳 |

> 制度文档（`doc_type='institution'`）对应"百科"能力，不分价值等级，直接入库供检索。

**`PersonaConfig`（人格层）** — 1:1 归属 founder skill

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| founder_skill_id | UUID | unique，1:1 |
| formality | int | 1-5 正式度 |
| conciseness | int | 1-5 简洁度 |
| counter_question_tendency | int | 1-5 反问倾向 |
| style_notes | TEXT | 风格校准备注 |
| signature_phrases | JSONB | 标志性表达（口头禅） |
| created_at / updated_at | timestamp | 时间戳 |

> 与 `SkillProfile` 的区别：后者是自由文本画像，本表是**结构化可调参数**，驱动 prompt 数值化风格指令。

**`CandidatePrinciple`（人审工作台）** — 对标现有 `CandidateGrain` 的审核模式

| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |
| founder_skill_id | UUID | 归属 |
| material_id | UUID | 来源素材（可空） |
| source_chunk_ids | JSONB | 溯源 |
| title / statement / rationale / applicable_scenario / boundary | — | 同 Principle |
| status | varchar(20) | pending_review / approved / rejected / modified |
| confidence | double | 提取置信度 |
| reviewed_by / reviewed_at / review_note | — | 审核信息，review_note 记录修改说明 |
| created_at | timestamp | 时间戳 |

### 2.3 索引设计

每张新表：`founder_skill_id` 建 B-tree 索引（按 skill 查询）；`embedding` 建 HNSW 余弦索引（`<=>` 算子，与 `GrainRetriever` 一致）；`content`/`statement` 用 generated column + GIN 索引（`to_tsvector('simple', ...)`，对标现有 `experience_grain`）。

### 2.4 Flyway 迁移

新增 `V40__founder_skill.sql`：建 5 张表 + `SkillMessage` 加 `citations JSONB` + `SkillMaterial` 加 `value_level varchar(1)`。

## 三、构建 Pipeline（素材 → 原则库）

### 3.1 复用与新建边界

**复用**：
- 素材上传/解析/清洗：`SkillMaterialController` + `MaterialCleaningService` + `MaterialCleaningScheduler` 的 scan→lock→parse→clean 骨架
- 线程池：`AiConfig` 的 `parseExecutor`/`cleanExecutor`/`embeddingExecutor`
- 分布式锁、`DashScopeEmbeddingService` 向量化

**新建**（founder 专属，与销售颗粒萃取解耦）：
- `FounderExtractionScheduler`：`@Scheduled(fixedDelay=30s)`，扫 founder skill 归属且 `status=analyzed` 的素材
- `FounderExtractionService`：chunk 切分 + LLM 提取候选原则

### 3.2 状态机

```
上传 uploaded → [复用] parsed → analyzed（现有清洗链路）
  → [新建] FounderExtractionScheduler 发现 founder 素材
      → chunk 分块 → founder_chunk 落库 + 向量化（embeddingExecutor）
      → LLM 提取候选 → candidate_principle(pending_review)
          → 人审 ✅ approved → Principle/Stance 落库 + 向量化
              ✏️ modified → 落库（写 review_note）
              ❌ rejected → 丢弃（保留备查）
```

**关键实现**（对标 `MaterialCleaningScheduler.processMaterial`）：
- skill 级 Redis 锁 `founder:extract:{skillId}` 防重复提取
- AI 调用在事务外，落库用 `REQUIRES_NEW` 短事务（self 自注入）
- 向量化失败不阻断

### 3.3 人审接口 `FounderReviewController`

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/founder/{skillId}/candidates?status=` | 分页列候选（用 `PageResponse.of`） |
| PUT | `/admin/founder/candidates/{id}` | 审核 `{action: approve\|reject, edited, note}` |
| POST | `/admin/founder/{skillId}/principles` | 人工直接创建原则（回填清单 → 手动补录） |
| PUT | `/admin/founder/principles/{id}` | 编辑原则（版本递增） |
| GET | `/admin/founder/{skillId}/principles` | 原则库列表（领域地图数据源） |

## 四、对话编排

### 4.1 三段式（`FounderChatService`，对标 `ChatStreamService.chatIndividual`）

```
Phase 1 Setup（同步，订阅前）:
  权限校验（company_admin/super_admin）
  → SensitiveTopicGuard 敏感拦截（命中短路）
  → FounderIntentResolver 意图识别（judgment / generate / faq）
  → 按意图路由检索（判断→Principle/Stance，百科→FounderChunk，代笔→不检索取人格）
  → 溯源组装（区分原话 vs 推断）
  → 组装 system prompt（按意图选模板）
  → upsertConversation（复用 ConversationPersistenceService）

Phase 2 Stream: ChatStreamAdapter.chatStream

Phase 3 Post-stream: meta + judgment/citation 事件 + saveAiMessage(含 citations)
```

### 4.2 意图识别 `FounderIntentResolver`

三路，零额外 LLM 优先（规则+关键词，不可靠时降级单次 LLM 判断）：

| 意图 | 关键词 | 检索 | 输出 |
|------|--------|------|------|
| `generate` | 帮我写/起草/生成/路演/融资/文章 | 不检索，取 PersonaConfig | 代笔草稿 |
| `faq` | 是什么/流程/报销/参数/分工 | 检索 FounderChunk | 百科答案 |
| `judgment` | 该不该/怎么办/要不要/怎么权衡 | 检索 Principle + Stance | 判断卡片 |

敏感词命中（薪酬/人事/未公开交易/法律）→ 最高优先级拦截。

### 4.3 反向追问（judgment 专属）

触发条件：`judgment` 意图 且（检索 tier 全部为 none/fallback，或问题缺关键维度）。

此时不生成结论，而是输出"需补充 X/Y/Z 信息"列表。实现：在 setup 阶段，若 `grains.tiers()` 全部命中 fallback 或为空，走反问模板而非判断链模板。

### 4.4 溯源组装

新增 `Citation` record：`{ kind(principle|stance|chunk), refId, title, quote, isInference, sourceName }`。

- 判断/百科：`isInference=false`，带原文引用
- 代笔：不溯源，但强制带"草稿"标注（不是 citation，是输出前的前缀）

通过 `ChatChunk.event(type, data)` 下发 `judgment` 事件（已存在），前端 `sse.ts` 的 `onEvent` 捕获。

## 五、Prompt 设计

新建 `prompts/domain/founder/` 下的模板，复用 `PromptLoader.format` 机制：

| 模板 | 用途 | 关键内容 |
|------|------|---------|
| `founder_judgment.md` | 判断能力 | 判断链：先原则→再分析→再结论→最后边界；担责事项明示"以老板确认为准"；未覆盖诚实表态 |
| `founder_generate.md` | 代笔能力 | 注入 PersonaConfig 人格参数 + signaturePhrases；保持口吻；不编造业绩/观点；强制带"AI草稿需润色"标注 |
| `founder_faq.md` | 百科能力 | 直接命中即答；动态信息带"截至XX时间"标注 |
| `founder_extract_principle.md` | 构建 pipeline | 从素材提取候选原则（陈述+依据+场景+边界） |

`FounderPromptAssemblyService` 对标 `PromptAssemblyService.buildSkillSystemPrompt`，按意图选模板。

## 八、分阶段实现

| 阶段 | 内容 |
|------|------|
| **Phase 1** | 数据模型（V40 迁移 + 5 实体 + repository）+ 意图识别 + 判断能力（判断链 prompt + 溯源）|

## 十、验证

- **迁移**：`V40` 执行后 5 表建成，`skill.type='founder'` 可写入
- **构建链路**：上传全员信 → 清洗 → founder_chunk 生成 → 候选原则 → 人审 approve → principle 落库 + 向量化
- **对话三路**：`/founder/{id}/chat` 输"这个市场该不该进"→判断卡；"帮我写路演稿"→代笔草稿带标注；"报销流程"→百科答案带时效
- **反向追问**：输信息不足的判断类问题→先反问缺什么
- **敏感拦截**：输"XX的薪酬"→短路转"直接问老板"
- **溯源**：历史消息回放，`citations` 可渲染
