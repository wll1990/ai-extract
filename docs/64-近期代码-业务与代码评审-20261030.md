## 3. P1（建议本轮修复）

### P1-1 报告第 3 次租约耗尽后永久卡在 generating
- 类型：Bug / 状态机
- 位置：`ReviewReportRepository.java:29-42`；`SalesReviewReportWorker.java:48-55`；`SalesReviewService.java:184-189`
- 场景：第 3 次 claim 成功（attempts=3）后进程被 kill/OOM，租约 10 分钟后过期。`lockClaimableIds`/`claim` 都要求 `attempts < 3`，不再领取；无 sweeper 置 failed；`requestReport` 把 generating 当 active 返回。
- 后果：前端永远轮询 generating，无法重新生成，收不到失败通知。
- 修复：新增 stale sweeper：`status='generating' AND lease_expires_at < now() AND attempts >= maxAttempts` → failed 并通知；`requestReport` 对耗尽租约视为 failed，允许新版本。
- 测试：attempts=3 + 租约过期 → failed + 通知；耗尽后 requestReport 生成 v+1。

### P1-2 转线索并发不幂等，产生重复线索
- 类型：Bug / 并发
- 位置：`SalesLeadService.java:64-127`；`sales-schema.sql` 无 `lead(source_review_id)` 唯一约束
- 场景：双击/两标签页同时转线索，两个事务都读到 `session.leadId=null`。
- 后果：创建两条线索，后提交者覆盖 `session.leadId`，另一条成孤儿；两条都写 created 活动。
- 修复：转线索前 `findByIdForUpdate(sessionId)`；加 `UNIQUE(source_review_id) WHERE source_review_id IS NOT NULL`；冲突回读已有线索返回幂等结果。
- 测试：并发两线程只生成 1 条 lead；DB 唯一索引断言。

### P1-3 先建任务后转线索，任务永久丢 lead_id
- 类型：数据一致性 / 流程
- 位置：`SalesTaskService.java:73-79`；`SalesLeadService.java:118-121`、`:160-161`；`sales-schema.sql:313-319`
- 场景：用户先在复盘页「生成任务」（不要求已转线索），再「转线索」。
- 后果：任务 `lead_id=null`，线索详情「关联任务」为空，后续转交/升级活动也不入线索时间线。
- 修复：转线索成功后 `UPDATE follow_up_task SET lead_id=:leadId WHERE review_id=:sessionId AND lead_id IS NULL`，并补 `task_created` 时间线。
- 测试：create tasks → convert → detail 任务非空。

### P1-4 培训 schema 带补训数据后不可重复执行
- 类型：DDL / 部署
- 位置：`scripts/training-schema.sql:299-301`、`:367-370`
- 场景：已有 round 1/2 补训记录后重跑 schema；脚本先 ADD 旧唯一键 `(assignment_id,task_id)`，再 DROP。
- 后果：23505 中断，文档声称的幂等不成立。
- 修复：删除旧唯一键 ADD，或把 P3 段 DROP 前置。
- 测试：插入 round1+2 后重跑 schema 无异常。

### P1-5 客户信号可无 evidence，产生“无引用客户事实”
- 类型：逻辑 / 需求
- 位置：`SalesReviewReportParser.java:96-129`
- 场景：模型输出 `sourceType=customer_words`、`value=30 万`、无 evidence。
- 后果：前端以「客户原话」展示，但无引用可回看，违反“每条结论有引用、客户事实不编造”。
- 修复：`sourceType != unknown` 且 evidence 为空 → 整份拒绝重试；非空 value 至少一条 quote。
- 测试：known source 无 evidence → reject。

### P1-6 转线索/建任务可用旧版报告
- 类型：业务逻辑 / 流程
- 位置：`SalesLeadService.java:72-74`；`SalesTaskService.java:49-93`
- 场景：v1 ready，重新生成 v2（queued/generating/failed）后，直接调 API 转线索/建任务；前端按钮虽按 latest 隐藏，但接口无校验。转线索查询会命中 v1。
- 后果：基于旧版或失败报告创建业务数据。
- 修复：取最新报告并校验 `status='ready'`；建任务同样要求最新版 ready。
- 测试：v2 queued + v1 ready → 两个接口 409；无报告建任务 409。

### P1-7 P3 补训后旧轮次仍可开考/复核，计数漂移
- 类型：状态机 / 数据
- 位置：`TrainingAttemptService.java:146-149`、`:172-177`；`TrainingProgressService.java:104-118`
- 场景：round1 failed、创建 round2 后，仍用 round1 recordId 开考/复核。
- 后果：round1 pass 走 delta +1，重复计数；可能触犯 `ck_ta_counters` → 500；看板/认证口径漂移。
- 修复：startAttempt/review/regrade 统一校验目标 record 是该 task 的 `max(round_no)`；旧轮次 409。
- 测试：旧轮开考/复核 409；round2 passed 后 round1 pass 不改变计数。

### P1-8 导出审计被轮询放大 + OSS 预签名 365 天
- 类型：合规 / 安全 / 性能
- 位置：`AdminTrainingExportController.java:59-72`；`TrainingExportService.java:109-121`；`OssExportStorage.java:22-37`；`OssService.java:87-88`
- 场景：前端每 2s 轮询 `GET /exports/{id}`，done 后 `get()` 内部调用 `download()`，每次写 `training.export.download` 审计；OSS 走无参 `generatePresignedUrl`，固定 365 天，`presign-seconds=900` 未使用。
- 后果：一次真实下载产生多条 PII 外发审计，日志不可用于追责；下载直链长期有效。
- 修复：`get()` 不写审计、不生成 URL；只在 `/download` 生成并审计一次；OSS 用带 TTL 重载。
- 测试：get 不写审计；download 恰一条；OSS 单测断言 TTL=900。

### P1-9 通知/提醒失败静默，提醒标志已提交后永久丢失
- 类型：可靠性 / 可观测性
- 位置：`SalesTaskReminderService.java:26-77`；`NotificationService.java:89-109`
- 场景：`remindDueSoon/remindOverdue/autoEscalate` 先置标志，通知 afterCommit 写失败（DB/去重/序列化）只 `log.warn`；userId/companyId 为空直接 return 无日志。
- 后果：提醒永久丢失；运营无指标/告警/重试。
- 修复：通知成功后再置标志（或 outbox + 重试）；至少加成功/失败/去重指标与空收件人 WARN；关键通知可补发。
- 测试：通知失败时标志不置位或可重试；空收件人有日志/指标。

## 6. 流程走查结论

### 销售
新建 → 报告 → 追问 → 转线索 → 任务 主链可走通；断点在：
- 先任务后线索丢关联；
- 报告耗尽卡死；
- 旧版报告可通过 API 转线索/建任务；
- 追问上下文不足，长对话后半段答不上；
- 列表看不到报告失败原因，必须点进详情。

### 教练
请求 → 通知 → 台账 → 工作台 → 补充 → 发起人可见 主链可走通；断点在：
- 取消后教练仍可写；
- 未授权原文时引用提示错误；
- 多条备注 N+1；
- 台账入口对无分身员工也显示。

### 管理员
- 企业 Key 配置/轮换/停用可用；运行期错误无稳定子码，员工只看到原始异常；
- 销售全公司列表可用；缺索引，长期数据量下会慢；
- P3 导出/滞留/看板存在审计失真、失败即终态、取消后待复核无法裁决等运营问题。

### 培训
补训/撤销/延期/通知/导出主链已落地；风险集中在旧轮次可继续操作、取消后评分链路未终止、滞留扫描饥饿、schema 带数据不可重跑。
