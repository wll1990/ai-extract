## 1. 范围

P2 交付一条**闭合**的培训链路：

```
建计划 → 配阶段/任务 → 预览 → 发布版本 → 建批次 → 分配学员
   → 学员学习/陪练/考试 → 自动评分 → 主管/导师复核 → 学员看成绩
   → 必修全过 → 待认证 → 主管确认上岗
```

| 阶段 | 内容 |
|---|---|
| **P2** | 计划与版本（阶段、新建版本、发布/退役）、批次（创建、进度）、分配（批量、取消、我的培训）、学习（阅读/陪练/考试、草稿、恢复、提示、提交）、评分（worker、结果、复核）、**认证确认** |
| **P3** | 补训、批次看板明细、学员详情与证据下钻、导出（`export_job`）、`pending_review` 滞留监控 |

## 3. 数据模型

完整 DDL 见 [scripts/training-schema.sql](scripts/training-schema.sql)（10 表：9 张 `training_*` + `export_job`）。不建外键，状态列 `varchar + CHECK`，与 `evaluation_*` 一致。

| 表 | 作用 | 关键约束/索引 |
|---|---|---|
| `training_plan` | 计划，版本化 | `ck_tp_status`；`(company_id, status, created_at desc)` |
| `training_plan_version` | 版本，发布冻结 | `UNIQUE(plan_id, version)` |
| `training_task` | 任务，按阶段分组 | 类型条件 CHECK（阅读必须有资源、陪练必须绑分身、考试必须有题集+时长+禁提示）；`(plan_id, version, phase_no, order_no)` |

| `training_task_record` | 学员-任务进度行 | `UNIQUE(assignment_id, task_id)`；waived 必须有人和理由；`(assignment_id, status)` |

## 5. 状态机

```
计划      draft ──publish──> published ──retire──> retired
版本      draft ──publish──> published（含已发布版本的 task 只读）
批次      active ──结班──> completed / cancelled / archived

任务记录  locked ──前置达成──> available ──start──> in_progress
          阅读:   in_progress ──acknowledge──> passed
          陪练/考试: attempt 出结论回写 → passed / failed
          任一:   → pending_review（评分需复核）→ passed / failed
          waived（P3 开放入口，须人+理由）

尝试      in_progress ──submit──> submitted ──worker 领取──> grading
              ├─> finalized（自动通过）
              ├─> pending_review ──复核──> finalized
              └─> error（AI 失败/超次数）──重试──> submitted
          result: pass / fail / undetermined（独立字段）

分配      not_started ──首次开始──> in_progress
          in_progress ──必修全 passed──> pending_certification
          pending_certification ──主管/导师确认──> certified
          cancelled（终止未完成，保留历史）
```

**不变式**
1. `pending_review` 只能由评分产生，前端不可直写。
2. `passed` 必须有证据：阅读看 `acknowledged_at`，陪练/考试看 `attempt.result=pass`。
3. 逾期不是状态，`deadline` 是时间派生态；`error` 不是"没考过"，不产生业务结论。
4. 提交后答案不可改（仅 `in_progress` 可写 `answers`）。
5. `grading` 与 `submitted` 都必须可被重新领取，否则进程崩溃会永久卡死。

## 6. 计数一致性（评审 B8 的修复）

三列冗余给批次看板与认证判定用。**增量必须带状态迁移守卫**，不能无条件 `+1`：

```sql
-- 读旧行 → 算 delta → 原子 UPDATE（同一事务内）
-- 旧状态非终态才计完成；非 passed → passed 才计通过
UPDATE training_assignment
   SET completed_tasks = completed_tasks + :completedDelta,
       passed_tasks    = passed_tasks    + :passedDelta,
       required_passed = required_passed + :requiredPassedDelta
 WHERE id = :assignmentId;
```

| 场景 | completed | passed | required_passed |
|---|---|---|---|
| `available → in_progress` | 0 | 0 | 0 |
| `in_progress → failed`（首次出结论） | +1 | 0 | 0 |
| `failed → passed`（补考通过） | **0** | +1 | +1（必修） |
| `in_progress → passed` | +1 | +1 | +1（必修） |
| `→ waived` | +1 | 0 | 0 |

- 单测必须覆盖「同一 task_record 两次 attempt 只计一次完成」。
- `passed_tasks <= completed_tasks <= total_tasks`、`required_passed <= required_total <= total_tasks` 有 CHECK 兜底（已实测）。
- `pending_certification` 触发：`required_total > 0 AND required_passed = required_total`，在同一事务内改分配状态。

## 7. 权限与路由（D9/D18/D21 的落地）

### 7.1 权限码

| 权限码 | 授予 | 覆盖 |
|---|---|---|
| `TRAINING_MANAGE` | super_admin、company_admin | 计划/任务/批次/分配/取消（管理侧写操作） |
| `TRAINING_REVIEW` | super_admin、company_admin、**employee** | 复核、认证、批次进度（employee 仅限本人任导师的批次） |
| `TRAINING_LEARN` | super_admin、company_admin、employee | 我的培训、任务记录、尝试 |

`TRAINING_REVIEW` 发给 employee 是**故意**的：URL 级权限只回答"这个人是不是复核人"，"这个人能不能复核**这个批次**"由服务层回答。

### 7.2 数据级授权（D21）

```java
// TrainingAccessService
void assertCanReview(UUID cohortId) {
    TrainingCohort cohort = requireCohort(cohortId);          // 404
    assertSameCompany(cohort.getCompanyId());                 // 404
    if (isAdmin()) return;                                    // COMPANY_MANAGE
    if (!Objects.equals(cohort.getMentorId(), TokenContext.getUserId())) {
        throw new BusinessException(403, "只能复核自己带的批次"); // 403
    }
}
```

覆盖率要求：非导师员工复核 → 403；跨企业导师 → 404；导师改别人的批次 → 403；**自己复核自己 → 403**。四条都要有单测。

入参到批次的映射链**冻结**（不允许实现时各写一套）：

| 端点 | 入参 | 映射链 |
|---|---|---|
| #21 复核 | `attemptId` | attempt → task_record → assignment → cohort → `assertCanReview(cohortId)` |
| #19 认证 | `assignmentId` | assignment → cohort → `assertCanReview(cohortId)` |
| #16 进度 | `cohortId` | 直接 `assertCanReview(cohortId)` |
| #20 管理侧 attempt 详情 | `attemptId` | attempt → assignment → `company_id` 断言（含金标，仅管理侧） |

### 7.3 路由与 SecurityConfig（顺序敏感）


## 8. 不可妥协的安全约束（4 条，每条都要单测）

1. **正确答案不下发浏览器**：`question_snapshot` 含 `expectedPoints/forbiddenPoints/scoringRule`；`GET /me/training/attempts/{id}` 与 `/result` 走 `stripAnswerKey()`。单测断言响应 JSON 不含 `expectedPoints`。
2. **考试禁提示**：`allow_hints=false` 时 `POST /me/training/attempts/{id}/hints` 返回 403，不依赖前端隐藏。
3. **计时以服务端为准**：开始考试时 `deadline = min(now + exam_duration_minutes, assignment.deadline)`；提交以服务端时间判超时；倒计时由服务端下发剩余秒数，客户端只展示。
4. **归属校验（D18）**：每个学员端点先 `assertLearnerOwnsXxx`，不匹配返回 **404**（不用 403，避免探测存在性）；管理侧走另一条路径（§7.2）。
5. **strip 覆盖全部下发路径（D23）**：不只是 `GET attempt` 与 `result`——`POST task-records/{id}/attempts`（开始/续接）是**第一次下发题面**的地方。所有学员侧 attempt 响应必须走同一个 `toLearnerAttemptMap()`，单测遍历四个返回路径断言不含 `expectedPoints/forbiddenPoints/scoringRule/goldBasis/retrievalExpected`。
6. **答题写入必须条件更新（D24）**：`UPDATE ... WHERE id=? AND status='in_progress'`，rowcount=0 返回 409；提交同样用条件迁移，只有迁移成功的请求才建评分任务。仓储方法已按此实现，T4/T5 必须有并发用例。
7. **管理侧归属链（D25/D29）**：`training_attempt`/`task_record`/`training_review` 没有 `company_id`，管理侧一律 `attempt → assignment → company_id`、`record → assignment → company_id`、`review → attempt → …` 断言；且**先查存在性再放行 super_admin**，不复用 `assertSkillOwnership` 的前置 return 写法（实测它会放过幽灵 ID）。
8. **不能自己复核自己（D26）**：`review`/`certify` 服务层拒绝 `TokenContext.get() == learnerId`（super_admin 除外）。导师同时是学员时，必须由第二人复核。
