# 多领域架构设计方案

> 基于当前项目代码的深度 review，针对"如何做到多领域"这一核心问题，给出从架构到商业的完整设计方案。

---

## 一、现状分析：当前领域体系的能力与局限

### 1.1 已有的领域基础设施（做得好的部分）

当前项目已构建了一套 **YAML 继承 + Prompt 变量注入** 的领域配置体系，核心能力包括：

| 能力 | 实现方式 | 评价 |
|------|---------|------|
| 领域定义 | YAML 5段配置(domain/acceptance/precheck/pipeline/chat) | ✅ 结构清晰，字段覆盖全面 |
| 领域继承 | `extends` 递归加载 + deepMerge | ✅ 优雅的继承机制，子域只需覆盖差异 |
| 领域树 | `_tree.json` 前端展示 | ✅ 树形结构直观 |
| Prompt 分层 | 通用prompt + 领域专属prompt，变量自动注入 | ✅ 减少重复，但仍有13个文件需逐域编写 |
| 领域标签 | `role_label/knowledge_unit` 等术语 | ✅ 每域有自己的话语体系 |
| 准入/预检 | 领域关键词密度/业务白名单/异议信号 | ✅ 领域感知的质量检查 |
| 萃取管道 | `extraction_role/extraction_task` 注入prompt | ✅ 领域定制萃取 |

### 1.2 核心局限（扩展到10+领域时会爆的问题）

| 局限 | 具体表现 | 影响 |
|------|---------|------|
| **每个领域13个Prompt文件** | 添加一个领域需写13个md，2-3小时 | 10域=130个文件，维护噩梦 |
| **关键词库手动编写** | `sales_keywords/business_whitelist/marketing_signals` 全靠人写 | 质量不稳定，新域无法自动生成 |
| **无领域质量评估闭环** | 领域上线后没有"萃取质量达标率"度量 | 无法判断领域配置是否有效 |
| **无冷启动机制** | 新领域分身第一天是空壳 | 用户立即流失 |
| **领域数据完全隔离** | 销售"异议处理"方法论无法迁移到法律"异议反驳" | 知识浪费 |
| **无领域版本管理** | YAML改了就改了，没有灰度发布 | 配置错误直接影响生产 |
| **领域ID硬绑定Skill** | 创建Skill时选择domain，之后不可改 | 领域拆分/合并极困难 |
| **前端领域展示固定** | `_tree.json` 手动编辑 | 无法动态增减领域 |

## 二、多领域架构设计：7层架构

### Layer 1 — 领域元模型（Domain Meta-Model）

**目标**：把当前5段YAML升级为可类型校验、可自动补全的元模型。

#### 2.1.1 配置类型系统

```yaml
# domain_meta.yml — 领域元模型定义（全局唯一）
types:
  keyword_group:
    fields: [name, keywords, weight]
    validation:
      weight: {min: 0, max: 5}
      keywords: {min_length: 3}

  scene_mapping:
    fields: [label, keywords, description]
    validation:
      keywords: {min_length: 2}

  context_dimension:
    fields: [name, type, values]
    validation:
      type: {enum: [enum, range, free_text]}
      values: {required_if: {type: enum}}

domain_sections:
  domain:
    required: [id, name, role_label, counterparty_label, skill_label, knowledge_unit]
    derived: [knowledge_unit_plural]  # 自动由 knowledge_unit + "s" 或手动指定

  acceptance:
    required: [min_text_length]
    optional: [sales_keyword_density_min, first_person_ratio_min, ...]
    defaults:
      min_text_length: 100
      chinese_ratio_min: 0.80
      duplicate_similarity_max: 0.85

  precheck:
    required: [scene_mapping]
    defaults:
      min_dialogue_turns: 0
      noise_ratio_max: 0.40

  pipeline:
    required: [extraction_role, extraction_task, extraction_output_fields, context_dimensions]
    defaults:
      extraction_output_fields: [scene_description, expert_thought, standard_script, common_mistakes, applicable_condition]

  chat:
    required: [modes, practice_intents]
    defaults:
      modes: [qa, talk, practice]
```

**收益**：
- 新增领域时，元模型可以 **自动校验配置完整性**（缺了什么字段一目了然）
- IDE 或 CLI 工具可以 **自动生成领域骨架**（`domain init healthcare` 自动生成带默认值的YAML）
- 默认值机制减少80%的配置工作量——大部分领域只需覆盖 3-5 个差异化字段

#### 2.1.2 领域配置继承增强

当前继承是"子覆盖父的非null字段"。升级为：

```yaml
# healthcare.yml — 只需覆盖差异化部分
extends: base  # 不再从具体领域继承，从 base 继承
domain:
  id: healthcare
  name: 医疗健康
  role_label: 医生
  counterparty_label: 患者
  skill_label: 临床决策能力
  knowledge_unit: 诊疗策略

# 其余 4 段全部继承 base 默认值，只需覆盖差异：
acceptance:
  min_text_length: 150  # 医疗案例通常较长
  sales_keyword_density_min: 0  # 不做销售关键词检测
  business_whitelist: [症状, 诊断, 治疗方案, 随访, 影像, 病理]

precheck:
  scene_mapping:
    - label: 急诊决策
      keywords: [急诊, 危重, 抢救, 生命体征]
    - label: 门诊诊疗
      keywords: [门诊, 主诉, 查体, 辅检]
```

**关键升级**：引入 `base.yml` 作为所有领域的根基配置，而非从 `sales.yml` 继承。

#### 2.1.3 领域配置校验器

```java
// DomainConfigValidator.java — 新增
public class DomainConfigValidator {
    private DomainMetaModel metaModel;

    public ValidationResult validate(DomainConfig config) {
        ValidationResult result = new ValidationResult();

        // 1. 元模型字段校验
        metaModel.getDomainSections().forEach(section -> {
            section.getRequired().forEach(field -> {
                if (isNull(config, section, field)) {
                    result.addError(section, field, "required field missing");
                }
            });
        });

        // 2. 关键词库最小覆盖校验
        config.getPrecheck().getSceneMapping().forEach(scene -> {
            if (scene.getKeywords().size() < 2) {
                result.addError("precheck.scene_mapping", scene.getLabel(), "too few keywords");
            }
        });

        // 3. Prompt 文件覆盖率校验
        int covered = countPromptFiles(config.getDomain().getId());
        int required = metaModel.getRequiredPromptCount();
        if (covered < required) {
            result.addError("prompts", null, covered + "/" + required + " prompt files found");
        }

        return result;
    }
}
```

### Layer 2 — 领域注册中心（Domain Registry）

**目标**：从静态 `_tree.json` 升级为动态的、版本化的领域注册中心。

#### 2.2.1 领域注册数据模型

```sql
-- 新增表 domain_registry
CREATE TABLE domain_registry (
    id              VARCHAR(64) PRIMARY KEY,  -- 'sales', 'finance.secondary_market'
    name            VARCHAR(128) NOT NULL,
    parent_id       VARCHAR(64),              -- 领域树父节点
    status          VARCHAR(16) DEFAULT 'draft',  -- draft/review/beta/published/deprecated
    config_version  INT DEFAULT 1,
    config_yaml     TEXT NOT NULL,
    created_at      TIMESTAMP DEFAULT NOW(),
    published_at    TIMESTAMP,
    deprecated_at   TIMESTAMP,
    created_by      VARCHAR(64),
    metadata        JSONB                     -- 扩展字段：行业标签/适用场景/种子数据URL
);

CREATE TABLE domain_version_history (
    id              SERIAL PRIMARY KEY,
    domain_id       VARCHAR(64) REFERENCES domain_registry(id),
    version         INT NOT NULL,
    config_yaml     TEXT NOT NULL,
    change_note     TEXT,
    created_at      TIMESTAMP DEFAULT NOW(),
    created_by      VARCHAR(64)
);

-- 领域关系表（替代 _tree.json）
CREATE TABLE domain_relations (
    parent_id       VARCHAR(64) REFERENCES domain_registry(id),
    child_id        VARCHAR(64) REFERENCES domain_registry(id),
    depth           INT DEFAULT 1,
    PRIMARY KEY (parent_id, child_id)
);
```

#### 2.2.2 领域生命周期 API


#### 2.2.3 题域生命周期 Gate

每个阶段升级需通过对应的 Gate 校验：

| 转换 | Gate | 校验内容 |
|------|------|---------|
| draft → review | 配置完整性 | YAML字段校验、required字段覆盖、关键词库≥3组 |
| review → beta | Prompt覆盖率 | ≥80%的领域prompt文件存在、变量注入测试通过 |
| beta → published | 萃取质量 | 3组样本素材萃取测试，颗粒质量评分≥7/10 |
| published → deprecated | 上线SLA | 活跃Skill数<5 且 30天无新素材上传 |

### Layer 3 — Prompt 模板引擎（Prompt Template Engine）

**目标**：从"13个文件逐域编写"升级为"1个模板 + 领域变量注入 = 全域覆盖"。

#### 2.3.1 当前问题

当前每个领域需13个prompt文件：

```
prompts/domain/sales.b2b_enterprise/
  material_context_tag.md
  material_extract_full.md
  material_extract_short.md
  interview_system.md
  meta_interview_system.md
  skill_practice_customer.md
  skill_practice_opening.md
  skill_practice_angles.md
  skill_practice_evaluate_response.md
  skill_practice_full_answer.md
  practice_analyzer_intent.md
  skill_qa_chat.md
  skill_qa_system.md
```

10个领域 = 130个文件。文件间80%内容相同，只有角色名、术语、场景名不同。

#### 2.3.2 解决方案：三层 Prompt 架构

```
L1 — 通用模板层 (prompts/templates/)
  interview_system.tmpl.md      ← 包含 {domain.*} 变量占位符
  material_extract_full.tmpl.md
  ...

L2 — 领域微调层 (prompts/domain/{domainId}/)
  interview_system.md           ← 仅包含需要覆盖的部分（可选）
  _overrides.yml                ← 声明哪些模板需要领域微调

L3 — 运行时合并层 (PromptTemplateEngine)
  加载 L1 → 注入领域变量 → 检查 L2 是否有覆盖 → 合并输出最终 prompt
```

#### 2.3.3 模板变量体系升级

当前6个变量：`{domain.id}`, `{domain.name}`, `{domain.role_label}`, `{domain.counterparty_label}`, `{domain.skill_label}`, `{domain.knowledge_unit}`

升级为完整变量注入：

```yaml
# domain/sales.yml 新增 prompt_vars 段
domain:
  id: sales
  role_label: 销冠
  counterparty_label: 客户
  skill_label: 销售技巧
  knowledge_unit: 销售锦囊

prompt_vars:                    # 新增段 — 领域专属 prompt 变量
  extraction_focus: "销冠的行为模式、判断时机、话术策略"
  practice_scenario: "我扮演客户，你来扮演销售"
  evaluation_criteria: "是否在正确时机用了正确技法"
  scene_list: "价格谈判、竞品对比、异议处理、决策推进、需求挖掘、方案演示、客户维护、催单逼单"
  knowledge_format: "一个锦囊 = 场景描述 + 销冠内心OS + 标准应对 + 常见失误 + 适用条件"
```

模板中使用：

```markdown
# prompts/templates/interview_system.tmpl.md

你是{domain.role_label}经验萃取师。你的任务是深入访谈{domain.role_label}，
提取他们的{domain.skill_label}——特别是那些{prompt_vars.extraction_focus}。

## 四阶段访谈流程
...
在深度追问阶段，围绕以下场景展开：
{prompt_vars.scene_list}

## 知识颗粒格式
每个{domain.knowledge_unit}应包含：
{prompt_vars.knowledge_format}
```

**收益**：
- 新增领域只需写1个YAML文件 + `_overrides.yml`（如有需要）
- 从13个md文件降到0-2个md文件
- 模板改动一次全域生效

#### 2.3.4 PromptTemplateEngine 实现

```java
public class PromptTemplateEngine {
    private PromptLoader promptLoader;
    private DomainConfigLoader domainConfigLoader;

    public String render(String templateName, String domainId) {
        // 1. 加载领域配置
        DomainConfig config = domainConfigLoader.load(domainId);

        // 2. 构建变量表
        Map<String, String> vars = buildVarMap(config);

        // 3. 加载 L1 通用模板
        String template = promptLoader.loadTemplate(templateName);

        // 4. 检查 L2 是否有领域微调
        String override = promptLoader.loadDomainOverride(templateName, domainId);
        if (override != null) {
            template = mergeTemplate(template, override);
        }

        // 5. 注入变量
        return injectVars(template, vars);
    }

    private Map<String, String> buildVarMap(DomainConfig config) {
        Map<String, String> vars = new LinkedHashMap<>();
        // 基础 6 变量
        vars.put("domain.id", config.getDomain().getId());
        vars.put("domain.role_label", config.getDomain().getRoleLabel());
        vars.put("domain.counterparty_label", config.getDomain().getCounterpartyLabel());
        vars.put("domain.skill_label", config.getDomain().getSkillLabel());
        vars.put("domain.knowledge_unit", config.getDomain().getKnowledgeUnit());
        // prompt_vars 扩展变量
        if (config.getPromptVars() != null) {
            config.getPromptVars().forEach(vars::put);
        }
        return vars;
    }
}
```

### Layer 4 — 题域路由网关（Domain Router Gateway）

**目标**：从"创建Skill时固定domain"升级为"意图识别自动路由领域"。

#### 2.4.1 当前问题

用户创建Skill时选择一个domain，之后所有素材上传、访谈、聊天都绑定这个domain。这意味着：
- 一个用户只能在一个领域内操作
- 跨领域知识无法流动
- 领域选择是静态的一次性决策

#### 2.4.2 解决方案：领域路由层

```python
# ai-service/routers/domain_router.py — 新增

class DomainRouter:
    """基于用户意图 + 领域特征 自动路由到最匹配领域"""

    async def route(self, user_input: str, space_id: str) -> str:
        # 1. 检查 space 是否指定了领域偏好
        domain_preference = await self.get_space_preference(space_id)
        if domain_preference and domain_preference.get("locked"):
            return domain_preference["domain_id"]

        # 2. 意图识别：用轻量 LLM 判断输入属于哪个领域
        domain_scores = await self.classify_domain(user_input)

        # 3. 选择得分最高的已发布领域
        best_domain = max(domain_scores, key=lambda x: x["score"])
        if best_domain["score"] > 0.6:
            return best_domain["domain_id"]

        # 4. 低置信度 → 落入 "general" 通用领域
        return "general"
```

#### 2.4.3 领域意图识别 Prompt

```markdown
# prompts/templates/domain_classifier.tmpl.md

你是一个领域分类器。根据用户输入判断最匹配的领域。

可选领域：
{domain_list_with_descriptions}

用户输入：
{user_input}

请返回JSON格式：
{
  "scores": {
    "sales": 0.3,
    "finance": 0.8,
    "healthcare": 0.1
  },
  "best": "finance",
  "confidence": 0.8
}
```

#### 2.4.4 领域路由应用场景

| 场景 | 当前行为 | 路由后行为 |
|------|---------|-----------|
| 素材上传 | 用户手动选domain | 自动检测domain，用户可修改 |
| 访谈开始 | 沿用Skill的domain | 沿用或按访谈内容动态切换 |
| Chat提问 | 沿用Skill的domain | 跨域提问时推荐最匹配领域的分身 |
| 企业总调度 | 硬路由到默认domain | 按问题意图路由到最匹配分身 |

### Layer 5 — 跨域知识迁移（Cross-Domain Knowledge Transfer）

**目标**：让方法论型知识可以跨领域流动，专业知识严格隔离。

#### 2.5.1 知识颗粒分类体系

当前颗粒没有区分"方法论"和"专业知识"。升级为：

```sql
-- 颗粒表新增字段
ALTER TABLE skill_grain ADD COLUMN grain_type VARCHAR(16) DEFAULT 'domain_specific';
-- grain_type 取值: methodology | domain_specific | cross_domain

ALTER TABLE skill_grain ADD COLUMN domain_source VARCHAR(64);
-- 标记颗粒来源领域

ALTER TABLE skill_grain ADD COLUMN transferable_domains JSONB DEFAULT '[]';
-- 可迁移到哪些领域（methodology 类型才有值）
```

#### 2.5.2 方法论萃取（Meta-Extraction）

当前 `meta_interview` 只萃取"萃取方法论"。升级为 **双轨萃取**：

```
轨1 — 领域萃取 (当前已有)
  销冠访谈 → 提取销售技巧颗粒 (grain_type=domain_specific)

轨2 — 方法论萃取 (新增)
  销冠访谈 → 提取"决策时机判断方法论" (grain_type=methodology)
  此方法论可迁移到: 医疗(临床决策时机) / 法律(诉讼策略时机)
```

#### 2.5.3 方法论萃取 Prompt

```markdown
# prompts/templates/methodology_extraction.tmpl.md

在提取领域专属知识之后，请额外提取可跨领域应用的方法论。

方法论定义：不依赖特定领域术语、描述的是思维模式或决策框架的通用规律。

例如：
- "在信息不完整时如何做决策" — 来自销售异议处理，可迁移到医疗急诊
- "如何识别对方隐藏的真实需求" — 来自销售需求挖掘，可迁移到法律客户诉求分析

输出格式：
{
  "methodology_name": "信息不完整决策法",
  "description": "当信息不完整时，通过假设验证循环逐步缩小不确定性",
  "source_domain": "sales",
  "transferable_domains": ["healthcare", "legal", "education"],
  "original_grain_id": "xxx"
}
```

#### 2.5.4 跨域迁移规则

| 规则 | 说明 |
|------|------|
| **方法论可跨域** | `grain_type=methodology` 的颗粒可出现在其他领域的Chat回答中 |
| **专业知识隔离** | `grain_type=domain_specific` 的颗粒仅在原领域可见 |
| **迁移需标注来源** | 跨域颗粒在回答时标注"此方法论来自{domain.role_label}领域" |
| **用户可关闭** | Space设置中有"是否启用跨域知识增强"开关 |
| **迁移有权重衰减** | 非本领域方法论在检索时权重降低50% |

#### 2.5.5 跨域检索实现

```java
public class CrossDomainGrainSearcher {
    private GrainRepository grainRepo;

    public List<Grain> search(String query, String currentDomain, boolean crossDomainEnabled) {
        // 1. 本领域颗粒检索（权重1.0）
        List<Grain> domainGrains = grainRepo.searchByDomain(query, currentDomain);

        if (!crossDomainEnabled) {
            return domainGrains;
        }

        // 2. 跨域方法论颗粒检索（权重0.5）
        List<Grain> methodGrains = grainRepo.searchMethodology(query, currentDomain);

        // 3. 合并排序：本领域优先，方法论补充
        List<Grain> merged = new ArrayList<>(domainGrains);
        merged.addAll(methodGrains);
        return merged.stream()
            .sorted(Comparator.comparingDouble(g ->
                g.getGrainType().equals("domain_specific") ? g.getScore() : g.getScore() * 0.5
            ).reversed())
            .limit(20)
            .toList();
    }
}
```

### Layer 6 — 题域冷启动引擎（Domain Cold-Start Engine）

**目标**：解决新领域"第一天分身是空壳"的问题。

#### 2.6.1 三层冷启动方案

```
L1 — 种子框架层 (Seed Framework)
  每个领域配置 YAML 中声明 seed_framework_url
  包含: 行业公开知识框架 + 结构化场景树 + 50-200条种子颗粒

L2 — 公开知识层 (Public Knowledge)
  从行业百科/公开案例/专业教材中自动提取种子颗粒
  标记: grain_type=seed, confidence=0.5 (低于实际萃取的0.9)

L3 — 迁移增强层 (Migration Enhancement)
  从跨域方法论池中迁移适用颗粒
  标记: grain_type=methodology, domain_source=其他领域
```

#### 2.6.3 冷启动加载流程

```java
public class DomainColdStartEngine {
    public void initializeDomain(String domainId) {
        DomainConfig config = domainConfigLoader.load(domainId);
        ColdStartConfig coldStart = config.getColdStart();

        // 1. 加载种子框架
        SeedFramework seed = loadSeedFramework(coldStart.getSeedFramework());
        seed.getGrains().forEach(grain -> {
            grain.setGrainType("seed");
            grain.setDomainSource(domainId);
            grain.setConfidence(0.5);  // 种子颗粒置信度低
            grainRepo.save(grain);
        });

        // 2. 从公开源提取
        coldStart.getPublicSources().forEach(source -> {
            List<SeedGrain> extracted = publicKnowledgeExtractor.extract(source);
            extracted.forEach(g -> {
                g.setGrainType("seed");
                g.setDomainSource(domainId);
                g.setConfidence(0.4);
                grainRepo.save(g);
            });
        });

        // 3. 迁移方法论
        coldStart.getMethodologyTransfer().forEach(transfer -> {
            List<Grain> methodGrains = grainRepo.findMethodologyByDomain(transfer.getFrom());
            methodGrains.forEach(mg -> {
                Grain transferred = remapGrain(mg, transfer.getMappings(), domainId);
                transferred.setGrainType("methodology");
                transferred.setDomainSource(transfer.getFrom());
                transferred.setConfidence(0.6);
                grainRepo.save(transferred);
            });
        });

        log.info("Domain {} cold-start completed: {} seed grains, {} methodology grains",
            domainId, seed.getGrains().size(), methodGrainCount);
    }
}
```

### Layer 7 — 题域市场与商业引擎（Domain Marketplace & Commerce）

**目标**：多领域不仅是技术架构，更是商业策略。

#### 2.7.1 题域商店模型

```
题域商店 = 题域配置包 + 种子数据 + 行业适配 Prompt + 认证状态

三种角色:
  平台方 → 提供基础设施 + 2-3个标杆领域(销售/金融/医疗)
  行业伙伴 → 提供行业领域配置 + 种子数据, 平台审核后上架
  企业客户 → 选择领域 + 上传素材 + 萃取自有分身
```

#### 2.7.2 题域定价模型

| 层级 | 内容 | 价格模式 |
|------|------|---------|
| 基础领域 | 平台提供的标杆领域(销售/金融) | 免费或基础订阅 |
| 行业领域 | 行业伙伴提供的领域(医疗/法律/教育) | 按领域订阅，¥X/月 |
| 定制领域 | 企业客户定制的专属领域 | 按定制费 + 萃取量计费 |
| 跨域增强 | 开启跨域方法论迁移 | 按迁移颗粒数计费或高级订阅 |

#### 2.7.3 题域效果计量

```sql
-- 题域效果度量表
CREATE TABLE domain_metrics (
    domain_id       VARCHAR(64),
    metric_date     DATE,
    active_skills   INT,          -- 活跃 Skill 数
    total_grains    INT,          -- 颗粒总量
    avg_grain_quality FLOAT,      -- 平均颗粒质量评分
    chat_sessions   INT,          -- Chat 会话数
    chat_satisfaction FLOAT,      -- Chat 满意度(用户评价)
    practice_sessions INT,        -- 对练会话数
    practice_improvement FLOAT,   -- 对练提升率(前后对比)
    seed_ratio      FLOAT,        -- 种子颗粒占比(越低越好,说明真实萃取越来越多)
    cross_domain_usage INT,       -- 跨域颗粒被调用次数
    PRIMARY KEY (domain_id, metric_date)
);
```

#### 2.7.4 题域运营看板

```
核心指标:
  题域健康度 = (avg_grain_quality × 0.3) + (chat_satisfaction × 0.3) + (practice_improvement × 0.2) + ((1-seed_ratio) × 0.2)

  健康度 > 0.7 → 题域运行良好
  健康度 < 0.5 → 需要投入更多种子数据或调整配置
  健康度 < 0.3 → 题域考虑废弃

增长指标:
  新Skill创建速率
  颗粒增长速率(真实萃取 vs 种子)
  跨域迁移利用率
```

## 七、关键设计决策与争议点

### 7.1 题域继承应从 base 还是从同类领域继承？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: 从 base 继承** (推荐) | 干净的继承链，无领域间耦合 | 需写 base.yml 的默认值 |
| B: 从同类领域继承 | 如医疗从金融继承 | 领域间耦合，金融改配置影响医疗 |

**推荐方案A**。base.yml 应只包含最通用的默认值（如 `min_text_length=100`），所有领域从 base 继承后再覆盖差异化部分。

### 7.2 跨域迁移是否应自动？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: 半自动** (推荐) | YAML声明迁移映射，人工确认 | 需人工配置映射关系 |
| B: 全自动 | LLM自动判断可迁移颗粒 | 准确率不稳定，可能迁移不相关内容 |
| C: 不迁移 | 领域完全隔离 | 知识浪费，冷启动困难 |

**推荐方案A**。冷启动配置中声明迁移映射（如异议处理→患者顾虑应对），运行时按映射表迁移，用户可开关。

### 7.3 种子颗粒的置信度如何与真实萃取区分？

| 方案 | 说明 |
|------|------|
| **confidence 分级** | 种子=0.5, 迁移方法论=0.6, 实际萃取=0.9 |
| 回答标注 | 种子回答标注"尚未经过专家验证" |
| 逐步替换 | 真实萃取颗粒积累后，自动降低种子权重 |

**推荐全部采用**。confidence 值在检索时直接影响排序权重，回答标注给用户透明度，自动降权确保分身越用越好。

## 八、总结：从2领域到20领域的路径

| 维度 | 当前(2领域) | 升级后(20领域) |
|------|------------|---------------|
| 新增领域耗时 | 4-6小时 | 1-2小时 |
| 配置文件数 | 13×N=26 | 1×N=20 + 1模板集 |
| 冷启动 | 空壳 | 种子+迁移，首日即有回答能力 |
| 知识迁移 | 无 | 方法论跨域流动 |
| 质量闭环 | 无 | 题域健康度度量 → 配置迭代 |
| 版本管理 | 无 | 题域版本历史 + 灰度发布 |
| 商业模型 | 未定义 | 题域订阅 + 效果计量 |
| 题域运营 | 手动 | CLI工具 + 运营看板 |

核心原则：**领域差异化部分应尽量少，通用部分应尽量多**。通过元模型默认值、Prompt模板引擎、冷启动种子、跨域迁移四个机制，把新增领域从"写全套配置"降到"只写差异化声明"。
