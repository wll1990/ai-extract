## 3. 阻塞项（T1 编码前必须改设计）

### B1 「阶段」概念在 DDL 里丢失

**证据**：docs/38 §3「阶段、任务」、§6 T1「配置阶段和任务」、§7「即时刷新阶段列表」；计划文件表名直接写「training_task 任务/阶段」。docs/43 的 `training_task` 只有 `order_no`，没有阶段列，§2 的 D1–D8 也没把它列为缺口。

**后果**：计划编辑器只能画扁平列表，docs/43 §八 自己承诺的「PlanEditor 阶段任务树」无法落地；学员「我的培训」无法按阶段分组。

**裁决建议**：`training_task` 增 `phase_no int NOT NULL DEFAULT 1` + `phase_name varchar(100)`，不建独立 stage 表——阶段只需要分组和排序，没有独立生命周期、权限或截止时间，建表是过度设计。索引 `(plan_id, version, phase_no, order_no)` 覆盖任务树读取。

### B2 分配链路断在第一步：没有创建批次的接口

**证据**：培训侧 API 只有 `GET /training-cohorts`，`POST /training-assignments/batch` 却要求 `cohortId`。docs/43 已识别（D1），但 API 清单没补。

**裁决建议**：补 `POST /admin/training/cohorts`，请求体 `{planId, planVersion, name, mentorId, deadline}`，服务端校验计划版本已发布。

### B3 路由前缀自相矛盾，按任一套实现都会 403

**证据**：docs/43 §7 权限码表用无前缀的 `/training-plans`、`/training-cohorts`，同节 `SecurityConfig` 却只放行 `/admin/training/**`；而 `SecurityConfig` 默认 `denyAll()`。评测侧实际落地是 `/admin/evaluations`。

**裁决建议**：冻结为
- 管理侧：`/admin/training/**`（`/admin/training/plans`、`/cohorts`、`/assignments`、`/task-records`）
- 学员侧：`/me/training/**`（`/me/training/assignments`、`/me/training/task-records/{id}/...`、`/me/training/attempts/{id}/...`）

学员侧统一挂 `/me/` 不只是命名偏好——它让"我是谁"只能来自 JWT，从路由层就堵住 B7 的越权。

### B4 补训与 `UNIQUE(cohort_id, learner_id)` 直接冲突，且无处存溯源

**证据**：契约 `POST /training-assignments/{id}/remediations → {newAssignment}`；表上 `UNIQUE (cohort_id, learner_id)`。同一批次给同一学员再建一条 assignment 会 409。`training_assignment` 也没有 `source_assignment_id`，docs/38 要求的「链接原失败结果」无字段可存。

**裁决建议**：**补训 = 新建一个补训批次（cohort）**，绑定同一计划的新版本或专门的补训计划，新 assignment 通过 `source_assignment_id` 指回原分配。理由：
1. 保住「分配绑定冻结版本」的不变式（同一 assignment 里塞不进新版本的 task）；
2. 保住唯一约束；
3. 「我的培训」把补训批次和原批次都列出来，语义清楚。

DDL 增 `training_assignment.source_assignment_id uuid`。这条虽然是 P3 功能，但列必须现在加，否则上线要迁表。

### B5 评分失败无 `error` 态 + `grading` 租约不可恢复

**证据**：`training_attempt.status` 只有 `in_progress/submitted/grading/pending_review/finalized`；`idx_tat_claimable` 只索引 `WHERE status='submitted'`。评测侧已经踩过这个坑并留下了注释：[evaluation-schema.sql:202-204](scripts/evaluation-schema.sql#L202-L204) 的索引覆盖 `('pending','generating')` 两态，`lockClaimableIds` 同样捞两态。

**故障场景**：worker 把行置 `grading` 后进程崩溃 → 租约到期，但状态不是 `submitted`，永远领不回来 → 学员永远看到「评分中」。AI 报错时同样无处落错误原因。

**裁决建议**：
- 状态枚举加 `error`，表加 `error_message text`、`grading_attempts int NOT NULL DEFAULT 0`
- 索引改为 `(status, lease_expires_at) WHERE status IN ('submitted','grading')`
- 领取条件同样覆盖两态；评分异常走 `markError`（置 error + 释放租约），提供主管侧「重试评分」

### B6 没有截止扫描器，也没有考试时长字段

**证据**：D4 新增了 `deadline_policy=auto_submit/timeout_fail`，但 §9 的 T1–T6 里没有任何截止扫描任务；索引也没有支撑 `status='in_progress' AND deadline < now()`。`training_task` 无 `exam_duration_minutes`，`training_attempt.deadline` 只能抄批次截止时间。

**故障场景**：学员在批次截止前 1 分钟开考 → 1 分钟后被判超时；逾期策略完全不生效。

**裁决建议**：
- `training_task` 增 `exam_duration_minutes int`（exam 类型必填）
- 开始考试时 `deadline = min(now() + duration, assignment.deadline)`
- 增 `TrainingDeadlineSweeper`（复用评测 worker 的租约 + 短事务模式），部分索引 `(deadline) WHERE status='in_progress'`
- 扫描器进入 T5 交付物

### B7 学员可以拿自己的 JWT 读/改别人的考试（IDOR）

**证据**：docs/43 §7 只有 URL 级 `hasAuthority(TRAINING_LEARN)`；§8 的三条"不可妥协"约束里没有归属校验。`TRAINING_LEARN` 一旦给 employee 全员，任意员工猜一个 UUID 就能 `GET /training-attempts/{id}`、`PUT answers`、`POST submit`。

**裁决建议**（同时解决 B3 的归属问题）：
1. 学员侧一律走 `/me/training/**`，`userId` 只从 `TokenContext` 取；
2. `TrainingAccessService.assertLearnerOwnsAttempt(attemptId)` / `assertLearnerOwnsRecord(recordId)`：attempt → assignment → `learner_id == userId`，不匹配返回 **404**（不是 403，避免探测存在性）；
3. 管理侧复核走另一条路径，按 `company_id` + `TRAINING_REVIEW` 校验；
4. 纳入 §8「不可妥协」清单，单测必须覆盖「学员 A 读 B 的 attempt → 404」。

### B8 冗余计数会在重考时重复累加，撞 CHECK 直接回滚

**证据**：§6 规定 `completed_tasks` 只做 `+1` 增量；docs/38 明确支持「再练/补考」。attempt1 失败 → task_record 置 `failed`、`completed+1`；attempt2 通过 → 再 `+1`。单任务计划下 `completed=2 > total=1`，违反 `ck_ta_counters`，提交事务回滚。

**裁决建议**：增量必须带状态迁移守卫——
```sql
-- 仅当旧状态不是终态时才 +1，且 passed 只在非 passed → passed 时 +1
UPDATE training_assignment
   SET completed_tasks = completed_tasks + 1,
       passed_tasks    = passed_tasks + :passedDelta
 WHERE id = :assignmentId;
```
配合 `TrainingTaskRecordService` 用**旧状态**判定（读旧行、算 delta、原子 UPDATE），并把「同一 task_record 的多次 attempt 只算一次完成」写进单测。这是 docs/43 只写"同一事务"但没写"只迁一次"的漏洞。

### B9 复核与进度：接口/页面互相缺失

**证据**：T6 要交付「批次详情」页（成员+进度），但 `GET /cohorts/{id}/progress` 被划到 P3；§9 又把「主管复核」提进 P2，却没有承载复核的页面（学员详情也归 P3）。

**后果**：页面是空壳或要造假数据（违反零假数据）；`pending_review` 依然卡死——正是把复核提进 P2 想解决的问题。

**裁决建议**：
- 把 `GET /admin/training/cohorts/{id}/progress` 提进 P2（直接读 `training_assignment` 三列冗余 + 学员姓名，不聚合任务明细，代价极低）
- 复核交互放在「批次详情 → 学员抽屉 → 尝试详情」，不单开「学员详情页」；抽屉里做通过/退回
- P3 保留「学员详情页 + 证据下钻 + 补训」

### B10 陪练没有前端页面

**证据**：T6 列 5 个页面，缺「任务执行页」；阅读与陪练都落在这页。docs/38 §1 明确三种任务含陪练。

**裁决建议**：T6 改为 7 页：计划列表、计划编辑器（阶段树）、批次详情（含学员/尝试抽屉）、我的培训、任务执行页（按 `type` 渲染阅读/陪练）、考试页、成绩页。

### B11 导师 `mentor_id` 没有权限落点

**证据**：角色只有 super_admin / company_admin / employee。`TRAINING_REVIEW` 只在公司管理员层；`cohort.mentor_id` 指向的用户若为 employee，无法复核。

**裁决建议（P2）**：复核权限**只给 company_admin / super_admin**；`mentor_id` 仅用于展示与后续通知，不授予权限。若必须支持"导师只复核自己批次"，需要在 Service 层做数据级授权（`cohort.mentor_id == userId` 或同企业），那是 P3 的事，现在不要用字段暗示一个不存在的权限模型。

### B12 计划发布后无法修改（缺"新建版本"）

**证据**：评测侧有 `POST /evaluation-datasets/{id}/versions`；培训侧 API 清单没有对应物，而 docs/38 说「计划之后更新不自动重置学员进度」。

**裁决建议**：补 `POST /admin/training/plans/{id}/versions`（从已发布版复制任务到新 draft），并明确：**published 版本的 task 只读**，任何编辑走新版本。

### B13 P2 终点是 `pending_certification` 死胡同

**证据**：§5 状态机保留 `pending_certification → certified`，但 `certify` 归 P3。学员全部必修通过后，没有任何接口能推进。

**裁决建议**：把 `POST /admin/training/assignments/{id}/certify` 提进 P2（服务端校验必修全过 → 写 `training_certification` + 置 `certified`，一个事务）。理由：这是"培训闭环"的最后一环，缺了它 P2 交付的是半成品；而实现量只有一个端点 + 批次详情里的一个按钮。P3 再补「补训、看板、导出、学员详情」。

## 8. 评审结论

- docs/43 V1.0 作为"数据模型草案"是合格的：版本化、执行态与结论分离、计数同事务、三条安全方向都站得住。
- 作为"可直接编码的设计"**不合格**：13 条阻塞项里有 6 条会写进表结构，之后修要迁数据。
- 修订后按 docs/43 的任务拆分推进，但 T1 之前必须先把 §3 的裁决落到文档里，再冻结。

> 评审中"技术：不通过"是本次的真实结论，不修饰。前两轮（docs/41/42）评测侧之所以能收口，是因为在真实环境里跑过；培训侧一张表都没有，设计阶段的漏洞只能在纸面上抓，这一轮抓出的比评测侧多属正常。
