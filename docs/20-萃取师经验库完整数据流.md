## 一、整体架构

```
 ┌──────────┐    POST JSON     ┌────────────┐    @Scheduled     ┌──────────────┐
 │  D3 页面  │ ──────────────→ │  Backend    │ ←────────────── │  Scheduler   │
 │ (上传弹窗) │   /admin/experts │ (Spring)   │   每30s扫描      │ (定时轮询)    │
 └──────────┘   /upload        └─────┬──────┘                 └──────┬───────┘
                                     │                               │
                                     │ status=pending                │ 1. findPendingTasks
                                     │ locked_by=NULL               │ 2. tryLock(id, workerId)
                                     ▼                               │ 3. analyzeMaterials(id)
                              ┌────────────┐                         │ 4. releaseLock(id)
                              │ PostgreSQL │ ←──────────────────────┘
                              └─────┬──────┘
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
           expert_skill      expert_grain     expert_document
           (locked_by,       (7 categories,   (file_name, parsed_content,
            locked_at,        application_     file_url, status)
            status)           rule, priority)
```

## 二、状态机

```
                    ┌─────────┐
          上传 ──→  │ pending │  (locked_by=NULL, 待调度器扫描)
                    └────┬────┘
                         │ @Scheduled 抢锁成功
                         ▼
                    ┌───────────┐
                    │ analyzing │  (Worker 正在调用AI+文件解析)
                    └─────┬─────┘
                          │ 成功                      失败
                          ▼                           ▼
                    ┌────────────┐              ┌────────┐
                    │ extracting │              │ failed │ (locked_by释放, 下次重试)
                    └─────┬──────┘              └────────┘
                          │ 手动点"提取法则"
                          ▼
                    ┌────────────┐
                    │ extracting │  (法则已提取, status=under_review)
                    └─────┬──────┘
                          │ 管理员审核激活
                          ▼
                    ┌────────┐
                    │ active │  (法则 status=active, 可注入访谈)
                    └────────┘
```

## 三、数据存储位置

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 萃取师基本信息 | `expert_skill` 表 | name, description, styleTags(JSONB), industryTags(JSONB), seniority, status, locked_by, locked_at |
| 上传文件元数据 | `expert_document` 表 | file_name, file_url, file_type, file_size, parsed_content(TEXT, AI解析后的纯文本), status |
| 上传文件物理存储 | `/data/files/experts/{expertId}/{fileName}` | Docker 卷挂载，由 Python parse-file 端点读取 |
| AI 生成报告 | `report` 表 | title, content_json(JSONB, 六章结构), space_id(NULL表示萃取师报告) |
| 萃取法则 | `expert_grain` 表 | category(7类), knowledge_content, application_rule, priority, consensus_type, status |
| 综合 Skill | `prompts/experts/expert_composite.md` | 由 ExpertComposer 生成，含所有 active 萃取师的共识/独家/矛盾经验 |
| 调度器状态 | `expert_skill.locked_by` + `expert_skill.locked_at` | 乐观锁字段，超时 5 分钟自动释放 |

## 四、完整流程（从上传到激活）

### 步骤 1：前端上传

```
D3 页 UploadExpertModal
  → onUpload({name, styleTags, industryTags, seniority, files})
  → POST /admin/experts/upload (JSON body: {name, ..., files:[{fileName, fileType, fileSize}]})
```

**后端处理** (`ExpertService.uploadExpertMaterials`):
- 创建 `expert_skill` 记录: `status='pending'`, `locked_by=NULL`
- 创建 `expert_document` 记录: `status='uploaded'`, `parsed_content=NULL`
- **返回** expertId + status=pending

### 步骤 2：定时调度

```
ExpertAnalysisScheduler.scanAndProcess() @Scheduled(fixedDelay=30_000)
  → findPendingTasks(): WHERE status='pending' AND (locked_by IS NULL OR locked_at < NOW()-5min)
  → tryLock(id, workerId): UPDATE SET locked_by=?, locked_at=NOW() WHERE id=? AND locked_by IS NULL
  → 抢锁成功(返回1) → analyzeMaterials(id)
  → releaseLock(id): UPDATE SET locked_by=NULL, locked_at=NULL
```

### 步骤 3：AI 分析 (`ExpertService.analyzeMaterials`)

```
1. 状态改为 "analyzing"（前端显示"分析中..."）
2. 查 expert_document 列表
3. 逐个调 Python /internal/parse-file 解析文件
   - 文档类 → 自动解析 → status="parsed"
   - 图片/音频 → 返回提示词 → status="pending_manual"
4. 如果有 pending_manual 文件 → 跳过AI分析，保持 pending
5. 全部 parsed → 构建分析提示词:
   - 萃取师元数据 + 全部文件 parsed_content
6. 调 AI 生成七章《萃取师经验报告》JSON
7. structureExpertReport() 二次格式化为六章标准 JSON
8. 存入 report 表 (space_id=NULL)
9. reportId 追加到 skillFile（注意：该字段同时存储 prompt 文件路径和报告 ID 历史 JSON 对象，见 ExpertService.saveSkillFileMeta） 历史列表（JSON数组）
10. 状态改为 "extracting"
```

### 步骤 4：提取法则（自动化 + 全量重提）

```
analyzeMaterials 完成后 status=extracting，需管理员手动调用 POST /admin/experts/{id}/extract 触发 extractGrains()

extractGrains():
  1. 删除该萃取师全部旧法则（deleteAll）
  2. 从 skillFile 读取全部历史报告ID列表
  3. 逐个加载报告 contentJson → AI拆解法则
  4. 降级: generateDefaultExpertGrains() 生成基础法则
  → expert_grain(status='under_review')
  → 更新 expert_skill.grainCount

核心理念:
  - 传了就分析，每次全量重新提取
  - 今天传3个 → 提取3条法则
  - 明天又传3个 → 删旧法则 → 从6份报告全量提取
  - 用户不需要关心"传完没"，系统自动处理
```

**7 类颗粒映射**:
| category | 含义 | 在访谈中的应用 |
|---|---|---|
| `typing_method` | 销冠分类方法 | 开场定调阶段判断销冠类型 |
| `judgment_intuition` | 追问判断直觉 | 注入到追问规则 |
| `mental_model` | 心智模型 | 注入到模型提炼阶段 |
| `failure_lesson` | 失败经验教训 | 注入到禁忌规则 |
| `validation_method` | 验证方法 | 注入到收网确认阶段 |
| `metaphor_framework` | 隐喻框架 | 注入到心智挖掘阶段 |
| `rhythm_sense` | 对话节奏 | 注入到对话节奏控制 |

### 步骤 5：激活 Skill

```
POST /admin/experts/{id}/activate
  → ExpertService.activateExpert
  → under_review 法则 → active
  → 设置 expert_skill.skill_file = '/prompts/experts/expert_{id[:8]}.md'
  → expert_skill.status = 'active'
  → @Async regenerateCompositeAsync（当前为空壳实现，待后续版本完成）:
     加载所有 active 萃取师的法则
     → 按 category 分组比对语义相似度
     → 合并共识(consensus)、保留独家(single)、标记矛盾(conflict)
     → 生成 expert_composite.md
```

### 步骤 6：访谈注入

```
创建访谈时:
  选"综合" → loadCompositeExpertKnowledge()
              → 查所有 active 萃取师 + active 法则
              → 拼入 System Prompt

  选"张萃取师" → loadExpertKnowledge(expertSkillId)
                 → 查该萃取师的 active 法则
                 → 按 category 分组拼入 System Prompt

  选"基础版" → 不加载任何萃取师经验
```

## 五、追加文件（简化设计）

```
用户随时上传新文件:
  → 创建 expert_document 记录
  → 设置 expert_skill.status = 'pending'
  → 调度器下次扫描时自动重新分析
  → 分析完成 → 自动提取法则（全量重提）

不需要手动"追加/替换/删除"操作——传了就分析。
报告历史通过 skillFile 字段（JSON数组）追踪。
每次提取法则时从全部历史报告重新提取。
```

## 六、关键设计决策

1. **DB 层任务队列而非消息队列**: 当前规模下，PostgreSQL 轮询 + 乐观锁足以保证任务不丢不重。未来扩展至 100+ 萃取师时可引入 RabbitMQ。

2. **report.space_id 可空**: 萃取师报告不属于任何销售空间，`space_id=NULL` 是正确设计。之前的 `NOT NULL` 约束是遗留问题。

3. **文件解析在 Python 端**: 利用 Python 生态（python-docx, PyPDF2）处理文档解析，Java 端只存元数据和调用 HTTP。

4. **法则独立于报告**: `expert_grain` 表不依赖 `report` 表的外键。报告重新生成→颗粒重新提取，但旧颗粒保留历史版本。
