# 培训方案生产协作平台与IM数字分身

> 范围修订（2026-11-13）：根据后续讨论，首版收缩为标准资料归集、共享查询、一个可复用的方法能力，以及IM文字查询/临时补充背景。下文项目群绑定、IM上传、审批、生产任务通知等均为延期设想，不进入当前MVP。首版以《40-团队资料与Agent能力共享MVP》为准。

日期：2026-11-13。状态：讨论稿；范围为团队生产培训方案与课程，不等同于新人学习系统。

## 1. 产品定位

网页管理项目、知识资产、流程、版本和审核；IM数字分身负责便捷沟通、需求收集、查询、任务发起和通知。
网页与IM操作同一套后端业务、权限和任务记录，不能形成两套项目事实。

业务主线：需求接收→澄清确认→问题诊断→匹配案例知识→方案/课程大纲→交付物制作→审核交付→复盘沉淀。
资料分为原始资料、项目上下文、已审核团队资产、生产记录；客户资料不自动进入团队公共知识库。

## 2. IM具体需求

| 场景 | 用户表达/动作 | 系统实际行为 |
|---|---|---|
| 进入项目 | 打开绑定项目群，或私聊选择项目 | 显示项目名称、阶段与本人可操作事项 |
| 记录需求 | 发文字、语音或文件 | 原文留存、解析转写，生成待确认需求；语音/文件接入须验证渠道权限和API |
| 补充事实 | “受众改成区域经理” | 展示简报修改差异，确认后产生新版本 |
| 检索经验 | “有没有类似制造业主管培训案例” | 按项目和成员权限检索，返回依据及适用边界 |
| 讨论方案 | 针对当前方案提问 | 使用指定方案版本讨论，建议不直接覆盖正式文档 |
| 发起生产 | “按已确认需求生成一天课程大纲” | 生成任务提案，明确输入/输出，确认后排队执行 |
| 查看进展 | “大纲做到哪里了” | 从任务记录返回真实进度，不由模型猜测 |
| 提交修改 | “第二模块多加一个练习” | 绑定目标版本产生修改任务，新版保留旧版 |
| 审核 | 批准/退回及理由 | 对身份、权限、状态、版本再次校验，保存审核记录 |
| 接收通知 | 等待任务结果/审核提醒 | 异步完成后发送摘要和受控网页链接 |
| 知识沉淀 | “把这个项目整理成案例” | 建待审核候选，脱敏授权后才进入共享资产 |

首版只支持内部团队；客户外部群使用独立权限和内容策略，后续单独确认。
日常讨论不自动归档为客户事实；明确提到机器人/指定采集操作才纳入处理，渠道订阅行为另行核实。

## 3. 绑定与身份

新增ExternalIdentity绑定渠道租户+外部用户与内部User，不能继续用合成UUID加employee角色访问项目资产。
绑定经过内部登录/管理员邀请校验；离职、取消成员和企业停用即时阻止后续操作。
新增ProjectConversationBinding：企业、渠道、机器人、群聊/会话、项目、允许用途与通知规则。
项目群首版建议一个群绑定一个项目；同一项目可有多个受控入口。
私聊支持显式选择/切换项目，每次写操作显示目标；无法确定时先选择，不凭聊天猜测归属。
项目绑定权限与群成员可见范围分别校验；员工有权限不代表可以把私有结果发到其所在任意群。
群成员变化后重新检查共享范围；敏感结果只回私聊或发受控链接，链接访问再次鉴权。

## 4. 技术链路

IM适配器→验签/事件去重→用户身份与企业解析→项目上下文→意图识别→只读查询或动作提案→业务服务→任务执行→版本结果→通知发件箱→IM适配器。
网页直接调用同一业务服务。
后端决定读写范围；模型只提出结构化意图和参数，不直接执行SQL、不自行决定授权。
附件经授权下载、大小/类型验证、存储与解析；保留渠道来源与消息ID。文档中的指令不能覆盖系统权限。

建议新增服务职责：
- ProjectService/ProjectBriefService：项目、成员、确认事实和需求版本。
- ContextAssemblyService：只组装当前任务所需且有权读取的资料，保留出处。
- ProductionWorkflowService：阶段、前置条件、负责人、审核规则。
- ProductionTaskService/Worker：生成与修改、幂等、检查点、超时、取消、恢复。
- DeliverableService：版本、引用、差异、批准及导出。
- ImProjectRouter/ExternalIdentityService：渠道身份与项目路由。
- ActionProposalService：意图参数校验、提案、确认与执行审计。
- NotificationOutboxService：任务完成/失败/待审通知，投递重试和状态。

复用现有Spring Boot、Next.js、PostgreSQL/pgvector、知识案例库、解析服务、飞书桥和HMAC机制。
需要核实第三方渠道的附件、语音、按钮回调、群事件和主动消息权限；未验证能力不承诺上线。

## 5. 长任务与确认

IM先快速受理并返回任务号，后台持久执行；不保持一个消息请求等待整份课件生成。
回调事件幂等按企业+渠道+事件ID，动作确认按提案ID；按钮重复点击不得重复创建任务或扣额度。
提案包含项目、动作、目标版本、输入快照、输出类型、有效期和发起人。
生成可按企业规则确认；覆盖需求、批准、对外发送、公开共享必须明确授权，首版通过确认卡/网页确认。
确认时重新鉴权与版本检查；旧卡片版本失效返回冲突，并引导查看新版，不直接覆盖。
通知由业务事务写outbox，后台投递；发送失败不把已完成生成任务改为失败。
渠道不支持可靠卡片确认时，退回受控网页，不用模糊“好的”推断批准。

## 6. 模型与上下文

任务持久保存企业、项目、操作者、资料版本、方法包版本和模型配置引用；不能只依赖ThreadLocal。
企业Key由后端路由，IM永不接收/展示明文Key；模型失败不未经授权切到其他企业或平台凭证。
知识检索先权限过滤再召回；项目资料、共享内容与聊天历史分开，禁止全量历史直接注入。
聊天讨论、已确认事实、AI推断分别存储；重要决策形成结构化版本记录。
面向Codex/Pi/Grok等工具可先导出授权任务包并回传产物，不预设每个工具都可API调用。

## 7. 首版顺序与验收

1. 项目空间+简报+成员权限+知识案例引用+大纲版本。
2. 飞书文字入口+真实身份绑定+单群项目绑定+查询与需求补充。
3. IM生成任务提案→确认→后台大纲生成→结果通知→网页审核→IM查询同一状态。
4. 再接文件、语音、卡片审核、更多交付物和其他IM渠道。

最小验收：项目负责人在群里提出需求，机器人整理待确认简报；确认后生成课程大纲；另一成员在网页修改，负责人收到待审提醒；批准版本全渠道一致。
异常验收：重复消息不重复执行；未授权成员无访问；群内不泄露个人受限资料；旧按钮不能批准新版本；服务重启任务可恢复；通知失败可重试。
效果观察：需求澄清轮次、首份可用大纲耗时、审核修改量、交接成本、引用错误及资产复用。

## 8. 当前代码的具体差距

ImInboundService当前将外部用户转为合成UUID，以employee角色进入分身聊天，不是完整内部账号授权。
飞书Bridge.askMessage聚合SSE正文；parseSse忽略source/meta等，尚不是任务受理与结果通知协议。
ImChannel主要绑定Skill，项目与群聊的绑定需新增；不能简单把Skill当项目。
现有文档评论处理可作为来源入口复用，但不等于文档编辑/版本审核功能。
