## 1. 认证确认

### 状态机

```
pending_certification ──certify──> certified
```

- 只有分配处于 `pending_certification` 才能确认；`in_progress/not_started` → 409「必修任务尚未全部通过」，`cancelled` → 409「已取消」。
- 认证前**从 `task_record` + 冻结任务表重算**必修通过数，不直接读 `required_passed` 冗余列。
- 写入 `training_certification`（`UNIQUE(assignment_id)`）：`status=confirmed`、`confirmed_by`、`confirmed_at`、可选 `note`；`company_id`/`learner_id` 取自分配，不取 token。
- 重复确认**幂等**：已 `certified` 且认证记录 `confirmed` 时直接返回既有记录。

### 并发与权限

- 先对 `training_assignment` 加 `PESSIMISTIC_WRITE` 行锁，再查认证记录：两个并发确认不会撞 `uq_tcf_assignment`，第二个请求走幂等分支。
- 数据范围与复核同源：`assignment → cohort → assertCanReview(cohortId)`；跨企业/非导师 404。
- 不能认证自己（D26）：`reviewer == learner` → 403，`super_admin` 例外。
- 认证结果统一为 `CertificationView{status,confirmedBy,confirmedByName,confirmedAt,note}`，在 certify 响应、我的培训、批次详情成员、批次进度行四处共用；无记录时显式 `null`。
- 批次进度行额外下发 `canCertify`、`certifyBlockedReason`（`already_certified/cancelled/not_pending/required_not_passed/self`）与 `certificationBlockers[{taskId,title,recordStatus}]`，主管不用点进认证按钮才知道缺哪门必修；`pendingReview` 逐行标识待复核学员。

### 接口

`POST /admin/training/assignments/{id}/certify`（`TRAINING_REVIEW`）

```json
// 请求（body 可省略）
{"note":"必修全过，确认上岗"}

// 响应
{"assignmentId":"...","status":"certified",
 "certification":{"id":"...","status":"confirmed","confirmedBy":"...",
                  "confirmedAt":"2026-10-29T00:43:48","note":"..."}}
```

## 2. 截止扫描器

`TrainingDeadlineSweeper`（`scheduler/`，`@Scheduled` 默认 60s）每轮处理两类来源：

| 来源 | 查询 | 说明 |
|---|---|---|
| 考试 | `training_attempt.deadline < now()` | 命中部分索引 `idx_tat_deadline` |
| 陪练 | `training_attempt.deadline IS NULL` 且 `training_assignment.deadline < now()` | 陪练没有 attempt 级截止，以分配截止为准 |

策略（来自 `training_task.deadline_policy`）：

- `auto_submit`：条件更新 `in_progress → submitted`，并写 `termination_reason=auto_submit`，随后由评分 worker 正常判分；
- `timeout_fail`：条件更新 `in_progress → pending_review`，写入建议结论 `fail` 与 `termination_reason=timeout_fail`，进度行转待复核。
  **超时结论不直接定稿**：必须给主管一次裁决机会（可申诉），避免“系统判死、学员无路可走”。
  主管通过 → 任务 passed；退回 → failed。

> 2026-10-29 五方复审修订：原实现是 `timeout_fail → finalized/fail`，被安全 S-F13 / 产品 P-F5 / 技术 T-F1 同时判定为不可申诉终态，已改为转人工复核。
> AI 评分连续失败落 `error` 时同样把进度行转待复核，并允许主管复核 `error` 尝试（否则认证永久卡死）。

安全点：

- 所有状态写入都带 `WHERE status='in_progress'`，学员恰好先提交时命中 0 行，不会覆盖正常流程；
- 两条查询都过滤 `training_assignment.status IN (not_started,in_progress,pending_certification)`：已取消/已认证的分配不再被扫描、不再产生成绩或计数副作用；
- 单个尝试一个短事务，事务内无 AI/网络调用；单条异常只记日志，不拖垮整轮；两类查询各自 try/catch，互不阻塞；
- **无法处理的脏行置 `error` 移出队列**（任务/记录缺失、分配已结束），避免队头永久占满每轮 LIMIT；
- 学员侧写路径（存草稿/发言/提示/交卷）统一校验分配仍可操作，取消后不能继续写。

配置：

```yaml
app.training.deadline:
  enabled: true
  interval-ms: 60000
  initial-delay-ms: 30000
  batch-size: 50     # 每类每轮最多处理条数
```

## 4. 实机证据（真实服务 + 真实库）

认证：

```
POST certify → 200 certified / certification{confirmed, confirmedByName=系统管理员, confirmedAt, note}
再次 certify → 200 alreadyCertified=true（幂等，无新记录，备注不被覆盖）
对 in_progress 分配 certify → 409「必修任务尚未全部通过，不能认证」
批次进度行：canCertify=false / certifyBlockedReason=already_certified
            certificationBlockers=[]
批次详情成员、我的培训：同一 CertificationView（含 confirmedByName）
```

截止扫描（2026-10-29 复审后）：

```
auto_submit：deadline 改为 5 分钟前
  → 扫到代交 → 评分 worker 判分 → attempt=pending_review/pass
  → terminationReason=auto_submit（来源可见）

timeout_fail：新建计划（1 题、1 分钟、timeout_fail）→ 开考 → deadline 改为 5 分钟前
  → attempt=pending_review/fail，terminationReason=timeout_fail，needsReview=true
  → 学员成绩 status=pending_review、result=null、score=null
  → 主管复核 pass → 200 finalized/pass，record=passed，分配 completed 1 / passed 1
    → 进入 pending_certification
  日志：逾期转人工复核 policy=timeout_fail
```

## 5. 已知限制

| 事项 | 说明 |
|---|---|
| 扫描延迟 | 最坏一个扫描周期（默认 60s）后才结束逾期尝试；前端以服务端状态为准 |
| `pending_review` 滞留 | 不自动定稿（成绩不能由超时决定）；监控/提醒归 P3 |
| 通知 | 认证完成、逾期判失败均未接通知渠道（飞书/站内信）；P3 |
| 补训/整改 | 认证后的 `remediating` 与补训批次归 P3 |
| 陪练逾期查询 | 以分配截止驱动（`idx_ta_deadline_open`），再按 `training_attempt(assignment_id)` 关联（`idx_tat_assignment`）；单轮处理量受 `batch-size` 限制 |
