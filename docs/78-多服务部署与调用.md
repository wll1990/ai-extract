# 多服务独立部署与调用设计

> 状态：v1.0（2026-11-18）
> 范围：5 个服务的部署拓扑、服务发现、负载均衡、域名与网关配置、容器化与 K8s 示例、拆分顺序
> 非目标：多集群容灾、服务网格、灰度发布平台
> 现有文档关系：[DEPLOY.md](../DEPLOY.md) 是**当前生产单机**的执行手册（本地打包 → scp → 远端脚本重启）；[docs/上线部署手册.md](上线部署手册.md) 第九章是早期分布式草案，部分内容（如 `allowedOriginPattern("*")`）已过时。本文以代码事实为准，冲突处以本文为准。

## 0. 结论先行

1. **现在不要上注册中心**（Eureka/Nacos/Consul）。5 个服务、调用图接近一条直线，DNS + 反向代理足够；引入注册中心只会多一个必须高可用的组件。
2. **域名用同域反代，不要拆独立 API 域**。B 端会话走 `HttpOnly Cookie` + `SameSite=Strict`（`AuthController.java:228`），前端 `fetch` 用 `credentials: 'same-origin'`（`frontend/src/lib/api/client.ts:88`）。拆到 `api.` 域后 Cookie 根本不发，`credentials: 'same-origin'` 也不带凭证，等于把整条 B 端认证推翻。
3. **负载均衡只在入口层做**（Nginx / K8s Service / 云 LB），业务代码里不写客户端轮询。backend 无状态，**不需要 sticky session**。
4. **backend 扩到 2 个实例之前，必须先解决定时任务互斥**（当前没有 ShedLock，`@Scheduled` 在每个实例都会跑），见 §12。
5. **ai-service 的 `/internal/parse-file` 目前没有任何鉴权**，只能靠网络隔离；跨机器部署前必须补，见 §12。

## 3. 调用矩阵

| # | 调用方 → 被调方 | 路径 | 协议 | 地址来源 | 鉴权 | 超时/重试 |
|---|---|---|---|---|---|---|
| 1 | 浏览器 → frontend/platform | `/` | HTTPS | 域名 | — | — |
| 2 | 浏览器 → backend | `/api/v1/**` | HTTPS + SSE | 同域，Nginx 反代 | 会话 token（Cookie / Bearer / SSE query） | SSE：`proxy_read_timeout ≥ 300s` |
| 3 | frontend/platform SSR → backend | `/api/v1/**` | HTTP（内网） | `NEXT_PUBLIC_API_BASE_URL` | 同 #2 | 同上 |
| 4 | backend → ai-service | `/internal/parse-file` | HTTP（内网） | `AI_SERVICE_URL` | **暂无**（见 §12-1） | 解析大文件耗时分钟级，读超时 ≥ 120s |
| 5 | backend → im-bridge | `/internal/push`、`/register`、`/connect`、`/disconnect` | HTTP（内网） | `IM_BRIDGE_URL` | HMAC | 短超时，失败只影响消息推送 |
| 6 | im-bridge → backend | `/api/v1/internal/im/**` | HTTP（内网） | `BACKEND_URL` | HMAC | 失败重试由桥控制 |
| 7 | 飞书/企微/钉钉 → im-bridge | `/feishu/*`、`/wecom/callback`、钉钉 Stream | 公网 HTTPS / 长连接 | 渠道后台配置 | 渠道验签 + 我方 HMAC | 平台重试 |
| 8 | 合作方后端 → backend | `/api/v1/internal/partner/**` | 公网 HTTPS | 域名 | HMAC + nonce | 幂等重试 |
| 9 | 合作方 H5 → backend | `/api/v1/c/auth/partner/exchange` | 公网 HTTPS | 域名 | 一次性 code | 不重试，重新签发 code |
| 10 | backend → PG / Redis / DeepSeek / DashScope / OSS | — | 出站 | 环境变量 | 各自凭证 | 见 `application.yml` |

**需要发现与负载均衡的只有 #2（入口）和 #4（backend → ai-service）**，其余是固定内网地址。

## 4. 部署拓扑

### 4.1 单机（当前生产）

```
一台机器（/opt/mindforge）
├─ Nginx :443（域名分流）
├─ backend   :8080
├─ frontend  :3000
├─ platform  :3001
├─ ai-service:8000（仅 127.0.0.1）
├─ im-bridge :3010（公网 webhook）
└─ PG :5432 / Redis :6379
```

### 4.2 多机（目标态）

```
                  公网
        ┌──────────┼──────────────┐
   admin.example.com  platform.example.com  im.example.com
        │                │                  │
   ┌────▼─────┐     ┌────▼─────┐      ┌─────▼──────┐
   │frontend×N│     │platform×N│      │ im-bridge×1│
   │ :3000    │     │ :3001    │      │  :3010     │
   └────┬─────┘     └────┬─────┘      └─────┬──────┘
        │ /api/v1        │ /api/v1          │ HMAC
        └────────┬───────┴──────────────────┘
                 ▼
          ┌─────────────┐        ┌─────────────────┐
          │ Nginx / LB  │───────▶│ backend ×2 :8080│
          └──────┬──────┘        └───┬─────────┬───┘
                 │ /internal/parse-file│         │
                 ▼                    ▼         ▼
          ┌─────────────┐       PostgreSQL   Redis
          │ai-service×N │        (托管)      (托管)
          │ :8000(内网) │
          └─────────────┘
```

拆分依据：

- backend：会话在 Redis + `auth_session`，文件在 OSS，可直接水平扩；**唯一阻碍是定时任务**。
- frontend/platform：`output: 'standalone'`，无共享缓存依赖，可扩。
- ai-service：解析无状态，可扩。
- im-bridge：飞书 WebSocket、钉钉 Stream 是长连接，**多实例会重复收消息**；企微是回调，`ImInboundService` 有 Redis 去重可多实例。长连接渠道先保持单实例，后续按租户/机器人分片。

## 5. 服务发现

| 运行方式 | 发现机制 | 配置示例 |
|---|---|---|
| docker compose | compose 网络内服务名即 DNS | `AI_SERVICE_URL=http://ai-service:8000`、`BACKEND_URL=http://backend:8080/api/v1`、`IM_BRIDGE_URL=http://im-bridge:3010` |
| Kubernetes | `Service` + CoreDNS；公网走 `Ingress` | `http://ai-service.mindforge.svc.cluster.local:8000` |
| 虚拟机/物理机 | 云内网私有 DNS（或 `dnsmasq`） | `ai-svc.internal:8000`、`pg.internal:5432`、`redis.internal:6379` |

**约定**：所有服务地址只能来自环境变量，禁止写死 IP/主机名。当前代码已满足（`AI_SERVICE_URL`、`IM_BRIDGE_URL`、`BACKEND_URL`、`NEXT_PUBLIC_API_BASE_URL` 全部可配）。

**升级到注册中心的触发条件**（满足任意两条再考虑）：

- 服务数 > 10，或同一服务多语言多团队各自发布；
- 需要按权重灰度、动态摘除、跨集群寻址；
- 调用关系从树形变成网状，手工维护 upstream 成本高于运维注册中心。

## 6. 负载均衡与 SSE

### 6.1 Nginx upstream

```nginx
upstream backend_pool {
    least_conn;                                  # SSE 长连接多，least_conn 比轮询均衡
    server 10.0.2.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.2.12:8080 max_fails=3 fail_timeout=10s;
    keepalive 64;
}

upstream ai_pool {
    least_conn;
    server 10.0.3.11:8000 max_fails=2 fail_timeout=15s;
    server 10.0.3.12:8000 max_fails=2 fail_timeout=15s;
    keepalive 16;
}
```

### 6.2 三条原则

1. **不要 sticky session**。会话是 Redis + DB 的不透明 token，任何实例都能校验；加 `ip_hash` 只会把扩容做废。
2. **不要在 Spring 客户端里做轮询**。`FileParseService` 只认一个 `ai.service.url`，指向内网 VIP / Nginx / K8s Service，让 LB 去选实例；客户端轮询会把健康检查、摘除、重试全部重新实现一遍。
3. **重试只给幂等请求**。`POST /skills/{id}/chat` 是流式计费接口，禁止 `proxy_next_upstream` 重放；文件解析有 `material` 乐观锁 + skill 级 Redis 锁，重复投递安全。Nginx 只对 `GET` 或"连接建立失败"重试：

```nginx
proxy_next_upstream error timeout;
proxy_next_upstream_tries 2;
```

### 6.3 SSE 必须配的参数

漏掉 `proxy_buffering off` 的典型症状：回答不流式，最后一次性吐出来。

```nginx
location /api/v1/ {
    proxy_pass http://backend_pool;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;          # 后端 chat.timeout=180s，留余量
    proxy_send_timeout 300s;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 100m;
}
```

### 6.4 健康检查

| 服务 | 探针路径 | 说明 |
|---|---|---|
| backend | `GET /api/v1/public/stats` | 公开只读，现有脚本已用它 |
| ai-service | `GET /internal/health` | 自带 |
| im-bridge | `GET /health` | 返回渠道与 bot 数量，可判断是否真的连上 |
| frontend/platform | `GET /` | 200 即可 |

K8s 用 `readinessProbe` 摘流量、`livenessProbe` 重启；后端 `initialDelaySeconds: 120`，`failureThreshold: 6`。

## 7. 域名与 Nginx

### 7.1 域名规划

| 域名 | 指向 | 说明 |
|---|---|---|
| `admin.example.com` | frontend:3000；`/api/v1` → backend | B 端管理后台 |
| `platform.example.com` | platform:3001；`/api/v1` → backend | C 端 MindForge |
| `h5.example.com`（或 platform 子路径） | frontend/platform 的 H5 路由 | 合作方 iframe/WebView 嵌入；`Referrer-Policy: no-referrer` |
| `im.example.com` | im-bridge:3010 | 只暴露渠道回调与 `/health` |
| `ai-svc.internal` | ai-service:8000 | **不配公网 DNS、不开放公网端口** |
| `pg.internal` / `redis.internal` | PG / Redis | 安全组只放 backend |

### 7.2 为什么必须同域

- `token` Cookie 是 `HttpOnly; SameSite=Strict`（`AuthController.java:222-229`）。跨站请求浏览器不会带它。
- 前端请求固定 `credentials: 'same-origin'`（`client.ts:88`），指向 `api.` 域时**连 Cookie 都不会发**。
- 同域还省掉 CORS 预检、第三方 Cookie 被 Safari ITP 拦截、`Referer` 泄露 token 等问题。

如果坚持 `api.example.com`，要同时改三处：前端 `credentials: 'include'` + `NEXT_PUBLIC_API_BASE_URL` 绝对地址 + 后端 CORS 白名单；Cookie 还要 `SameSite=None; Secure`。**不推荐**，收益只有"API 域名漂亮"。

### 7.3 完整 Nginx 配置

```nginx
# ---------- 公共 ----------
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers HIGH:!aNULL:!MD5;
ssl_session_cache shared:SSL:10m;

server {
    listen 80;
    server_name admin.example.com platform.example.com im.example.com;
    return 301 https://$host$request_uri;
}

# ---------- B 端管理后台 ----------
server {
    listen 443 ssl http2;
    server_name admin.example.com;

    ssl_certificate     /etc/letsencrypt/live/admin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.example.com/privkey.pem;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # API：必须在进入 Next 之前截获
    location /api/v1/ {
        proxy_pass http://backend_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 100m;
    }

    location /files/ {
        proxy_pass http://backend_pool/files/;
        proxy_set_header Host $host;
        client_max_body_size 100m;
    }

    # Next 静态资源
    location /_next/static/ {
        proxy_pass http://frontend_pool;
        proxy_cache_valid 200 30d;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location / {
        proxy_pass http://frontend_pool;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# ---------- C 端平台 ----------
server {
    listen 443 ssl http2;
    server_name platform.example.com;

    ssl_certificate     /etc/letsencrypt/live/platform.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/platform.example.com/privkey.pem;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location /api/v1/ {
        proxy_pass http://backend_pool;
        # 参数同 admin，SSE 必需
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 100m;
    }

    location / {
        proxy_pass http://platform_pool;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# ---------- IM 桥：只放回调 ----------
server {
    listen 443 ssl http2;
    server_name im.example.com;

    ssl_certificate     /etc/letsencrypt/live/im.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/im.example.com/privkey.pem;

    location = /health          { proxy_pass http://im_bridge; }
    location /feishu/           { proxy_pass http://im_bridge; }
    location /wecom/            { proxy_pass http://im_bridge; }
    location /dingtalk/         { proxy_pass http://im_bridge; }

    location / { return 404; }
}
```

`upstream frontend_pool / platform_pool / im_bridge` 按实例数补齐，写法同 `backend_pool`。

### 7.4 公网不能出现的路径

| 路径 | 处理 | 原因 |
|---|---|---|
| `/api/v1/internal/im/**` | 只允许 im-bridge 所在网段 / 内网 | `permitAll` + HMAC，但不该暴露攻击面 |
| `/api/v1/im/*/callback` | 同上（除非 im-bridge 与后端同域反代） | 渠道回调应由 im-bridge 接 |
| `/api/v1/internal/partner/**` | **必须公网可访问**（合作方服务端） | 已 HMAC + nonce + 限流 |
| `/api/v1/actuator/**` | 仅内网 | 只放 `/actuator/health` |

用 Nginx 按来源网段限制：

```nginx
location /api/v1/internal/im/ {
    allow 10.0.0.0/8;
    deny all;
    proxy_pass http://backend_pool;
}
```

### 7.5 H5 嵌入的 CSP（现状会挡住 iframe）

两个 Next 应用当前对所有路由下发：

```
Content-Security-Policy: ...; frame-ancestors 'none'
X-Frame-Options: DENY
```

合作方 iframe 会被浏览器直接拒绝。两条路：

- **代码方案（推荐，长期）**：按路由下发，`/h5/**` 用 `frame-ancestors <PartnerApp 白名单>`，其余保持 `'none'`；
- **边缘方案（过渡）**：Nginx 对 H5 路径先 `proxy_hide_header` 再 `add_header`：

```nginx
location /h5/ {
    proxy_pass http://platform_pool;
    proxy_hide_header X-Frame-Options;
    proxy_hide_header Content-Security-Policy;
    add_header Content-Security-Policy "frame-ancestors https://partner-a.com https://partner-b.com" always;
    proxy_set_header Referrer-Policy "no-referrer";
}
```

### im-bridge

| 变量 | 必填 | 说明 |
|---|---|---|
| `BACKEND_URL` | 是 | 例：`http://backend:8080/api/v1` |
| `IM_BRIDGE_TOKEN` | 是 | 与 backend 的 `IM_BRIDGE_TOKEN` 一致；默认值 `dev-im-bridge-token` 禁止上生产 |
| `PORT` | 否 | 默认 3010 |
| `BRIDGE_ID` | 否 | 多实例时区分实例 |

### frontend / platform

| 变量 | 构建期 | 说明 |
|---|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | **是** | `NEXT_PUBLIC_*` 在 `next build` 时内联；同域保持 `/api/v1`，改域名必须重新构建 |

## 11. 拆分顺序与验收

每一步都可独立回滚，前一步不稳不进下一步。

### 第 1 步：ai-service 独立

- 改动：新机器/新容器跑 `uvicorn`，backend 的 `AI_SERVICE_URL` 指向内网地址。
- 验收：
  - 上传 txt/docx/pdf 各一份，解析、萃取、报告全链路正常；
  - 从公网 `curl http://<公网IP>:8000/internal/health` **不通**；
  - 断开 ai-service，上传接口返回明确错误，对话不受影响（`FileParseService` 失败重试/报错不阻塞其他链路）。

### 第 2 步：im-bridge 独立

- 改动：`BACKEND_URL` 指向 backend 内网地址；公网域名只映射 im-bridge。
- 验收：
  - 飞书、企微、钉钉各发一条消息，能进后端并回复；
  - 同一条消息重复投递只入库一次（`ImInboundService` Redis 去重）；
  - `curl https://im.example.com/api/v1/public/stats` 返回 404。

### 第 3 步：frontend / platform 独立域名

- 改动：Nginx 按 §7.3 配置；`NEXT_PUBLIC_API_BASE_URL` 保持 `/api/v1`（同域）。
- 验收：
  - 登录 → 刷新页面保持登录（Cookie 生效）；
  - 五种对话（QA/Talk/Practice/Enterprise/Organization）SSE 逐字输出；
  - 文件上传下载正常（`client_max_body_size`）；
  - 检查 `/api/v1` 请求没有打到 Next（`next start` 日志无 `/api/v1` 记录）。

### 第 4 步：backend 双实例

- 前置：完成 §12-2（调度互斥）。
- 改动：Nginx `backend_pool` 加第二个节点；DB/Redis 连接数按 `实例数 × Hikari 池` 重算。
- 验收：
  - 滚动重启期间 SSE 不中断（连接排空）；
  - 连续登录同一账号 10 次，设备数仍 ≤ 5（会话在 Redis，任一实例可校验）；
  - 观察 24h：定时任务每个只执行一次；两实例错误率无差异。

## 13. 观测、备份与回滚

### 13.1 观测

- 访问日志：Nginx 记录 `$host $request_uri $status $request_time $upstream_response_time`，带上前端传的 `X-Trace-Id`；
- backend：`logs/backend.log` + `X-Trace-Id` 串联；关键指标 `/api/v1/public/stats`；
- im-bridge：`/health` 看各渠道 `bots` 数量，掉线立即发现；
- ai-service：解析耗时、失败率按文件类型统计。

### 13.2 备份

- PG：每日 `pg_dump` + WAL 归档（PITR）；
- Redis：会话可回源 DB，不是强依赖；`noeviction`，监控 `evicted_keys`；
- 配置：`config/*.env` + `secrets.env` 不入库，单独加密保存。

### 13.3 回滚

| 层级 | 动作 | 数据影响 |
|---|---|---|
| frontend/platform | 回滚镜像 tag | 无 |
| backend | 回滚 jar/镜像；Flyway 不回退，保持向前兼容 | 新迁移已在库中，需确认旧版本兼容 |
| ai-service / im-bridge | 回滚镜像 | 无 |
| 域名切换 | 改 Nginx upstream，保留旧节点 10 分钟再下线 | 无 |

> backend 回滚的前提是**迁移向前兼容**：只增列/加表，不删列、不改语义。当前 V107 满足。
