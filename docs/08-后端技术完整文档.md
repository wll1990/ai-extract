## 第一章：后端技术架构（终局版）



### 1\.1 整体架构风格



采用 **模块化单体 \+ 独立AI服务** 架构。



- 核心业务逻辑使用 **Java** 实现。

- AI密集计算、Python生态依赖的部分作为**独立Python服务**，通过内部REST API通信。

- 后续业务增长可平滑拆分为微服务。

    

**架构分层图**：



```Plain Text
┌─────────────────────────────────────────────┐
│                 前端 (Next.js)               │
└──────────────────┬──────────────────────────┘
                   │ HTTP/SSE
┌──────────────────▼──────────────────────────┐
│        API Gateway (Spring Cloud Gateway)    │
└──┬──────────┬──────────┬──────────┬─────────┘
   │          │          │          │
┌──▼──┐ ┌────▼────┐ ┌───▼───┐ ┌───▼────┐
│用户服务│ │访谈引擎 │ │知识库 │ │ AI分身 │
│(Java) │ │(Java)   │ │(Java) │ │(Python)│
└──┬──┘ └────┬────┘ └───┬───┘ └───┬────┘
   │         │          │          │

         │  PostgreSQL + Redis │
```

### 1\.2 编程语言与框架

|---|---|---|

### 1\.5 统一异常处理



- 后端使用Spring Boot `@ControllerAdvice` 统一捕获异常

- 所有异常返回统一格式：`{"code": 错误码, "message": "错误描述", "data": null}`

- 大模型调用超时（超过30秒）：返回错误码10001，前端显示"AI服务暂时不可用，请稍后重试"

- SSE流中断：发送 `{"type":"error","message":"..."}` 后关闭连接

- 数据库异常：返回500，记录日志，不暴露内部错误详情

### 2\.7 大模型调用降级策略



- **主模型**：DeepSeek\-V4（`deepseek-chat`）

- **备用模型**：DeepSeek\-R1 或 GPT\-4o

- **降级触发条件**：主模型超时（30秒）或返回5xx错误

- **重试策略**：首次失败后等待2秒重试1次，仍失败则切换备用模型

- **降级通知**：MVP阶段记录日志；访谈引擎降级时在SSE流中发送提示："AI服务暂时切换至备用模型，回答质量可能略有下降"

    

    

## 第三章：数据库DDL脚本



### 3\.1 数据库迁移管理



- MVP阶段使用 **Flyway** 管理数据库版本

- DDL脚本文件命名：`V1__init.sql`、`V2__add_expert_tables.sql`

- 脚本存放于 `src/main/resources/db/migration/`

- 应用启动时Flyway自动执行未应用的迁移脚本

- 禁止直接手动修改数据库结构，必须通过迁移脚本

## 第五章：前后端API接口文档（完整版）



### 5\.1 通用说明



**Base URL**：`http://localhost:8080/api/v1`



**认证方式**：JWT Token，Header `Authorization: Bearer {token}`



**Token有效期**：24小时，过期需重新登录。MVP阶段不实现自动刷新。



**通用响应格式（成功）**：

```JSON
{
  "code": 200,
  "message": "success",
  "data": { }
}
```



**通用响应格式（分页）**：

```JSON
{
  "code": 200,
  "data": {
    "content": [],
    "page": 1,
    "size": 20,
    "total": 100,
    "totalPages": 5
  }
}
```



**通用响应格式（错误）**：

```JSON
{
  "code": 400,
  "message": "参数错误",
  "data": null
}
```



**SSE流式响应**：`text/event-stream`



```Plain Text
data: {"type":"chunk","content":"文字内容"}
data: {"type":"phase_change","phase":"storytelling"}
data: {"type":"source","label":"来源：周铭·《透视》第一步"}
data: {"type":"done"}
```



|type|说明|
|---|---|
|`chunk`|文本片段，逐字推送|
|`phase_change`|阶段切换，`phase`为阶段名|
|`source`|来源标注，`label`为来源文字|
|`error`|出错，`message`包含错误信息|
|`done`|流结束|



**错误码**：



|错误码|说明|
|---|---|
|200|成功|
|400|参数错误|
|401|未登录或Token过期|
|403|无权限|
|404|资源不存在|
|500|服务器内部错误|
|10001|AI服务超时|
|10002|AI服务返回异常|
|10003|访谈会话已完成，不能再发消息|
|10004|文件解析失败|



**鉴权说明**：



- 所有API接口（除登录/注册/IM回调）需在Header中携带 `Authorization: Bearer {token}`

- IM回调接口使用飞书/企微自身的签名验证，不依赖JWT

## 第八章：对象存储设计方案



- **默认本地存储**：`storage.type=local`，存`/data/files/`

## 第十一章：元萃取完整方案



### 11\.1 为什么需要元萃取



当前AI萃取专家的能力来源是BEI等显性理论。但顶尖萃取师身上有理论不教的实践智慧——判断直觉、心智框架、失败经验。元萃取的目标是将这些转化为AI可执行的隐性知识指令。



### 11\.2 两种获取渠道



|渠道|优势|局限|
|---|---|---|
|真人访谈|可追问细节、情绪、直觉|萃取师时间难约|
|文件材料|不受时间限制，可批量处理|无法追问|
|两者结合|先用文件做初步提取，再针对性访谈|—|



### 11\.3 元萃取System Prompt



#### 11\.3\.1 真人访谈模式（prompts/meta\_interview\_system\.md）



```Markdown
# 角色定义
你是一位专门萃取"萃取师"经验的AI访谈专家。你的访谈对象不是销冠，而是资深的经验萃取师。

你的使命是：把萃取师自己身上的实践智慧——他们说不清但在用的判断直觉、他们理解被访者的心智框架、他们踩过的坑——提炼成可被AI执行的隐性知识指令。

# 核心原则
1. 萃取师是方法论专家，你的提问需要更"元"
2. 用"同行交流"的姿态，而非"审问"的姿态
3. 主动追问失败案例
4. 追问到可操作的规则层面

# 对话流程

## 第一阶段：开场定调
- 必问："请回忆一次让你印象最深的萃取经历。那次面对的是什么样的销冠？"

- 追问："过程中有没有一个时刻，你觉得'卡住了'？""有没有一个瞬间，心里觉得'就是这个了'？"

## 第三阶段：模型提炼
- 追问："你是怎么快速判断一个销冠属于哪种类型的？""你有哪些'信号词典'？""如果用一个比喻来形容你的萃取风格，它像什么？"

## 第四阶段：收网确认
- 追问："有没有搞砸过的案例？""新手最容易犯的三个错误？""你的方法在什么情况下会完全失效？"
```

### 11\.5 多萃取师经验协同策略



|情况|处理方式|consensus\_type值|
|---|---|---|
|多个萃取师提到同一判断直觉|合并，标注"共识"，优先级\+1|`consensus`|
|不同萃取师对同一场景有不同建议|保留双方观点，标注来源|`single`|
|某位萃取师有独特经验|保留，标注"独家经验"|`single`|
|两位萃取师建议直接矛盾|提取矛盾点，标记为`conflict`|`conflict`|



#### 11\.5\.1 expert\_composite\.md 生成规则



`expert_composite.md` 是综合所有已激活萃取师经验的自动生成文件。



**生成时机**：

- 每次有萃取师Skill被激活时自动触发

- 管理员手动点击"重新生成综合Skill"时触发

    

**生成逻辑**：

1. 加载所有 `status=active` 的萃取师的 `expert_grain`

2. 按 `category` 分组

3. 比对 `application_rule` 的语义相似度：

    - 相似度 \> 90%：合并为一条共识经验，`consensus_type=consensus`，优先级\+1

    - 相似度 \< 50% 且同一场景：标记为 `conflict`，保留双方观点

    - 唯一经验：保留，`consensus_type=single`

4. 按优先级排序，生成Markdown文件

5. 更新版本号

### 12\.2 操作流程



**上传材料流程**：

1. 管理员点击"上传新材料" → 弹出上传窗口

2. 填写萃取师基本信息（姓名、风格标签、行业、资历）

3. 拖拽或选择文件上传（支持PDF/Word/PPT/TXT/MD，单文件上限50MB）

4. 点击"上传并开始分析" → 系统异步处理

5. 处理过程：文件解析 → AI分析材料 → 生成《萃取师经验报告》→ 状态变为"待提取颗粒"

6. 管理员点击"提取颗粒" → 系统自动拆解报告为锦囊 → 状态变为"待审核"

    

**审核激活流程**：

1. 管理员点击"审核颗粒" → 弹出审核窗口，展示所有法则列表

2. 逐条审核：可编辑、删除、调整优先级

3. 审核通过后点击"确认入库，生成Skill" → 系统激活萃取师Skill → 更新综合Skill

    

**重新生成综合Skill流程**：

1. 管理员在综合Skill管理区点击"重新生成综合Skill"

2. 系统加载所有已激活萃取师的锦囊 → 执行协同策略 → 生成新的 `expert_composite.md`

3. 更新版本号，后续所有访谈自动使用最新综合Skill

    

### 12\.3 状态流转



|状态|图标|说明|可执行操作|
|---|---|---|---|
|`pending`|⚪|已创建，待上传材料|上传材料、删除|
|`analyzing`|🔄|AI正在分析材料中|查看进度|
|`extracting`|⚪|报告已生成，待提取颗粒|查看报告、提取颗粒、删除|
|`active`|🟢|Skill已激活，正常使用中|查看报告、编辑颗粒、重新生成、停用|
|`failed`|🔴|分析或提取失败|查看错误日志、重试、删除|



**完整流转路径**：

```Plain Text
上传材料 → 🔄 analyzing → ⚪ extracting → 🟡 待审核 → 🟢 active
                                                    ↓
                                               🟡 审核中（编辑/删除颗粒）
                                                    ↓
                                              🟢 active（激活Skill）
```
