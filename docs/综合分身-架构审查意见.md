# 综合分身方案 — 架构审查意见

> 2026-07-28 · 对照方案文档逐条审查 · 4 个架构风险 + 5 个优化建议

---

## 总体结论

**方案方向正确，但有一个架构阻塞点和三个设计缺陷需要先解决才能进入开发。**

---

## 🔴 架构阻塞点

### B1. `Skill.spaceId = NOT NULL` 约束与综合分身无 space 矛盾

**代码事实**：`Skill.java:47` — `@Column(name = "space_id", nullable = false)`

方案说"综合分身也是一条 Skill 记录……无自己的 spaceId"。这在 JPA 层面直接报错——`spaceId` 不能为 NULL。DB 层 V1 DDL 同样是 `skill_id UUID NOT NULL`。

**两种解法：**

| 方案 | 做法 | 风险 |
|------|------|------|
| A. 创建占位 Space | 每个综合分身建一个空 Space | Space 表被污染，`findByUserId` 等查询需要排除这些占位记录 |
| B. 独立实体 | 新建 `OrganizationSkill` 表，不继承 Skill | 前端需要两套渲染逻辑，但数据模型干净 |

**建议**：选 **B**。`OrganizationSkill` 是一个轻量表（name, match_rule, avatar_url, company_id），不共享 Skill 的生命周期和约束。12-15 个文件的估算是按 A 方案算的，B 方案会多 2-3 个文件（新实体 + Repository + DTO），但避免了未来 3 年持续为"占位 Space"打补丁。

## 🟡 设计缺陷

### D1. `department` 自由文本做匹配键不可靠

方案用 `match_rule: {"department": "华东销售部"}` 做动态匹配。但 `Skill.department` 是发布时手动填的自由文本——"华东部"、"华东销售"、"华东Sales" 指向同一个部门但没有唯一标识。

**后果**：综合分身成员不全（拼写差异漏人）、或混入不该有的人（同名部门）。

**建议**：MVP 阶段退一步——不用 `match_rule` 动态匹配，改为创建综合分身时**手动勾选成员**，存入 `member_skill_ids JSONB`。这样简单、确定、零歧义。动态匹配是 Phase 2 的事情。

### D2. `enterprise_system.md` prompt 角色定位不对

方案说"复用现有 enterprise_system.md prompt"。但那个 prompt 的第一句是：

> 你是企业{domain.name}智慧的调度员

综合分身的角色应该是"华东销售部的知识库"，不是"全企业的调度员"。抄过来会让 AI 听起来像是在代表整个公司回答，而非某个部门。

**建议**：新建 `org_skill.md` prompt，角色定位为"你是{org_name}的团队知识库"，对话风格与 enterprise_system.md 保持一致（多来源并列、诚实说不知道）。10 行以内。

### D3. 统计聚合缺少去重逻辑

方案说 `userCount = 成员 userCount 之和（近似，可能重复）`。但这不仅仅是"近似"——同一个用户问了华东销售部的张经理和李总监各一次，综合分身的 `userCount` 就会把他算两次。

**建议**：综合分身的 `userCount` 应该从 `conversation_stats` 按 `(org_skill_id, user_id)` 去重计算，不能简单 SUM 成员的数字。或者干脆综合分身不展示 `userCount`，只展示 `conversationCount` 和 `satisfactionRate`——前者是客观的 SUM，后者用加权平均是合理的。

## 🟢 优化建议

### O1. 统一三条检索管道

当前有三条不同的检索路径：

| 管道 | 方法 | 质量 |
|------|------|------|
| 个人分身 | pgvector HNSW | 高 |
| 企业调度 | 关键词匹配 500→20 | 低 |
| 综合分身（计划） | pgvector 多 space | 高 |

综合分身上线后，企业调度的关键词方案就显得更差了。**建议**：把综合分身的 `GrainRetriever` 多 space 版本同时用于改造 `enterpriseChat`，让三条管道全部走 pgvector。关键词匹配代码（`GrainRecommendationService.relevanceScore()`）可以保留作为 fallback。

### O2. 综合分身聊天应走同一端点

不要新建 `/skills/organization/chat` 端点。让综合分身的 `orgSkillId` 作为普通 `skillId` 传入 `POST /skills/{id}/chat`。在 `ChatStreamService.chat()` 中判断 `skill.orgType`：

```
if (skill.orgType == 'organization') → 多 space 检索 → org_skill.md prompt
else → 单 space 检索 → 现有 prompt
```

好处：前端零改动（综合分身详情页就是 SkillChatView），鉴权复用现有规则，模式切换（QA/Talk/Practice）全部继承。

### O3. `match_rule` 的 JSONB 结构应预留扩展

即使 MVP 用 `member_skill_ids`，`match_rule` 的 schema 也值得现在定：

```json
{
  "type": "manual",           // "manual" | "department" | "tags" | "role"
  "member_skill_ids": [...],  // MVP 用这个
  "department": null,         // Phase 2 动态匹配
  "tags": null                // Phase 2 标签匹配
}
```

`type` 字段让代码可以 `switch` 分支处理不同匹配策略，未来扩展时不破坏现有数据。

### O4. 综合分身的 Talk 模式需要特殊处理

当前 Talk 模式是"像老同事一样自然对话"，prompt 是第一人称。综合分身的 Talk 不能第一人称（不存在"张经理+李总监"这个人）。建议 MVP 不做 Talk，只有 QA。Practice 同理——谁是客户？建议 MVP 也不做。

**MVP 范围确认**：综合分身仅 QA 模式，Talk/Practice 按钮置灰 + tooltip "组织分身暂不支持此模式"。

### O5. 性能验证点

在开发前建议做一个快速验证：

```sql
-- 模拟 5 个 space 的跨空间向量检索
EXPLAIN ANALYZE
SELECT g.*, 1.0 - (g.embedding <=> '...'::vector) AS similarity
FROM experience_grain g
WHERE g.space_id IN (SELECT unnest(ARRAY['uuid1','uuid2','uuid3','uuid4','uuid5']::uuid[]))
  AND g.status = 'active' AND g.embedding IS NOT NULL
ORDER BY g.embedding <=> '...'::vector
LIMIT 5;
```

确认 HNSW 索引在 `WHERE space_id IN (...)` 条件下的执行计划——是否走了 Index Scan + filter，还是退化成了 Seq Scan。如果退化，需要给 `(space_id, status)` 加一个 `WHERE embedding IS NOT NULL` 的部分索引。

## 修订后的改动量

| 层 | 改动 | 相比原方案 |
|------|------|-----------|
| DB | `organization_skill` 表 + `skill.org_type` | 多了独立表 |
| 实体 | `OrganizationSkill.java` | 新增 |
| 检索 | `GrainRetriever` 多 space 版 | 不变 |
| 管道 | `ChatStreamService.chat()` 分支判断 orgType | 不变 |
| 端点 | 复用 `POST /skills/{id}/chat` | 省了新端点 |
| Prompt | 新建 `org_skill.md`（10行） | 新增 |
| 统计 | 改 `SkillStatsScheduler` 去重 userCount | 小改动 |
| 前端 | 复用 SkillChatView | 不变 |

**修订后总估：约 2.5 周，15-18 个文件。**

---

## 审查结论

**可以做，但先修三个问题再开工：**

1. 🔴 `OrganizationSkill` 独立实体替代 `Skill + 占位 Space`
2. 🟡 MVP 用手动勾选成员 (`member_skill_ids`) 替代 `match_rule` 动态匹配
3. 🟡 新建 `org_skill.md` prompt，不直接复用 `enterprise_system.md`

这三个修完后，剩下的实现路径清晰，代码量可控。
