用户角色与认证架构全梳理
1. 两张用户表
B 端 user	C 端 app_user
实体	User.java	AppUser.java
所属	必须绑定 company_id	无企业归属（partner 来源除外）
角色	role 字段写死：super_admin / company_admin / employee	无 role 字段，角色在签发 JWT 时动态决定
状态	isActive 布尔	status 枚举：guest / registered
2. JWT 如何区分 —— 靠 claim 隐式区分
没有显式的 userType 字段。 全凭两个信号：


B 端 JWT:  { userId, companyId: "uuid", role: "employee" }     ← 有 companyId
C 端 JWT:  { userId, role: "c_user" }                          ← 无 companyId
代码在 JwtUtil.java:93-95：


if (companyId != null) {
    claims.put("companyId", companyId.toString());
}
B 端签发时传 companyId → claim 里有。C 端传 null → claim 里没有。

区分逻辑通过 claim 组合推断：

companyId claim	role	用户类型
有值	super_admin / company_admin / employee	B 端 User 表
null	c_guest / c_user / c_partner	C 端 AppUser 表
3. 认证流程（同一入口，分支处理）
所有请求走同一个 Filter：JwtAuthFilter.java，分三个分支：


请求进入
  │
  ├─ 有标准 JWT（Bearer/Cookie/query）
  │   └─ jwtUtil.validateToken() → 解析 {userId, role, companyId}
  │      → RolePermissions.getPermissions(role) → 权限码列表
  │      → SecurityContext 设 authorities = [role, ...权限码]
  │      → TokenContext.set(userId, companyId)
  │
  ├─ 有合作方 JWT（?token= 且含 appId claim）
  │   └─ PartnerJwtFilter.authenticate()
  │      → 查 PartnerApp → 验签 → 找/建 AppUser
  │      → 设 role="c_partner", companyId=null
  │
  └─ 无 token → 匿名（public 端点自己放行）
4. 合作方在 B 端的实际工作方式
合作方不走 B 端 User 表，走的是 C 端 AppUser 表，角色是 c_partner：


合作方服务器生成 JWT {appId, userId, userName}
        │
        ▼ 用合作方自己的 secretKey 签名
        │
        ▼ 嵌入 URL: ?token=<partner_jwt>
        │
        ▼ JwtAuthFilter 识别 appId claim → PartnerJwtFilter
        │
        ▼ 查 PartnerApp 表 → 用合作方 SK 验签
        │
        ▼ 在 AppUser 表找/建用户: account="partner:{appId}:{externalId}"
        │   source="partner", companyId=<appId>
        │
        ▼ Spring Security 设 authorities=[c_partner, SKILL_USE]
        │
        ▼ SecurityConfig 检查:
        │   · /interviews/** ✅ (允许 c_partner)
        │   · /skills/**   ✅ (允许 SKILL_USE)
        │   · /admin/**    ❌ (需要 DASHBOARD_VIEW，c_partner 没有)
所以合作方用户不能访问管理后台。他们只有 SKILL_USE，能做的是：和分身对话、参与访谈。这就是 SecurityConfig.java:91 的设计：


.requestMatchers("/interviews/**").hasAnyAuthority("super_admin", "company_admin", "employee", "c_user", "c_partner")
// ↑ c_partner 可访问访谈，但 c_guest 不行
5. 权限校验全链路

① 登录 → AuthService 查 User/AppUser 表
         → 确定 role 字符串
         → JwtUtil.generateToken(userId, companyId, role)
                ↓
② 请求 → JwtAuthFilter 解析 JWT
         → RolePermissions.getPermissions(role) 查映射表
         → 设 SecurityContext authorities
         → TokenContext.set(userId, companyId)
                ↓
③ URL 匹配 → SecurityConfig 规则链（顺序匹配，先细后粗）
         → hasAuthority(权限码) / hasAnyAuthority(角色名...)
                ↓
④ Controller → TokenContext.getCompanyId() 拿企业 ID
         → CompanyScopeService 做企业内数据隔离
         → 或 validateSkillOwnership() 做属主校验
关键设计点：SecurityConfig 最后一条 catch-all（L115）：


.anyRequest().hasAnyAuthority("super_admin", "company_admin", "employee")
任何没显式声明规则的新接口，默认只允许 B 端三个角色。 C 端接口必须显式加 .requestMatchers()，否则直接 403。

6. 总结
问题	答案
B/C 端怎么区分？	JWT claim 隐式区分：有 companyId=B端，无=C端
两个表怎么统一认证？	同一个 JwtAuthFilter，不同入口各自查表，统一设 SecurityContext
合作方在 B 端怎么支持？	不走 B 端。合作方用户存在 AppUser 表，角色 c_partner，只能访问访谈和分身对话
角色权限在哪管？	RolePermissions.java — 角色→权限码映射，单一真相源
