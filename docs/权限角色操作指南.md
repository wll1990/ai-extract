# B 端平台权限角色操作指南

## 架构概述

```
RolePermissions.java（单一真相源：角色 → 权限码集合）
       │
       ├──→ JwtAuthFilter 读取，设为 Spring Security GrantedAuthority
       │       └──→ SecurityConfig.hasAuthority() 门禁校验
       │
       ├──→ AuthService.getCurrentUser() 读取，填入 /auth/me 响应
       │       └──→ 前端 NAV_ITEMS 可见性 + 路由守卫校验
       │
       └──→ 任意 Service/Controller 调 RolePermissions.hasPermission(role, code)
```

**三个派生点从同一份映射表读取，不会出现不一致。**

## 操作手册

### 操作一：新增角色

> 例：3 个月后需要加一个"部门主管 department_admin"，能看本部门分身数据（工作台、分身调优、对话历史、场景地图），但不能管理用户和素材。

**只改一个文件：** `RolePermissions.java`

```java
// 在 RolePermissions 类中加一行
DEPARTMENT_ADMIN, Set.of(
    DASHBOARD_VIEW,
    SKILL_TUNING,
    CONVERSATION_VIEW,
    SCENE_COVERAGE
)
```

**为什么其他文件不用改：**

| 层 | 要改吗 | 原因 |
|----|:------:|------|
| SecurityConfig | ❌ | 用的是 `hasAuthority("DASHBOARD_VIEW")`，权限码本身没变，只是新角色拥有了它 |
| JwtAuthFilter | ❌ | 启动时加载 RolePermissions 全表，自动将新角色映射为 GrantedAuthority |
| `/auth/me` 响应 | ❌ | 运行时查 RolePermissions，新角色自动返回对应权限码列表 |
| 前端 NAV_ITEMS | ❌ | 读 `user.permissions` 判断可见性，新角色登录后自动只显示有权限的导航 |
| Controller/Service | ❌ | `TokenContext.getCompanyId()` 统一做数据隔离，不依赖角色判断 |

**新角色用户创建方式：** 管理员在用户管理页面创建时选择角色 "department_admin"。注册码注册时也可指定角色（需确认注册码配置）。

**生效时机：** 用户下次登录时，JWT 中的 role 为 `department_admin`，`/auth/me` 响应自动返回该角色对应的权限列表。

### 操作二：给已有角色增加一个权限

> 例：PM 决定 company_admin 也要看到本企业的 Token 统计。

**只改一个文件：** `RolePermissions.java`

```java
// 在 company_admin 的 Set 中加一行
COMPANY_ADMIN, Set.of(
    DASHBOARD_VIEW, USER_MANAGE, SKILL_MANAGE, SKILL_TUNING,
    MATERIAL_MANAGE, CONVERSATION_VIEW, SCENE_COVERAGE,
    EXPERT_MANAGE, GRAIN_MANAGE, ORG_SKILL_MANAGE,
    TOKEN_VIEW_COMPANY  // ← 加这一行
)
```

**影响范围：**

| 层 | 效果 |
|----|------|
| SecurityConfig | 无需改动。`/admin/token-usage/**` 早已配置 `hasAuthority("TOKEN_VIEW_COMPANY")`，只是此前 company_admin 不拥有此权限码 |
| 前端导航栏 | 下次登录后 `/auth/me` 返回新权限，导航栏自动出现 "🪙 Token 统计" |
| 数据 | 后端 Controller 按 `TokenContext.getCompanyId()` 过滤，company_admin 只能看到本企业数据 |

**适用场景：** 放开某个功能给已有角色、产品策略调整。

---

### 操作三：从角色移除一个权限

> 例：PM 决定 company_admin 不再能看到对话历史（隐私合规要求）。

**只改一个文件：** `RolePermissions.java`

```java
COMPANY_ADMIN, Set.of(
    DASHBOARD_VIEW, USER_MANAGE, SKILL_MANAGE, SKILL_TUNING,
    MATERIAL_MANAGE,
    // CONVERSATION_VIEW,  ← 删掉或注释这一行
    SCENE_COVERAGE, EXPERT_MANAGE, GRAIN_MANAGE, ORG_SKILL_MANAGE,
    TOKEN_VIEW_COMPANY
)
```

**影响范围：**

| 层 | 效果 |
|----|------|
| SecurityConfig | 无需改动。`/admin/conversations/**` 仍然配置 `hasAuthority("CONVERSATION_VIEW")`，但 company_admin 下次登录后不再拥有此权限码 → 请求被 403 拒绝 |
| 前端 | 下次登录后 `user.permissions` 中不再包含 `CONVERSATION_VIEW`，导航栏自动隐藏 |
| 已有会话 | 不影响。只是无法新增访问，历史数据保留 |

---

### 操作四：新增一个权限码

> 例：后续产品加了"知识库管理"功能，需要一个新的权限码 `KNOWLEDGE_MANAGE`。

#### Step 1: `Permission.java` — 加常量

```java
public static final String KNOWLEDGE_MANAGE = "KNOWLEDGE_MANAGE";
```

#### Step 2: `RolePermissions.java` — 分给角色

```java
SUPER_ADMIN, Set.of(
    // ... 已有
    KNOWLEDGE_MANAGE  // ← 加给超管
),
COMPANY_ADMIN, Set.of(
    // ... 已有
    KNOWLEDGE_MANAGE  // ← 也加给企业管理员（如果需要）
)
```

#### Step 3: `SecurityConfig.java` — 加门禁

```java
.requestMatchers("/admin/knowledge/**").hasAuthority("KNOWLEDGE_MANAGE")
```

#### Step 4: 前端 `NAV_ITEMS` — 加导航项

```ts
{ icon: '📚', label: '知识库管理', path: '/admin/knowledge', permission: 'KNOWLEDGE_MANAGE' }
```

> 导航项配置 `permission` 键，由框架根据 `user.permissions` 自动控制可见性。

**总共改动 4 个文件，没有隐藏依赖。**

## 架构约束（写新功能时遵守）

1. **SecurityConfig 只写权限码，不写角色名。** `hasAuthority("USER_MANAGE")` ✅，`hasRole("SUPER_ADMIN")` ❌
2. **Controller 只做数据归属校验，不做角色判断。** `if (user.role.equals("company_admin"))` 这种代码不应该出现。取 companyId 统一用 `TokenContext.getCompanyId()`
3. **前端只读 `user.permissions`，不读 `user.role`。** 导航可见性、按钮显示都通过 `user.permissions.includes('XXX')` 判断
4. **新功能必须先定义权限码。** 写代码前先问：这个功能谁可以用？在 Permission.java 加码，在 RolePermissions.java 分配

## 数据流总览

```
① 用户登录
   ↓
② AuthService.login()
   → jwtUtil.generateToken(userId, companyId, role)
   → JWT claims: { userId, companyId, role }
   ↓
③ JwtAuthFilter 拦截请求
   → 解析 JWT 得到 role = "company_admin"
   → RolePermissions.getPermissions("company_admin")
   → 返回 [DASHBOARD_VIEW, USER_MANAGE, SKILL_MANAGE, ...]
   → 设为 SecurityContext: GrantedAuthority 列表
   → TokenContext.setCompanyId(companyId)
   ↓
④ SecurityConfig 校验
   → 请求路径 /admin/users
   → 匹配规则 .hasAuthority("USER_MANAGE")
   → SecurityContext 中有 "USER_MANAGE" ✅ → 放行
   ↓
⑤ Controller 处理
   → companyId = TokenContext.getCompanyId()
   → userRepository.findByCompanyId(companyId, pageable)
   → 只返回本企业数据
   ↓
⑥ /auth/me（前端页面加载时调用）
   → AuthService.getCurrentUser(userId)
   → UserInfoResponse.permissions = RolePermissions.getPermissions(user.role)
   → 前端存储 user.permissions = ["DASHBOARD_VIEW", "USER_MANAGE", ...]
   ↓
⑦ 前端 AppLayout
   → 路由守卫: user.permissions 中有任何 admin 权限码 → 允许进入 /admin
   → 导航栏: NAV_ITEMS.filter(item => user.permissions.includes(item.permission))
```

## 关键文件索引

| 文件 | 职责 |
|------|------|
| `Permission.java` | 权限码常量定义 |
| `RolePermissions.java` | 角色→权限码映射表，唯一真相源 |
| `SecurityConfig.java` | URL pattern → 权限码门禁 |
| `JwtAuthFilter.java` | 登录时加载权限码到 SecurityContext |
| `TokenContext.java` | ThreadLocal 存储 userId + companyId |
| `AuthService.java` | 登录时查 RolePermissions 填入 /auth/me |
| 前端 `permissions.ts` | 权限码常量（与后端同源） |
| 前端 `AppLayout.tsx` | 导航栏 + 路由守卫 |

> **核心原则：RolePermissions.java 是唯一的真相源。改它，全局生效。**
