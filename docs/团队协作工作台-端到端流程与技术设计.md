# 团队协作工作台：端到端流程与技术设计

> 当前方案讨论入口：[方案对比与选型](团队协作方案对比与选型.md)。本文是方案D“自建工作台”的详细设计储备；其中Pi候选、先Web后IM的安排不约束方案B/C，也不表示当前必须实施全部模块。

日期：2026-11-13。状态：根据当前代码核对后的设计讨论稿，未实现业务代码。

本文件补充[《团队协作工作台-功能与交互清单》](团队协作工作台-功能与交互清单.md)，收敛其V1.1首条实施链路。目标用户是异地三人团队；课程是第一个成果模板，底层仍是通用共享工作台。以下区分代码事实、设计建议和待实测项，不把接入某个模型等同于具备完整Agent产品能力。

## 1. 当前范围与完整业务故事

先实现：共享文件→解析与索引→查资料→建立任务→指定Skill/模板→生成成果→对话纠正→保存版本→同事接续→确认并导出。

首条验收故事：A上传客户需求、历史方案和案例；B检索并选定资料，生成半天课程大纲；A多轮修订并确认大纲；C基于确认版生成各章节详细内容；B修改其中一节；A确认并下载。所有人在同一Web工作台操作，生成文件自动保存。

首版不自研自动长期记忆和历史语义压缩，不引入复杂流程画布、多Agent并行和任意桌面APP遥控；IM之后接相同的搜索与查询接口。真实Skill仍是原包资产，但首批只开放经过验证的方法和依赖；不建设通用在线代码IDE。

执行方式沿用已有方向：一个实际验证过的适配器先跑通，Pi+DeepSeek仍为候选，未验证前不得标可用。固定文本任务也可由Spring AI直连模型实现；两种路径遵守相同任务/成果契约，首版不同时建设两套执行链路，Spring AI升级不作为共享业务链路的前置。

## 2. 最新代码提供了什么，哪些不能直接复用

| 代码位置（仓库相对路径） | 已有能力 | 用于新工作台时的缺口 |
|---|---|---|
| `backend/.../service/FileStorageService.java`、`OssService.java` | 原件保存OSS、预签名下载、白名单/20MB上限 | 独立资料ID、不可变版本、团队/工作区权限、删除保留策略 |
| `backend/.../service/FileParseService.java` | 调Python解析、120秒超时、100000字符默认上限 | 目前主要返回纯文本；需要结构节点、来源定位、解析警告，不能静默截断 |
| `ai-service/routers/internal.py` | TXT/MD、DOCX段落、PDF文本、PPTX文本、CSV等解析分支 | DOCX当前未提取表格；PDF页边界和PPT页号未保留；表格结构、扫描件需单独处理；不能按代码分支宣称所有格式可用 |
| `backend/.../service/DocumentStructureParser.java` | 标题识别、章节切分、默认3000字符、相邻块重叠一段 | 这是萃取分批输入；不是完整可定位RAG索引。单个超长段落不切，不能作为严格长度保证 |
| `backend/.../service/KnowledgeCleaningService.java` | 解析→分节→LLM提取知识候选→审核；逐节进度、重试 | 共享资料上传不能强制先萃取成知识条目，否则丢失原始上下文；原文检索应走独立链路 |
| `backend/.../service/KnowledgeCaseRetriever.java` | pgvector余弦检索、企业/公共范围、状态/时效/阈值过滤 | 当前查销售知识/案例条目；新工作台需独立资料块和可选范围，不能直接调用后混搜 |
| `backend/.../service/DashScopeEmbeddingService.java` | 批量embedding、配置模型/维度、pgvector写入 | Key/URL目前写SDK全局静态字段；多配置并发不能照搬；批次失败返回部分结果，工作台需按chunk ID明确对应和失败 |
| `backend/.../service/ConversationPersistenceService.java` | 销售会话和消息持久化 | 数据归属绑定分身和个人；团队任务需要成员权限及独立表，不能直接借用分身会话 |
| `backend/.../service/PromptAssemblyService.java:buildChatMessages` | 从数据库取最近20条消息，再做预算裁剪 | 不是全部历史，也不是可靠摘要；不区分硬约束、当前稿、旧稿 |
| `backend/.../service/ContextWindowGuard.java` | 估算token、裁剪旧消息 | 保底保留若干消息时仍可能超预算；不能保证关键要求保留，不应直接当新工作台预算器 |
| `backend/.../service/ChatStreamAdapter.java` | 模型流式输出、SSE适配基础 | 当前将user/assistant历史串成单个user文本；新链路应保留真实消息角色/工具协议，不直接照搬 |
| `backend/.../service/ChatClientResolver.java` | 按企业选择模型Key和客户端 | 同一企业内尚无销售/团队用途区分；后台执行必须显式传入授权配置，不能依赖请求线程上下文 |

复用存储、身份、解析服务基础和pgvector部署；新建团队资料/检索/任务/成果模块。数据库可共用，团队数据使用独立表，原件使用独立OSS前缀。无需将新模块绑定现有数字分身Skill实体。

## 3. 流程A：上传资料、版本与预览

### A1. 收集标准

上传必填：文件、标题（默认文件名）、存放范围（团队共享库或当前工作区）。可选：分类、标签、来源、用途说明。企业和上传人由服务端身份确定，不接受前端任意指定。

至少区分客户原始资料、已确认经验/案例、历史方案、通用知识、模板、AI草稿。类型是管理标签，可信状态和访问范围是独立字段；移动分类不能自动改变权限。客户资料默认当前工作区，成果默认草稿，不自动变为可信公共知识。

### A2. 上传与版本

1. 前端上传→Java验证成员、扩展名/内容类型、大小和配额→生成资料及版本ID。
2. 原件写OSS：`team/{companyId}/{scopeId}/{assetId}/{versionId}/original.ext`；只存对象key，不存长期签名URL。
3. 数据库记录hash、大小、格式、创建者、版本说明；重复上传仅在同一授权范围内提示，不通过去重结果暴露别人的文件。
4. 成功后返回assetId、versionId、状态；提交持久处理任务。OSS成功而DB失败的孤儿对象通过补偿清理，DB不能指向未成功保存的对象。
5. 新版上传沿用assetId，新增versionId；不覆盖旧对象。运行固定版本，不能在上传新版后静默换输入。

首版小文件经Java上传即可，不必先做浏览器直传/断点续传；以后扩展直传时增加完成确认，不能仅凭前端“上传成功”就可检索。

### A3. 解析、预览和索引是独立状态

原件：`uploading→stored/failed`；解析：`pending→running→ready/needs_manual/failed`；预览与索引分别有状态。原件stored即可下载，不等于全文可搜。

新文件首次解析失败：保留原件、展示原因并允许重试/补文字。新版本索引失败：旧可检索版本可继续服务，但界面必须标明“原件V2，当前索引V1”。用户显式选V2生成时，若还不能读取/检索，应等待或明确改选V1，不能暗自替换。

预览按格式能力开放：文本/Markdown正文，PDF原样，Office可下载；Office全览需要独立转换服务及字体/版式验收后开放。解析文本不是原排版预览。下载与预览每次鉴权；短时签名发出后在到期前可能仍可访问，若要求移除成员即时失效，采用后端代理读取。

### A4. 结构化解析契约

Python返回`parserVersion、normalizedText/Markdown、nodes[]、warnings、needsManual`。node至少有`nodeId、type、text、headingPath、order、locator`。locator根据格式提供PDF page、PPT slide、DOCX段落/表格、表格sheet/row；没有可靠页码时不用伪造页码。

- DOCX按正文顺序读取标题、段落、表格；合并单元格等复杂结构给警告。
- PDF逐页保留位置；扫描页无有效文本标`needs_manual`，未接OCR不写“已完整解析”；复杂表格首版可要求人工核对。
- PPTX保留slide号及文本块顺序；图表、图片里的信息未解析要提示。
- 首批保证TXT/MD/DOCX/文本PDF；PPTX/CSV按实际样本验收再开放。XLSX、旧Office、音视频、图片OCR不因Python有分支就默认支持。
- 原件、解析结果、预览副本都绑定同一versionId；纯文本清理只能去已知格式噪音，不用LLM自由改写事实。
- 解析进程限制下载源、文件大小、解压后体积、处理时间和内存；HTML预览清理脚本，文件内容按不可信输入处理。

## 4. 流程B：分块、向量与索引更新

### B1. 两种用途分开

原文RAG链路：原件→结构化解析→原文分块→embedding→可检索。它保存的是依据，不要求LLM先提炼。

知识萃取链路：原文→LLM提取候选知识/案例→人工确认→正式条目。现有销售系统已有这一类能力，团队库先不自动进入这条发布链路。

### B2. 分块规则（建议起点，需样本验证）

1. 按章节/页/段落结构组织，标题链随块保存；完整小表格尽量不拆。
2. 超长章节再按句子/段落切；超长单段必须兜底切分，不能无限超限。
3. 初始目标每块约500—900 token，重叠约80—150 token；这是调参起点，不是固定最佳值。embedding输入上限和实际tokenizer决定硬上限；只有字符估算时留余量并校准。
4. 跨块表格按行分组并重复表头，保留表格ID/行范围；不让一块只有数值没有列名。
5. chunk保存原文位置、标题链、顺序、hash、chunker版本。重叠块检索后去重，必要时合并相邻块，避免重复占上下文。
6. 全文预览读取完整解析结果，不能把所有重叠chunk拼回“全文”。

chunk最小字段：`id、companyId、assetVersionId、indexBuildId、nodeIds/locator、ordinal、headingPath、text、tokenEstimate、contentHash、embedding`。

### B3. 向量配置和存储

- 原件/解析JSON/导出文件在OSS；元数据、块正文与向量在PostgreSQL独立team表，向量仍用pgvector。
- 每个索引构建保存embedding的provider、model、dimension、预处理版本。查询必须使用同一套配置；不同模型即使维度相同也不能混检。
- 当前项目的DashScope模型/1024维可作候选复用，但使用团队独立配置。聊天模型与embedding模型是两种配置、两笔调用，不因选DeepSeek就自动有向量能力。
- embedding任务按chunk ID映射，批次部分失败只标记相应块；维度/结果数量验证后写入。不能把缩短的向量数组顺序配给原始全量chunk。
- 少量团队资料可先在授权范围精确向量排序；数据增长后再启用/调优HNSW。近似索引过滤后的召回需实测，不能认为有LIMIT就一定返回足量结果。

### B4. 构建与切换

`pending→parsing→chunking→embedding→ready/failed/needs_manual`。每阶段短事务，记录attempt、进度、错误；worker调用模型/解析时不持有长DB事务。

以versionId+parser/chunker/embedding配置+chunk hash做阶段幂等。新构建完成并验收完整性后，原子切换资料的searchableVersionId/indexBuildId；旧索引在历史保留窗口内留存。重建不能半新半旧。

首版用DB持久job+worker轮询/租约即可，不增加Kafka；进程内异步线程池不能独自承担重启恢复。同一作业被重复领取时靠租约和幂等防重复落库。

## 5. 流程C：搜索、RAG与完整资料读取

### C1. 搜索路径

前端选择当前工作区/团队共享库/指定文件→Java按身份求授权范围→文件名/正文关键词与向量召回→合并去重→返回原文片段和位置。

首版关键词可用标题/正文精确包含匹配，规模小先保证正确；可按部署条件用pg_trgm加速包含查询，短词需验证。已有中文分词全文索引应先确认数据库扩展实际安装，再复用；不把PostgreSQL simple分词当完整中文搜索。

建议初始每路召回20条，按排名融合后保留约6—10条，再受总token预算约束；这些参数需以真实问法调整，reranker不是首版前置。关键词命中和向量距离不是可直接相加的同一种分数。

权限条件须进入各路检索和最终读取；不能先全库查出内容发给模型，再前端过滤。团队检索默认只查team资料表；显式需要销售知识时以后增加授权只读来源，不复用“企业+全部公共销售知识”的默认SQL。

### C2. 四种操作不能混淆

| 用户目的 | 读取方式 |
|---|---|
| 找相关案例/材料 | 搜索/RAG，返回相关片段 |
| 基于资料回答问题 | 对命中片段生成回答，保留引用 |
| 按指定完整模板写方案 | 模板全文或结构化完整读取；不能只靠Top-K片段 |
| 总结整份长文档/完整课程 | 逐节遍历、记录覆盖范围，再合并；不能把检索前几块当已看全文 |

“给第二部分再补一个练习”的检索query需加入当前任务主题、第二部分标题和受众，而不是只用这一句。首版可程序拼接这些已知条件；不强制先建复杂查询Agent。

RAG快照保存chunk ID、资料版本、原文片段hash、检索方式/分数。引用以服务端分配的来源ID为准；校验模型引用的ID确实在本次来源里，再跳转对应版本和定位。没有依据时标“待补充/通用建议”；来源ID有效不代表论断已被证实，仍需人工审阅或单独事实检查。

## 6. 流程D：建立任务与第一次生成

### D1. 任务输入

成员输入目标，选择成果类型、Skill/模板和资料。系统把缺失项列为待澄清点，不要求每次填写大表单。

任务保存：目标、受众、用途、范围、格式、时长等显式要求；课程字段只是模板扩展。资料分“必须遵守的客户需求/模板”和“可参考案例”，不能把历史案例的条件覆盖本次客户要求。硬约束应显式记录；长需求文件需提炼要求后由人确认，不能声称RAG一定召回全部限制。

### D2. 发送到完成

`operation`首版明确区分`discuss/search/generate/revise`：讨论和搜索不自动采纳/覆盖成果；生成和修改才创建成果候选。用户可先讨论，再点击生成。Skill试运行走相同执行链路，但标记为test。

1. 前端POST message/run，包含taskId、文本、operation、baseArtifactVersionId、targetBlockIds、资料引用和幂等键。
2. Java验证身份、成员、资料版本、Skill发布版本、执行配置及当前写入状态；重复幂等键且请求一致返回同一个run，复用键但请求不同拒绝。
3. 短事务保存用户消息与run/执行快照；后台worker领取，浏览器关闭不取消任务。
4. 固化taskBriefVersion、confirmedConstraintsVersion、inputVersions、skillVersion、executionProfileRevision、baseArtifactVersion和上下文来源清单；凭证只留受控引用。
5. 检索并组装本轮上下文→执行器生成→持久事件/SSE展示真实进度。
6. 输出先登记candidate，检查完整性、格式及供应商结束原因（如长度上限截断）；原件/正文落存储成功后才可供采纳。截断/失败的部分输出标partial，不晋升当前成果。
7. 用户采纳后通过乐观锁更新currentVersion；丢弃也保留run记录。生成成功和成果被采纳是不同状态。

前端不提交完整历史作为权威输入。后端从库读取，避免篡改、重复消息、客户端漏历史。共享会话的发言者保留真实成员身份。

## 7. 流程E：反复纠正——历史、上下文和成果如何配合

### E1. 必须分开保存的四层

1. **原始历史**：全部用户消息、回复、修改请求和操作结果，按taskId及单调序号保存，供回看、明确引用和排障；不等于每次全量发送。
2. **任务事实/确认要求**：人确认的受众、时长、禁用内容、已作决定等，带来源消息ID、版本和生效状态，后续每轮必要时重读。
3. **当前成果**：明确版本的正文/章节，是修改基准。旧版全文无需反复塞入历史；历史消息可以显示关联成果卡片。
4. **本轮工作上下文**：本次模型真正收到的规则、Skill、要求、当前稿/目标章节、必要历史、证据与修改指令。

不能仅靠“最新稿+本轮一句话”覆盖所有场景，也不能把“DB存了全部消息”等同于模型看到了全部历史。

### E2. 上下文组装与预算

建议实现`TeamContextAssembler`：

```text
固定规则 + 当前Skill说明/必要工具schema
+ 已确认任务要求（最新确认版本）
+ 当前稿，或目标章节+全局大纲+相邻必要内容
+ 必要历史：最近完整交互、用户明确引用的旧消息/版本
+ 本轮检索片段/完整必需模板
+ 当前修改要求及修改范围
```

保留真实system/user/assistant/tool角色；数据库历史仅按可见授权读取，材料内容作为资料而非系统指令。工具结果可以保存到文件并按需读片段，不让大段日志无限占窗口。

预算满足：`固定规则+工具/Skill+要求+稿件+历史+证据+本轮输入+输出预留+安全余量 <= 当前模型上下文上限`。实际模型限制来自执行配置/官方参数，不能用全局固定64K对所有模型兜底。使用provider tokenizer或可靠估算，并用返回usage校准；工具schema和后续工具结果也占预算。

超过预算的处理顺序：

1. 去重复旧稿、重复片段和无关工具日志，不删除原始存档。
2. 缩小本轮参考资料和可选历史；被用户明确引用的历史先纳入，不能为省token悄悄丢弃。
3. 完整稿过长则改为章节修改；整篇重写分章节执行并校验全局要求。
4. 仍放不下则停止本轮提交，提示具体哪部分超限，选择缩小范围、明确任务要求或开启基于已确认状态的后续阶段。

核心要求、当前指令和选定修改范围不能静默裁掉。首版不自研自由语义摘要来“保证不丢信息”。

### E3. 历史如何进入模型

Spring AI直连模型：平台按token预算读取完整近期交互，再加用户引用的旧消息/版本。不是固定“20条就够了”。旧成果通过版本引用加载；近期对话避免重复放入同一份全文。不得让记忆Advisor和自定义拼装重复加入同一历史。

Pi/Codex等原生执行器：固定任务→原生session/thread映射，串行继续；由执行器管理原生历史/压缩。平台每轮仍明确提供当前要求和稿件版本，不再把全部平台聊天重灌一遍。运行时需要验证会话保存、重启恢复和预算/压缩事件，无法控制时不承诺完全一致。

选定哪条执行路径，就明确谁负责原生历史，避免平台和执行器双重压缩。原始平台记录与执行器内部检查点分开，不能把隐藏推理作为团队共享记录。

### E4. 纠正要求如何不丢

- 对本次稿件的意见：绑定baseVersion和目标模块，采纳后由新版成果承载。
- “以后都要遵守”的要求：用户点击“加入任务要求”，或确认系统提出的候选要求后生效；保存来源与版本。不做后台自动记忆。
- 修改既有硬约束：显式显示变更，如半天→一天；生效后标出大纲/详细内容哪些需要重检。冲突要求未确认前不同时送入模型。
- “按之前那个来”：允许选历史消息、旧成果版本并引用后继续；定位不明确时澄清，不假装知道。
- 从很早一版重新修改：创建以该版为基准的候选；若当前版本已变化，不能直接覆盖，应选择派生或确认替换。

一个真实限制：用户未确认成要求、也未在本轮带入的很早讨论，首版不能保证始终记得。通过可见任务要求、历史引用和阶段确认控制这项风险，不能用“支持记忆”掩盖。

### E5. 短大纲与详细课程分别处理

短大纲：在预算内给完整当前稿，让模型生成候选全文，做差异预览；模型可能误改其他部分，因此局部修改仍应限制目标模块。

详细课程：按稳定blockId/sectionId保存章节。每轮读取全局要求、大纲、目标节、必要邻接内容和证据，仅允许返回目标节新内容。后端按ID合并，非目标节沿用原始内容，不靠提示词保证不误改。合并校验baseVersion，生成新完整成果版本。

首版结构可用“成果版本body JSON中的章节数组+Markdown渲染”，不必先做复杂富文本协同引擎。块ID由系统生成并跨版本保留，章节重排不以‘第2节’字符串作为唯一身份。

整篇风格统一/时长变化等全局修改会影响多个块：先确认范围，再逐节生成候选，最终检查总时长、结构和术语。可程序核验的检查用规则；教学适配、内容专业性仍由人审，不能以LLM自评代替验收。

## 8. 流程F：Skill、固定流程与热更新

真实Skill保留`SKILL.md、scripts、references、assets`。按指令型/带脚本工具型声明依赖，初期由管理员发布少量受信任包。

导入→路径/解压体积/依赖校验→草稿→样例试运行→查看成果→发布不可变版本。Skill原包不按知识块萃取，不把所有参考文件每轮全部注入。按需加载参考，来源仍可追溯。

模型API能生成文字和提出工具调用，但脚本由受控执行器运行；依赖不能因为写在SKILL.md里就自动存在。脚本放隔离容器，不挂业务宿主目录、不带Docker socket，只给当前任务所需输入和受控凭证。首版不开放任意外部系统写操作。

热更新含义：编辑草稿→试运行→发布新版本→新任务使用；正在运行的任务固定旧版，同一任务后续默认沿用旧版。显式升级时新建后续阶段/运行快照，不在半轮执行中替换文件。

首条内置流程：整理需求→检索材料→生成大纲→确认→生成各节详细内容→修订→导出。步骤状态存数据库，人工确认后可关闭页面再回来；不靠模型从聊天里猜流程停在哪。用户自定义步骤编辑器保留为后续目标。

## 9. 流程G：成果、导出、资料更新和团队接续

候选生成→预览/对比→采纳→当前草稿；最终确认固定某个不可变版本。人工文本编辑同样创建新版本，并参与乐观锁。

内容以Markdown/结构化JSON为主；导出DOCX等是独立可重试步骤，记录源成果版本和导出模板版本。模型正文生成成功而导出失败时，只重试导出，不重新花钱生成全文。不把聊天中“已生成文件”当真实文件，必须有存储对象、大小、hash和下载入口。

详细内容绑定其大纲基准版本。大纲后续修改标记受影响详细内容待检查，不静默使旧详情看起来已同步。汇总导出必须选择一致的大纲/详情版本集合。

同事接续读取同一任务的当前要求、当前成果、来源和可见历史；原生会话可用时恢复同一授权会话，不能读取成员个人电脑APP历史。无可用原生检查点时，从明确的任务状态和成果建立新阶段，并显示接续依据，不宣称内部状态无损恢复。

文件归档/删除：停止新检索和新选用；历史引用按保留策略存版本并继续鉴权，删除不等于把文件暴露为永久公开。正式清除需处理原件、预览、解析、chunk和向量的关联。

成果“存为团队资料”是显式动作，新增来源关系并走资料索引；AI草稿不得自动回灌销售案例库或作为已确认知识。确认事实有误时可追到依赖它的成果版本，首版先展示关联清单，不做自动全量重写。

## 10. 前后端接口、状态与失败语义

建议前缀`/api/v1/team`；以下是待实现契约，不代表已有接口。

| 操作 | 接口建议 | 关键字段/行为 |
|---|---|---|
| 工作区/成员 | `/workspaces`、`/workspaces/{id}/members` | owner/member，服务端逐次鉴权 |
| 上传/新版 | `POST /assets`、`POST /assets/{id}/versions` | scope、分类、文件、版本说明；返回版本和处理状态 |
| 文件详情/内容 | `GET /assets/{id}`、`GET /asset-versions/{id}/content` | 解析/预览/索引分开；返回定位节点 |
| 下载/重处理 | `GET /asset-versions/{id}/download`、`POST /asset-versions/{id}/reprocess` | 短签名或代理；重试只针对失败阶段 |
| 搜索/阅读 | `POST /search`、`GET /asset-versions/{id}/nodes` | query、范围、过滤；节点范围读取受预算限制 |
| 建任务/改要求 | `POST /workspaces/{id}/tasks`、`PATCH /tasks/{id}/brief` | expectedRevision，要求变更保留来源 |
| 发言/生成/修改 | `POST /tasks/{id}/messages` | text、operation、baseArtifactVersionId、targetBlockIds、引用、Idempotency-Key；返回messageId/runId |
| 任务/历史/事件 | `GET /tasks/{id}`、`/tasks/{id}/messages`、`/runs/{id}/events` | 消息和事件按seq分页/补取；SSE只是传输，不是任务执行器 |
| 停止/重试 | `POST /runs/{id}/cancel`、`POST /runs/{id}/retry` | 持久取消请求；重试新attempt，不覆盖旧run |
| 成果/采纳 | `GET /artifacts/{id}/versions`、`POST /artifacts/{id}/adopt` | candidateVersionId、expectedCurrentVersionId；冲突409 |
| 编辑/确认/导出 | `POST /artifacts/{id}/versions`、`/confirm`、`/exports` | 不可变版本；确认及导出指向明确版本 |
| Skill | `/skills`、`/skill-versions/{id}/test`、`/publish` | 草稿/试运行/发布不可变版本；执行快照固定版本 |

run状态：queued→preparing→running→succeeded/failed/interrupted；取消使用cancel_requested→cancelled，并处理取消与完成竞态。waiting_user用于明确需要用户补充/确认的节点，不宣称任意进程暂停可恢复。

事件至少有eventId/seq、runId、type、时间、可见payload。支持started、retrieval_completed、text_delta、artifact_candidate、warning、completed、failed、cancelled。事件先持久化或有可恢复检查点，再推送；流式token可合并为文本片段，避免逐token高频写库。

刷新只GET状态/补事件，不能重POST任务；网络断线不自动重生成。客户端根据run状态决定按钮可用性，服务端再次校验；SSE连接和下载接口都不能省成员鉴权。

同工作区首版一个写入运行，运行期间禁止采纳/人工写入同一成果；发送和采纳仍用DB锁/版本检查防竞态。其他人可看、写待发送草稿；锁由租约管理，不能依赖浏览器在线。跨工作区/企业配置也需隔离。

模型失败、429/超时、解析失败有错误类型和下一步；不无限重试。只读检索/embedding可有界退避重试；已产生外部副作用或不明执行结果的脚本不能盲重放。首版不承诺任意失败点自动续跑。

## 11. 数据模型与模块边界

以下是逻辑实体，可按需要合并物理表，避免先造通用企业平台：

- Workspace/Member：工作区背景、成员、版本、归档状态。
- Asset/AssetVersion：范围、分类、可信状态、原件和解析/预览引用、hash、版本及可检索版本指针。
- DocumentChunk/IndexBuild：原文、定位、索引构建、embedding配置、完成情况。
- Job：解析/索引/执行/导出任务的阶段、租约、attempt、错误；可共享基础调度，不混淆业务状态。
- Task/TaskBriefRevision/Message：目标、确认要求、操作历史、成果引用，消息用任务内seq确定顺序。
- Run/Event：运行配置快照、输入/检索/上下文清单、输出状态、usage、错误、操作者。
- Artifact/ArtifactVersion：类型、父/基准版本、章节内容、来源run、采纳/确认记录及导出引用。
- AgentSkill/AgentSkillVersion：真实方法包、依赖、验证组合、发布状态；不复用销售分身Skill表。
- ExecutionProfileRevision/CredentialRef：用途、provider、模型、上下文/输出限制、允许工具、预算及凭证引用。

上下文清单记录实际送入哪些消息/版本/来源、预算与删减原因，可将必要的请求快照加密受控保存用于排障；不在普通日志打印完整客户资料和Key，也不保存/共享隐藏推理作为业务要求。

模块建议：Java中独立`team`业务包，Next.js中`/team-workspace`，现有Python增加结构化解析契约；确需真实脚本执行时单独runner子工程。先做有边界的模块，不拆一批微服务。

## 12. 模型和销冠系统隔离

复用账号/企业身份；团队资料、chunk、任务、原生会话和成果独立存放。模型配置增加明确用途`SALES`/`TEAM_WORKSPACE`，团队使用独立ExecutionProfileRevision和CredentialRef；embedding也有明确配置，不使用销售Key隐式兜底。

每次run由服务端固化companyId、workspaceId、配置引用和限额。后台worker从可信run记录恢复身份范围并显式传入客户端/工具；不能在异步线程读取一个可能已丢失的HTTP ThreadLocal就决定租户。

Key只在服务端按授权解密使用，不进前端、聊天、Skill包、共享目录和日志。不能在并发请求里切SDK全局静态Key/URL。同企业两种用途若人为配置同一供应商Key，供应商配额仍共享，系统只能做本地预算，不能声称物理配额独立。

额度和故障按用途记账，团队runner不可用不影响销售系统；团队执行配置缺失直接提示配置，不悄悄借用销售Key。凭证轮换不保留明文快照，运行记录保存配置版本/引用及使用记录。

## 13. 按风险排序的实施与验收

### 13.1 先用真实样本验证，避免先做齐页面

准备：2份客户需求、3份历史方案/案例、含表格的DOCX、文本PDF、扫描PDF、一个真实Skill、大纲及详细内容的合格样例。已获授权的供应商Key/网络可用后再做收费调用；当前尚未验证模型实际效果。

先纵向验证：解析不漏关键字段→检索找回正确片段→大纲首稿→连续纠正→详细内容单节修改→版本保存/导出。只验证这条链路所需的一个执行适配器；没有实际文件和合格内容，不算“接通”。

### 13.2 技术点、方案与完成标准

| 优先 | 技术点 | 首版解法 | 验收证据 |
|---|---|---|---|
| P0 | 资料解析可靠性 | 结构化节点、表格/位置、人工处理状态 | 对照原件核对关键段落/表格；扫描件不假就绪 |
| P0 | 分块/检索 | 独立team块、同模型向量、关键词+语义、引用 | 约20个真实查询，预标正确资料/段落，统计召回和引用定位；上线阈值由团队样本确定 |
| P0 | 多轮纠正不丢约束 | 确认要求+版本稿+必要历史；长稿分节 | 连续修改约20轮，硬约束不丢；覆盖显式引用旧消息和冲突要求 |
| P0 | 局部修改不伤全文 | 稳定块ID、只合并目标块、版本检查 | 非目标块hash不变；并发基准冲突409 |
| P0 | 真Skill兼容 | 固定一个执行组合、样例验证 | 真实读资料/调用需要的工具/产出文件，缺依赖明确失败 |
| P0 | 版本/任务可靠性 | 幂等、持久job、原子采纳、刷新补取 | 重复发送只一run；断线不丢已保存结果；重启后明确恢复或中断 |
| P0 | 数据与Key隔离 | 独立team范围、显式执行配置 | 两工作区/企业越权读取、引用、下载、事件均拒绝；不调用销售Key |
| P1 | Office阅读与导出 | 版本化转换副本、独立导出重试 | 有样本版式验证；转换失败可下载原件，不重新生成正文 |
| 后续 | 自动记忆/复杂流程/IM | 基于已稳定搜索、任务和成果接口扩展 | 有真实使用数据再定义范围 |

这些属于关键链路集成验收，不为低风险页面文案堆测试。代码实现后重点覆盖原子版本更新、权限过滤、分块边界、预算超限和阶段幂等。

### 13.3 首版默认建议与仍需逐项确认的参数

建议默认：限定格式与大小、工作区资料默认私有于成员、一个执行组合、任务串行、候选稿需采纳、要求显式确认、详细内容按章节、固定内置流程。

待真实样本决定：最终首个执行器/模型与Skill兼容性；输入/输出上限和费用预算；分块/召回参数；是否第一批必须Office原样预览和DOCX导出。未定项可先做无收费的结构与文件验证，不妨碍明确接口契约。
