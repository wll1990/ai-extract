# 鉴权撤销方案（S-F6 / S-F7）

日期：2026-10-28
背景：[docs/45 安全评审](45-P2培训-安全评审-20261028.md) 发现两个全局缺陷——
`revokeUser` 无调用点（权限变更后旧 token 仍生效，最长 24h）、Redis 异常时撤销检查 fail-open。
本文给出可落地的方案；由架构专家评审 + 代码实测核对后成稿。

---

## 1. 结论

**推荐：token 内嵌 `ver`（用户安全版本号），改角色/停用时 DB `token_version + 1`；保留现有黑名单作为「封号/踢全部设备」的硬撤销；撤销检查失败时先回源 DB，DB 也不可用才拒绝。**

- 不引入 refresh token（与 C 端 7/30 天长 token 的硬约束冲突，改动面最大）。
- 不做「每请求查 DB 角色」（对话/对练每发一条消息就是一次请求，热路径压力不可控）。
- 版本号是正向白名单语义：改权限 = 旧 token 失效但可立即重登；封号 = 黑名单硬否决 + 强制下线。两者不混。

---

## 2. 现状（实测，带行号）

权限来源是 **token claim，不是 DB**：

```
请求 → JwtAuthFilter.doFilterInternal
  ├─ extractToken: Authorization: Bearer → ?token=            (JwtAuthFilter.java:151-159)
  ├─ validateToken 验签/验过期                                 (:61)
  ├─ isRevoked(userId, jti)  ← 唯一撤销检查点                   (:67)
  ├─ getPermissionsFromToken(token)  ← 权限直接取 claim         (:71)
  └─ setAuthentication(...) 写入 SecurityContext               (:72)
```

| 事实 | 证据 |
|---|---|
| JWT 有效期 24h | `jwt.expiration: 86400000`（[application.yml:120](backend/src/main/resources/application.yml#L120)） |
| C 端游客 7 天 / 注册用户 30 天，走同一条标准 JWT 路径 | `CAuthService:220`、`ShareService:475` |
| 签发点共 **4 处** | `AuthService:102`（登录）、`AuthService:177`（注册）、`CAuthService:220`、`ShareService:475` |
| `/auth/me` 返回的是 **DB 里的新权限** | `AuthService.buildUserInfoResponse` 用 `RolePermissions.getPermissions(user.getRole())` |
| 真正拦截请求的是 **claim 里的旧权限** | `SecurityConfig.hasAuthority(...)` |
| `revokeUser` 零调用点 | 全库仅定义（[TokenRevocationService.java:32](backend/src/main/java/com/aiextract/config/TokenRevocationService.java#L32)） |
| 只有登出会撤销单个 token | [AuthController.java:183](backend/src/main/java/com/aiextract/controller/AuthController.java#L183) |
| Redis 异常 → 撤销检查放行 | [TokenRevocationService.java:48-53](backend/src/main/java/com/aiextract/config/TokenRevocationService.java#L48-L53) |
| 合作方 JWT 每次请求重查 `PartnerApp.status` | `PartnerJwtFilter:60-62`（不受本次改动影响） |
| **当前没有任何「改 B 端角色 / 停用账号」的写接口** | `AdminController` 的 `/admin/users` 只有 GET |

> 所以 S-F6 今天是**潜在**缺陷，不是马上能打的洞；但 token 泄漏无法按人撤销是现在就存在的，且用户管理一落地就会变成真洞。

## 3. 方案对比

| | a. 只接 `revokeUser` | b. 短 TTL + refresh | c. 每请求查 DB | **d. token 内嵌 `ver`（推荐）** |
|---|---|---|---|---|
| 改动面 | 极小 | 最大 | 中 | 中 |
| 每请求开销 | 2 次 Redis EXISTS | 双 token + 刷新逻辑 | 1 次 DB | 3 次 Redis（可流水线合并） |
| 失效窗口 | 秒级 | access 分钟级 | 秒级 | 秒级（Redis 回源） |
| C 端 30 天 token | 黑名单 key 挂 30 天 | **冲突**（不能缩） | 可行 | 可行 |
| 改权限体验 | 强制全端下线 | 强制下线 | 下次请求生效 | 旧 token 失效，可立即重登 |
| 回滚 | 容易 | 难 | 容易 | 容易 |

**为什么不选 a 单用**：解决不了 S-F7；且黑名单是否决式语义，改个角色把用户所有设备踢下线太重。
**为什么不选 b**：C 端 30 天 TTL 不可降，refresh 泄漏后同样要撤销，等于把问题搬了个家。
**为什么不选 c**：对话类接口每发一条消息一次请求，`SELECT ... FROM "user" WHERE id=?` 打在热路径。

## 4. 代码级设计

### 4.1 Schema（注意：Flyway 当前是关闭的）

`spring.flyway.enabled: false`（[application.yml:24](backend/src/main/resources/application.yml#L24)），所以**只加迁移文件不会生效**。两处都要落：

1. `scripts/auth-revoke-schema.sql`（幂等，立即可执行）：
```sql
ALTER TABLE public."user"
    ADD COLUMN IF NOT EXISTS token_version bigint NOT NULL DEFAULT 0;
COMMENT ON COLUMN public."user".token_version IS '安全版本号：改角色/停用账号时 +1，旧 JWT 立即失效';
```
2. `backend/src/main/resources/db/migration/V50__add_user_token_version.sql`（同样的 `IF NOT EXISTS` 语句），供将来 Flyway 重新启用时使用；因为带 `IF NOT EXISTS`，对已执行过脚本的库也不会失败。

### 4.2 实体

`User` 加字段（表名是带引号的 `"user"`）：
```java
@Column(name = "token_version", nullable = false)
@Builder.Default
private Long tokenVersion = 0L;
```

### 4.3 JwtUtil

```java
// 版本参数设为必填，避免漏改某个签发点（当前 4 处，均会被编译期强制）
public String generateToken(UUID userId, UUID companyId, String role,
                            long ttlMillis, long tokenVersion);
// claims.put("ver", tokenVersion);
public long getTokenVersionFromToken(String token); // 无 ver claim 返回 0（兼容改造前签发的 token）
```

### 4.4 TokenRevocationService

```java
/** true = 拒绝；false = 放行。合并「版本 + 用户黑名单 + jti 黑名单」三次查询（executePipelined）。 */
public boolean isBlocked(UUID userId, String jti, long tokenVersion)
```

判定顺序：
1. `GET auth:ver:{userId}` → 与 `tokenVersion` 不等 ⇒ 拒绝；
2. `EXISTS auth:revoked:user:{userId}` ⇒ 拒绝；
3. `EXISTS auth:revoked:jti:{jti}` ⇒ 拒绝。

**失败策略（对评审方案的一处修正）**：不要「Redis 一异常就 401」——那会把 Redis 抖动放大成全站登录失效。改成：

```
Redis 正常        → 用 Redis 判定
Redis 异常        → 回源 DB 读 "user".token_version（每次异常请求一次 DB，仅故障期）
DB 也异常         → 拒绝（401），并计数告警
```

这样 S-F7 的「依赖故障时撤销整体失效」被修掉，同时不会制造新的可用性单点。可选加固（不必首版做）：30 秒本地版本缓存，把 Redis 抖动期的 DB 读也吸收掉。

### 4.5 JwtAuthFilter

```java
long ver = jwtUtil.getTokenVersionFromToken(token);          // 紧跟 getJtiFromToken
if (tokenRevocationService.isBlocked(userId, jti, ver)) {
    response.sendError(HttpServletResponse.SC_UNAUTHORIZED, "登录已失效，请重新登录");
    return;                                                   // 原来是匿名继续 → denyAll 403，改为明确的 401
}
```
前端 `client.ts:48` 已对 401 有跳登录处理，可直接用。**SSE**：`OncePerRequestFilter` 只在连接建立时跑一次，在途长连接不会被打断。合作方分支（`JwtAuthFilter:84-97`）**不接入**这套校验——它不是本服务签发、没有 `ver`，且已有 app 级禁用检查。

### 4.6 触发钩子（新建 `UserSecurityService`）

```java
/** 与 role/status 变更同事务调用：DB +1，提交后写 Redis */
public void onAuthoritiesChanged(UUID userId)
/** 封号/踢全部设备：提交后写 auth:revoked:user:{id}，TTL 30 天 */
public void revokeAll(UUID userId)
```
- DB `+1` 必须在**业务事务内**（回滚一起回滚）；
- Redis 写入必须在 **afterCommit**（否则回滚后 Redis 残留高版本会错杀）；
- Redis 写失败只记日志，**不影响主流程**（下一次请求会回源 DB）。

### 4.7 现有唯一 role 变更点

`CAuthService.register`（游客 → 注册用户）：
- 用**实体自增** `user.setTokenVersion(user.getTokenVersion() + 1)`，不要用 JPQL 自增，否则内存里还是旧值，紧接着 `issueToken(user)` 会签出「刚生成就失效」的 token；
- 4 个签发点全部改为传 `user.getTokenVersion()`。

### 4.8 未来的触发点（现在没有接口，先留钩子）

改 B 端角色、停用/启用账号、删除用户、C 端封号、企业整体停用——各自加一行 `onAuthoritiesChanged` / `revokeAll`。用户管理接口落地时一起接。

## 6. 测试矩阵

| 用例 | 期望 |
|---|---|
| 改 DB `token_version+1` 后旧 token 请求 | 401，重登后新 token 可用 |
| 旧 token（改造前签发、无 `ver`）+ 版本仍为 0 | 正常通过 |
| Redis 断开、DB 正常 | 请求正常（回源 DB），撤销仍生效 |
| Redis 与 DB 都断开 | 401 + 告警计数 |
| SSE 建连后再 bump | 在途流不断，新连接 401 |
| 合作方 `?token=` 带 `appId` | 不受影响，禁用 app 后下次请求 401 |
| 登出单 token | 该 jti 失效，其他设备不受影响 |
| `register` 升级后签发的新 token | 必须能通过校验（防止版本签错） |

## 7. 风险与防护

| 风险 | 防护 |
|---|---|
| **漏改某个签发点**，用户 bump 后新 token 立即失效 | `generateToken` 版本参数设为必填（无默认重载），编译期强制 4 处全改；补「bump 后签发必须可用」单测 |
| Redis 回源 DB 把主库打满 | 仅故障期触发；DB 也可作为短缓存回填 Redis |
| afterCommit 写 Redis 失败 | DB 仍是真相，下次请求回源；只记日志 |
| 30 天 key 堆积 | 只按 userId 一个 key，不按 jti 展开；TTL 严格 30 天 |
| 改权限把用户踢下线（体验） | 版本语义只让旧 token 失效，可立即重登；不写黑名单 |
| `/auth/me` 与拦截不一致 | bump 后旧 token 立刻 401 → 前端重登 → 新 token 与 `/me` 一致，窗口收敛到一次重登 |

| `backend/src/main/resources/db/migration/V50__add_user_token_version.sql` | 新建：同语句，供 Flyway 重开后使用 |

| `util/JwtUtil.java` | `generateToken` 增加**必填**版本参数 + `ver` claim；`getTokenVersionFromToken`（无 claim 按 0）；`getDefaultExpirationMillis` |
| `service/AuthService.java`（2 处）、`CAuthService.java`、`ShareService.java` | 4 个签发点全部传 `user.getTokenVersion()` |
| `service/UserSecurityService.java` | 新建：`onAuthoritiesChanged(User/UUID)`、`revokeAll`，DB 在事务内、Redis 在提交后 |
| `service/CAuthService.java` | 游客升级注册（c_guest→c_user）接钩子 |
| `config/TokenRevocationService.java` | `isBlocked`（版本 + 双黑名单）、`cacheVersion`；Redis 异常回源 DB，DB 也不可用才拒绝 |
| `config/JwtAuthFilter.java` | 改用 `isBlocked`，命中写 **401 JSON**（不再匿名→403） |

### 上机后发现并修掉的两个问题

这两个是纸面评审和单测都发现不了的，只有真跑才暴露：

1. **版本缓存 TTL 设成 30 天 → 陈旧缓存压住新版本。**
   手工改库或 Redis 写失败后，旧缓存会让旧 token 继续放行、新 token 被误拒。
   改为 **60 秒**：正常路径仍在事务提交后主动写 Redis（秒级生效），60 秒只兜异常路径。
2. **`sendError(401)` 被容器 error dispatch 改写成 403。**
   401 触发 `/error` 再走一遍过滤器链，被 `anyRequest().denyAll()` 覆盖。
   改为直接 `setStatus(401)` + 写 JSON，并补了 `JwtAuthFilterTest` 锁住这个行为。

### 实机证据

```
登录                       → token ver=1，/auth/me 200
DB +1 且 Redis 同步（模拟权限变更）→ 旧 token /auth/me → 401 {"code":401,"message":"登录已失效，请重新登录"}
重新登录                   → ver=2，/auth/me 200
登出                       → 该 token /auth/me 401（jti 黑名单仍生效）
```

`mvn clean test` → **220 用例 / 0 失败 / 2 跳过**（新增 24 条：JwtUtil 5、TokenRevocation 10、UserSecurity 6、JwtAuthFilter 3）。

### 仍未做的（有意）

- 现在没有「改角色/停用账号」接口，所以 `onAuthoritiesChanged` 除注册升级外暂无调用点——接口落地时一行调用即可。
- Lua 合并、本地缓存、refresh token 均未做（不需要）。
- 已退役 token 的 `/auth/me` 返回 401 而不是刷新后的用户信息，前端会跳登录，符合预期。

## 11. 简化（同日，专家复审后）

复审结论：本机制今天防的是一个**尚未存在**的触发路径（全库没有改角色/停用接口），
但它同时补上了一个**今天真实存在**的缺口——token 被盗后无法按人踢下线（logout 只能撤当前 jti）。
因此保留方向，砍掉冗余：

| 删除 | 原因 |
|---|---|
| `auth:revoked:user:{id}` 用户级黑名单 | 与版本号重复：`revokeAll` 本来也会 bump 版本，版本号已覆盖（含 Redis 故障期从 DB 回源） |
| `revokeUser` / `revokeAll` | 零调用；「踢掉某用户全部设备」= 版本 +1，不需要额外 key |
| 每请求的用户黑名单 `EXISTS` | 每请求 Redis 从 3 次降到 2 次（版本号 + jti），与改造前持平 |

保留：`ver` claim、`token_version` 自增、jti 黑名单（登出）、Redis 异常回源 DB、60 秒版本缓存 TTL。

裁决：**简化保留，不回滚**。回滚后再加，等于在用户管理接口上线时重新动一次鉴权核心；
而现在这套只有两处 Redis 读，成本与改造前相同。
