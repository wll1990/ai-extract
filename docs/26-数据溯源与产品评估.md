## 一、数据全景图

```
                        ┌──────────────┐
                        │   user 表     │  姓名/角色
                        └──────┬───────┘
                               │ userId
                        ┌──────▼───────┐
    注册时自动创建 ──────→│  space 表    │  title / description / tags
    上传材料 ────────────→│              │
                        └──┬────┬─────┘
                           │    │ spaceId
                  ┌────────▼┐  ┌▼────────────┐
                  │ report  │  │  skill 表    │  状态: generating / active / failed
                  │ 六章JSON│  │  model_name  │
                  └───┬─────┘  └──────────────┘
                      │ reportId
           ┌──────────▼──────────┐
           │ experience_grain 表 │  ← 访谈完成 → AI 拆解
           │ scene_tag / expert_ │
           │ thought / script    │
           └─────────────────────┘
                      │
           ┌──────────▼──────────┐
           │ expert_skill 表     │  ← 管理员上传萃取师材料
           │ styleTags / industry│
           │ grain_count         │
           └─────────────────────┘

所有数据的最终源头 = 访谈 → AI生成报告 → AI拆解颗粒 → 人工上传萃取师
```

### 2. 分身广场 — "在线"和"锦囊"

| 维度 | 详情 |
|------|------|
| **前端** | `app/skills/page.tsx` → `listSkills()` |
| **API** | `GET /api/v1/skills/list` |
| **后端** | `SkillController` → `SkillService.listAllSkills()` |
| **"在线"数据源** | `skill.status` 列 → CHECK 约束: `generating / active / failed` → 默认值 `generating` |
| **"在线"怎么来的** | 种子数据直接设 `active`。API: `PUT /skills/{id}/status` 手动切。**无自动激活** |
| **"锦囊"数据源** | `grainRepository.findBySpaceId(skill.getSpaceId()).size()` — 统计该空间的 `experience_grain` 行数 |
| **"锦囊"怎么来的** | 报告生成时 `extractExperienceGrains()` 调 AI 拆解 grains → `grainRepository.save()` |
| **ownerName 怎么来** | skill.spaceId → space.userId → user.name |
| **ownerTitle 怎么来** | `space.description` |

### 6. 萃取师经验库 — 卡片

| 维度 | 详情 |
|------|------|
| **前端** | `app/admin/experts/page.tsx` |
| **API** | `GET /api/v1/admin/experts?page=1&size=20` |
| **后端** | `ExpertService.getExperts()` → `ExpertSkillRepository` → `toListResponse()` |
| **卡片字段源** | |

| 卡片字段 | DB 列 | 怎么来的 |
|----------|------|----------|
| 名称 | `expert_skill.name` | 上传时管理员填写 |
| 状态 | `expert_skill.status` | pending→analyzing→extracting→active |
| 风格标签 | `style_tags` (JSONB) | 上传表单多选 |
| 行业标签 | `industry_tags` (JSONB) | 上传表单多选 |
| 来源 | `source_type` | 上传时硬编码 `"document"` |
| 法则数 | `grain_count` | `expert_grain` 表按 expert_id 计数，反规范化存储 |

**状态流转:**
```
pending (上传时)
  → ExpertAnalysisScheduler 每30秒扫描
  → analyzing (AI 解析文档)
  → extracting (报告生成完)
  → 管理员点"审核法则" → active
```

### 7. 场景地图

| 维度 | 详情 |
|------|------|
| **前端** | `app/admin/coverage/page.tsx` → `getSceneCoverage()` |
| **API** | `GET /api/v1/admin/scene-coverage` |
| **后端** | `AdminController.getSceneCoverage()` |
| **数据源** | `experience_grain` 表全量 → Java Stream groupBy(sceneTag) |
| **9个场景标签** | **硬编码**在 AdminController: 破冰、异议处理、逼单、竞品博弈、信任建立、决策链渗透、价格谈判、转介绍、高层拜访 |
| **reportCount** | `grains.map(getReportId).distinct().count()` — 去重报告数 |
| **充足/空白判断** | ≥3 份报告 = sufficient(充足) / 1-2 = moderate(一般) / 0 = empty(空白) |
| **scene_tag 怎么来** | AI 拆解 grains 时返回的 `sceneTag` 字段 → 存入 experience_grain.scene_tag |
| **AI 约束** | `grain_extraction.md` prompt 建议"破冰""异议处理""逼单""信任建立"但不强制 |

## 三、商业化产品评估

### 3.1 工作台 — 最新报告

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 快速访问最近生成的内容 |
| 有意义？ | ⚠️ 缺作者名和场景标签，不知道是谁的、什么场景的 |
| 改进 | 每条加上作者名 + sceneTag 徽章，改名"最近萃取成果" |

### 3.2 分身广场

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ "在线"是核心状态，"锦囊数"反映知识库丰富度 |
| 有意义？ | ⚠️ "在线"目前只有种子数据是 active。**新访谈完成→报告生成→grains 拆解后，skill 不会自动激活** |
| 改进 | **P0: 补自动激活逻辑** — 报告生成完成后自动将 skill.status 从 generating 切为 active |

### 3.3 空间总览

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 报告数告诉管理员谁有内容；分身状态告诉管理员谁能被提问 |
| 有意义？ | ✅ 管理员一眼看出团队知识资产分布，决定给谁安排访谈 |
| 改进 | 状态已修复为真实数据 ✅ |

### 3.4 经验广场

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 关键词搜索是刚需，场景标签筛选有业务价值 |
| 有意义？ | ⚠️ 搜索只覆盖标题+副标题，搜不到报告正文里的案例和方法论 |
| 改进 | **P1: 搜索扩展到 content_json 全文检索** |

### 3.5 分身管理

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 激活/未激活分开展示，状态切换按钮清晰 |
| 有意义？ | ✅ 管理分身生命周期的核心页面 |
| 改进 | 原"场景覆盖概览"已移除 ✅ |

### 3.6 萃取师经验库

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 卡片上 name/status/style/industry/grain_count 都是核心管理信息 |
| 有意义？ | ✅ 管理员需要判断萃取师质量、决定是否激活 |
| 改进 | 无需改动，产品逻辑完整 |

### 3.7 场景地图

| 评估 | 结论 |
|------|------|
| 合理？ | ✅ 9 个场景标签覆盖销售全流程，覆盖率视图直观 |
| 有意义？ | ✅ 管理员一眼看出哪些场景缺乏经验，针对性发起萃取 |
| 改进 | ⚠️ 硬编码的 9 个标签与 AI 自由生成的 scene_tag 可能不一致。应统一约束 |

## 四、改进优先级

| 优先级 | 问题 | 影响 | 改动范围 |
|--------|------|------|----------|
| 🔴 **P0** | skill 从 generating→active 无自动触发 | 正常流程下分身永远不"在线" | 后端: ReportGenerationService 加一步 |
| 🟡 **P1** | 搜索不支持全文 | 搜"逼单技巧"找不到报告里逼单的案例 | 后端: ReportRepository 加 JSONB 查询 |
| 🟡 **P1** | 场景标签硬编码 vs AI 自由生成不一致 | 场景地图数据可能遗漏或分散 | 后端+Prompt: 统一标签枚举 |
| 🟢 **P2** | 工作台报告卡片信息太少 | 看不出是谁的、什么场景 | 前端: page.tsx 显示 authorName + sceneTag |
