# 三人团队共享资料与Agent协作：方案对比与选型

日期：2026-11-13。状态：已补充代码与接口审核，执行建议以第10节为准；未部署，DSH运行配置和真实业务效果尚未验收。

> 审核更新：第10节将方案C细化为“现有平台最小资料入口＋独立团队任务层＋DSH官方SDK执行服务＋现有飞书桥的独立团队路由”。不把社区插件、共享云盘、文件自动回存或默认SDK能力视为已经解决。第1—9节保留方案比较，第10节是进入实现的执行建议；第一步先验收DSH运行组合，失败则停止该适配器投入，不同时铺开其他引擎。

本文是当前方案讨论入口。前面的Pi、Codex、自建工作台和云端讨论分别属于不同层次，不表示四套方案全部实施。产品完整目标见[功能与交互清单](团队协作工作台-功能与交互清单.md)；自建工作台的细节见[端到端流程与技术设计](团队协作工作台-端到端流程与技术设计.md)。后两份文件作为方案D的设计储备，不再表示必须先自建工作台才能协作。

## 1. 需求基线

三个人异地工作，已经使用Codex、Grokbot等成品工具，希望共用客户资料、历史案例、课程知识、Skill和脚本，完成查资料、生成大纲/方案/详细内容、多轮修改、共享成果与接力。未来可能接入更多工作方法、IM和流程。

当前先解决：资料找得到、方法可复用、成果自动或明确回存、别人可继续。暂不以自动长期记忆、所有执行器、复杂多Agent或流程画布作为前置。课程是第一个场景，文件和任务结构保持通用。

## 2. 四种完整方案

| 项目 | A 共享文件＋现有Agent | B 现成团队云Agent | C 自托管Harness＋IM | D 自建团队工作台＋执行器 |
|---|---|---|---|---|
| 基本组合 | 共同文件库＋各自现有APP | 团队文件库＋Grok Team Bot等产品 | 云主机DSH＋飞书/企业微信机器人＋文件库 | 现有销冠平台增加团队模块，后接Codex/Pi/DSH之一 |
| 日常入口 | 文件库、各自APP | 成品云Agent界面，或其支持的消息入口 | 飞书/企业微信；Harness网页辅助管理 | 自有Web，后续接IM |
| Agent运行位置 | 各人电脑或各自产品云端 | 供应商云端 | 我方云主机 | 我方执行服务或获支持的远端环境 |
| 文件共享 | 共享库；APP能否直接读需验证，否则同步/下载 | 通过共享文件或连接器，需明确授权 | 将项目文件挂载/同步到执行目录，结果回存 | 自建上传、版本、预览、检索、成果管理 |
| 上下文 | 各APP独立管理 | 产品原生会话；成员私聊未必共享 | Harness管理会话，IM消息映射到项目/话题 | 所选执行器管理；平台保存任务事实与版本 |
| Skill/脚本 | 原包共享，各环境安装测试 | 按产品支持导入，依赖和兼容性需验证 | 固定版本加载，云端安装依赖并隔离执行 | 自建登记、测试、发布，交执行器加载 |
| 开发量 | 最低，主要是协作规则 | 低，主要是账号/授权/配置 | 中，需要部署、渠道接入、状态保存和文件交付 | 最高，需要前后端和执行集成 |
| 成本构成 | 现有订阅＋文件存储 | 团队产品订阅/用量＋文件存储 | 云主机/备份＋模型API＋运维 | 开发维护＋执行/模型/存储 |
| 最适合 | 马上统一资料、保留使用习惯 | 已有可用团队产品，希望少运维 | 想直接在IM干活，希望自己控制资料和方法 | 明确要产品化权限、检索、版本和流程 |
| 主要缺口 | 手工交接较多，会话各自独立 | 受产品共享、配额和接口限制 | 预览框架/社区插件需验证，多人权限不是天然完整 | 容易过度建设，首条业务闭环投入大 |

以上开发量是相对判断，不是工期或报价承诺。三个人的规模不能单独决定服务器规格，实际取决于任务并发、脚本内存、文件大小和模型等待时间。

## 3. 方案A：先把文件与方法集中

做法：选一个三人都能稳定访问的共享文件库，统一项目目录、任务说明、当前进度、资料清单、Skill原包和成果文件名。各自工具读取授权材料，输出后同步/上传回共同目录。

优点：不要求迁移现有Agent习惯，立即能暴露文件和方法规范的问题。限制：能共享文件不等于APP自动连接文件库，不能保证自动回存或直接接力别人的会话；下载、同步、回存和版本确认需要验证或人工完成。

适用定位：它也可以作为B/C/D的共同文件基础，不必作为一个需要长期停留的最终产品。

## 4. 方案B：现成团队云产品

以用户常用的Grok Bot为例，使用其Team Bot共享方法和配置，再连接团队文件库。三人用独立账号，按产品授权访问共同资料。

已核实边界：官方文档提供Team Bot、共享Skills/Files和连接器；每个人与Team Bot的私聊独立，使用的云端电脑也不一定相同。不能把某人私聊附件或个人云端目录当成所有成员都能读的共享项目。生成成果应显式回存共同文件库。

要验证：团队功能是否对现有账号/套餐可用；三人是否能读取同一份资料；生成和修改文件能否稳定回存；现有Skill、Python脚本依赖是否可用；能否通过项目说明和当前稿接手，而非重复讲背景。

重要区别：这是直接使用一个云产品，不等于我们可以把它的全部执行内核、桌面操作和私有插件嵌进自己的平台。

## 5. 方案C：自托管DeepSeek Harness＋IM

```text
三人的飞书/企业微信
        ↓
IM桥接：身份、去重、项目/会话路由、任务反馈
        ↓
云主机上的DeepSeek Harness（DSH）
  ├─ 模型API
  ├─ Skill、MCP和Python工具环境
  ├─ 持久化会话/配置
  └─ 项目目录、输出目录
        ↓
团队文件库/OSS：原件、成果版本与备份
```

DSH是执行框架；DeepSeek模型是可配置的模型服务，两者分开。采用模型API时，不需因运行Harness而部署GPU。云主机负责进程、文件和脚本；并非把框架托管到飞书/企业微信平台。

官方仓库包含Web入口、会话、文件、Skill、MCP、压缩等模块，但当前仍为Developer Preview。IM已有社区桥接项目，不能把插件README的支持清单等同于本团队端到端验收完成。

首个验证建议只接飞书一个渠道；若团队主要使用企业微信，则替换该入口，不同时接两套。可以评估社区插件或复用现有feishu-bot桥，选择一条接入路线，不重复建设。现有飞书桥主要等待后端答案，长任务需改为先确认收到，再后台执行并回传状态/成果。

最小操作：查资料、按一个Skill生成、继续修改、状态/停止、回传成果。不把IM上传自动归类、复杂审批和自定义流程作为前置。

必须补的基础：

- 锁定Harness与插件的验证版本；会话/配置/成果放持久盘并备份。
- 限定三名成员及指定项目群。社区插件可能默认允许群内所有@者执行，必须验证并补齐白名单，不能依赖提示词限制权限。
- 项目群/话题与目录、会话明确对应；不同项目不混上下文，同一项目写入串行。
- 模型Key独立配置，资料原件只读，脚本环境与业务主机隔离。
- 任务先回执，再异步执行；成功必须真实保存并交付文件，发送失败有明确状态。
- 文件仍有版本、任务说明和当前进度，不能把上下文压缩当作长期资料管理。

适用定位：不先开发完整网页，就验证“通过聊天完成真实工作”。它不会自动提供完整多租户、成果审批或企业知识库管理。

## 6. 方案D：自建工作台，嵌入执行器

现有Java/Next.js/PostgreSQL/OSS继续使用，增加团队资料、任务、成果和权限模块；执行器通过独立服务接入。先接一个，不让三套引擎成为首版前置。

执行器候选不是四个完整产品方案：

| 候选 | 接入方向 | 当前应如何看待 |
|---|---|---|
| Codex | 官方SDK/App Server | 团队已有使用基准，适合优先做熟悉任务的接入验证；Python可用于执行服务 |
| Pi | SDK/RPC | 可加载Skill、调用脚本、管理会话；仍要验证选定模型与工具组合的业务效果 |
| DSH | 插件、SDK或相应服务接口 | 可作为C的执行基础，也可后续适配自有Web；按锁定版本验证 |
| Spring AI＋模型 | 平台自己组织调用、工具与上下文 | 适合范围明确的固定文本/RAG任务；不自动等同于完整文件Agent |

Python是脚本/服务语言，可承担文件解析、处理与导出，不与上述执行器互斥。选Pi或DSH不意味着Python脚本必须改成TypeScript；反过来，选Python也不自动获得成熟会话管理。

资料、任务要求、Skill原包和成果版本独立于引擎保存。以后可扩展适配器，但不承诺不同引擎原生会话、隐藏状态或APP专属能力无损迁移。旧的自建流程/API设计仅在确认进入方案D时逐项实施。

## 7. 当前建议：一个文件基础，优先验证一条聊天执行链路

建议顺序：**先统一方案A中的资料和交接规则，再用方案C做一个小范围技术验证。** 这是当前建议，不表示用户已经批准部署或购买服务。

选择C作为当前验证重点的理由：最近需求明确偏向IM聊天干活、复用真实Skill/Python和共享文件；DSH已有相关模块及社区渠道接入，可以先验证，不急于造完整Web。

方案B是少运维的替代路径：如果团队现有Grok Bot账号已具备共享及文件回存能力，可先试B；不必同时采购、部署B和C。若DSH兼容性/效果未通过，也不强行围绕它开发平台。

方案D在出现明确缺口时再推进，例如：文件版本经常混乱、需要精确RAG引用、成员权限超出IM能力、多个客户/企业隔离、固定审批/流程、交付看板。已经产出的技术设计可复用，不需要现在全部实现。

整个过程以资料和成果连续保存为共同基础，不把一次引擎选择变成不可撤回的系统绑定。

## 8. 统一验收故事与通过条件

准备一个客户项目、若干客户资料/案例、一个真实课程Skill、三名成员。无论选B/C/D，都用同一个故事验收：

1. A上传客户需求并确认目标、受众、时长及限制。
2. B查找并选定案例，生成大纲V1，保存回共同位置。
3. A连续提出修改，产生V2/V3，硬约束仍被遵守。
4. C根据任务说明、当前进度和确认版大纲接手，生成详细内容。
5. 只修改一个模块，其他模块保持；旧版可回看。
6. 关闭客户端、隔天或服务重启后，资料/已保存成果仍可读，会话可恢复或明确提示如何接续。
7. 重复消息不重复执行，失败/停止有状态；生成与回传成功分别确认。
8. 未授权成员或错误群不能读取、执行或下载；同项目并发写不覆盖成果。

记录每一步：是否自动、需要哪些人工动作、实际耗时、输出是否合格、模型用量及故障。只验证连通和机器人能回复，不足以决定选型。

## 10. 高级技术审核：进入实现的执行基线

### 10.1 审核结论与证据等级

建议实施方案C的修订版：现有平台提供最小资料/成果入口，飞书作为日常任务入口，独立Python worker通过DSH官方SDK执行任务。先支持本团队三名成员，一个飞书机器人，全局一次执行一个生成任务；其他任务排队。企业微信、类Codex网页聊天和其他执行器不进入第一条链路。

这不是“部署DSH就完成团队协作”。DSH负责原生Agent循环；资料授权、任务账本、输入版本、成果发布和消息投递需要我们实现。技术路径可以进入实现，不代表运行验收已通过。

证据标记：**代码事实**是本仓库已有代码；**本地实测**是本次实际执行的检查；**上游契约**是官方/插件文档声明；**待实现**是我们必须编写和验收的部分。

| 证据 | 发现 | 直接影响 |
|---|---|---|
| 代码事实 | `feishu-bot/src/bridge.js:24`等待后端SSE聚合，超时200000ms | 长任务需先持久化受理，再异步完成和投递，不能只延长HTTP超时 |
| 代码事实 | `ImInboundService.java:87`把bot绑定到销售分身；`:164`群聊使用messageId生成不同身份 | 新团队机器人走独立路由与任务会话，不能原样复用销售chat() |
| 代码事实 | 现有Redis去重/nonce在异常时有fail-open逻辑 | 运行任务必须以数据库唯一键防重；Redis不能承担唯一执行保证 |
| 代码事实 | `FileStorageService`保存OSS原件；`FileParseService`取回纯文本 | 复用存储/解析基础，补团队文件版本和结构；不能把OSS对象直接当共享文件夹 |
| 本地实测 | 用当前`ai-service/routers/internal.py:_parse_local`解析含段落与表格的临时DOCX：段落保留、表格未保留、未报人工处理 | DOCX表格解析属于资料链路上线前修复项，不能标“全部资料已读” |
| 上游契约 | DSH Python SDK可驱动子进程；`sdk`与`sdk-minimal`的插件组合不同，后者不等于完整Skill环境 | 固定`profile=sdk`作为验证目标，核对有效配置与实际工具；不能只复制minimal示例 |
| 上游契约 | 官方SDK恢复要求匹配持久存储与会话；恢复会话不等于恢复外部进程 | 新任务新会话，修改原任务续用；重启时中断运行明确标识，不盲目自动重跑 |
| 上游契约 | 社区IM插件README写明群内准确@即可下任务，且文件交付范围不天然等于项目授权范围 | 首条链路采用自有渠道准入与文件发布，不把插件直接作为权限边界 |
| 本地实测 | 当前PATH未发现dsh；当前Python未安装DSH SDK/runtime；终端访问GitHub的DNS失败，浏览工具能读上游文档 | 没有执行过DSH的安装/启动/模型调用，不能宣称云部署或SDK兼容已通过 |
| 用户确认 | 真实课程Skill在另一名同事电脑上 | 需要实际业务包才能验收；仓库中的graphify/hallmark不是课程能力替代品 |

上游主分支和文档会变化。本审核没有把不同抓取日期的页面拼成一个“确定版本”：准确SDK版本、runtime版本、profile和插件清单由G0实际安装后锁定，记录锁文件与构建摘要，不用`latest`上线。

### 10.2 首版范围与明确的入口

前端新增`/team-workspace`：工作区列表、资料上传/列表、文件详情/解析正文/下载、成果版本、任务状态。无需先做网页对话、Office在线编辑或用户定义流程。

日常执行走一个专用飞书应用机器人。现有销售机器人继续原路由；团队机器人不绑定销售Skill、不调用销售chat()、不使用其模型Key。

资料首批保证TXT/MD、DOCX（含常见表格）、文本PDF。扫描PDF明确提示未OCR；其他格式先保留下载，不宣称可检索。原件20MB和解析文本100000字符沿用当前默认限制，界面显示限制，超出拒绝且保留可处理的错误信息。

“查资料”第一批明确指：授权资料的文件名/分类/正文关键词搜索，返回匹配段落及章节读取。它不是完整语义RAG。已有完整目标中的向量检索作为后续独立任务，需新team块索引和单独embedding配置；不能混查销售知识或把当前功能标成已完成RAG。

### 10.3 数据与文件只有一套权威来源

```text
浏览器资料页 → Java团队模块 → PostgreSQL＋OSS
飞书 → 现有桥的团队分支 → Java团队任务模块
                                ↓ DB任务＋租约
                        独立Python执行服务
                                ↓ stdio SDK
                       隔离环境中的DSH
                                ↓
                    候选文件→校验→OSS→成果版本
                                ↓
                  持久投递记录→飞书回复/成果链接
```

业务元数据和执行状态在数据库，原件/发布成果在OSS；runner目录是处理副本，不给三人直接同时修改这个目录。没有“网盘、OSS和容器目录各自更新然后自动同步”的隐含步骤。

上传：成员鉴权→保存不可变原件→创建版本/解析job→返回状态→worker解析并保存正文。新版不覆盖旧版。下载与正文读取检查成员，不把OSS设为公共读。

运行目录建议：`projects/{workspaceId}/tasks/{taskId}/input、work、output、skills`；原件和选定Skill只读，work/output可写。持久Harness home与任务ID登记在受控状态目录。具体home和sessionId恢复能力必须在G0验证；不能让两个进程同时写同一home/session。

成果发布不依赖模型说“已保存”：我们分配run输出目录和允许交付的文件名，验证文件存在、realpath位于输出目录、不是符号链接、大小/类型合法；计算hash，上传OSS并提交版本后才显示“已保存”。禁止从回复文本猜任意绝对路径并下载发送。

### 10.4 完整操作契约

1. 管理员创建工作区，添加三名现有账号，并登记每人的飞书身份（应用范围内的用户标识），绑定专用群。应用身份与平台用户映射须服务端保存，显示名不作为身份。
2. A在资料页上传需求和案例，查看解析正文，确认表格/关键要求完整。上传进团队资料不是自动进入销售知识库。
3. 管理员在资料页为当前工作区登记首个已验证Skill和允许的模型配置；B创建任务，填写要求，选择具体资料版本。首版该步骤放网页，避免让IM猜文件或版本。
4. 任务绑定到项目群；`/task <taskId>`仅选择属于该群工作区且有权限的任务。首版一个群一个当前任务，切换时回显标题/ID；运行期间拒绝切换。普通@消息进入当前任务，无任务时提示去网页创建。
5. IM入口验证bot、群、成员和任务；以`channel+botId+messageId`数据库唯一键保存用户输入和run，提交后回复任务ID/排队状态。同消息重复到达返回已有任务，不重复调用模型。
6. Python worker领取租约，下载本轮固定版本输入及Skill；新任务创建原生会话，续改恢复登记的会话。每轮明确提供任务要求、当前成果版本和本轮指令；历史/压缩由经验证的DSH配置管理，不额外灌全部旧稿。
7. SDK通知转成公开步骤和文本事件存库；不暴露隐藏推理或凭证。全局并发1，同任务新消息在上一轮结束后顺序执行。
8. 候选成果经文件/格式检查后发布成新版本。模型结束但没有约定文件、输出截断或检查失败，记录失败/不完整，不将其设为当前稿。
9. 发布后建立独立投递记录，飞书发送摘要和需登录的成果链接。首版不依赖飞书文件附件权限，原文件可从资料页下载；原生附件发送可后补。执行成功而发送失败只补投递，不重新生成。
10. 修改仍在原任务，绑定明确基准版本；`/status`显示执行/保存/投递状态；`/cancel`只允许发起者/工作区owner，停止对应任务进程组，保存终态。正在编辑的文件只作partial候选，不覆盖已发布版本。

`/task、/status、/cancel`由网关程序解析，不交模型决定。问题和要求冲突返回澄清；不在首版开放任意外部系统写操作。后续如需运行时审批，再单独验证SDK请求/响应协议和消息卡片。

大纲第一批按完整小稿生成候选；详细内容按模块/章节生成。修改模块B时仅收集B的输出并合并，其他模块沿用基准版本，后台核验hash。全局时长/结构变化先更新任务要求，再明确重做哪些模块。

### 10.5 最小数据与接口

逻辑表建议（可按已有通用能力合并，不能省略语义）：工作区/成员、资料/资料版本、真实Skill版本、任务、消息、运行/事件、成果版本、IM群路由、投递记录。任务保存已确认要求和当前成果指针；run保存资料/Skill/模型配置快照、lease owner/epoch、native session引用、错误与usage。

新增接口建议，均为待实现契约：

| 接口 | 返回/约束 |
|---|---|
| `POST /api/v1/team/workspaces/{id}/assets` | 原件保存结果、版本ID、解析状态 |
| `GET /api/v1/team/workspaces/{id}/assets` | 成员可见列表/分类/关键词过滤 |
| `GET /api/v1/team/asset-versions/{id}/content`、`/download` | 正文/定位或鉴权下载 |
| `POST /api/v1/team/workspaces/{id}/tasks` | 明确要求、Skill和资料版本；返回taskId |
| `POST /internal/team-im/messages` | 沿用HMAC验证，独立团队路由；快速返回已有/新runId及状态 |
| `POST /internal/team-runs/claim`、`/{id}/heartbeat`、`/events`、`/complete` | runner专用认证、租约和epoch，拒绝旧worker回写 |
| `GET /api/v1/team/tasks/{id}`、`/runs/{id}` | 状态、版本和公开记录 |
| `POST /api/v1/team/runs/{id}/cancel` | 鉴权、持久取消请求，以实际停止结果为准 |

worker凭证只允许领取指定团队任务和读取其清单内文件，不是业务数据库账号或全OSS密钥。不能把HTTP请求的ThreadLocal当后台身份。代码修改范围：新增Java team模块、最小资料页、Python runner子工程；现有飞书桥新增明确团队路由，销售路由保留。

### 10.6 恢复、幂等与部署边界

- run状态：queued→preparing→running→succeeded/failed/interrupted/cancelled；成果发布和消息投递另有状态，不混作一个“成功”。取消与完成用DB原子条件确定终态。
- worker失联超过租约标interrupted并隔离旧epoch；先确认旧执行进程停止后才能重试。重试新attempt，不承诺任意脚本断点续跑。
- 发送接口可能出现“已发送但回执丢失”，不能承诺端到端严格只发一次；使用投递记录、平台能力和状态核对避免盲重发。确定失败的消息可有界退避重试。
- DSH在独立执行环境运行，源码/业务磁盘/数据库凭证不挂入；只接内部受信任Skill。工作目录不等于OS沙箱，多租户和任意不可信代码执行不在三人首版范围。
- 云端采用专用Linux运行环境、持久数据卷、进程托管和备份；首次上线需要做一次恢复演练。DSH原生Web先仅供管理员受控访问，不把它当现成三人登录和权限系统。
- 模型Key使用团队独立配置，不回退销售Key。Python脚本所需依赖锁定；不允许Agent在运行中任意升级Harness或插件。扩展MCP只加载已验证服务，平台权限仍由服务端检查。

### 10.7 可直接拆开发任务的顺序

| 编号 | 具体交付物 | 完成标准/失败处理 |
|---|---|---|
| G0 执行器验证 | 一个独立DSH标准sdk配置、锁定版本清单、运行样例、日志和费用记录 | 真实Skill、文件处理、一个MCP、连续修改、压缩和重启恢复通过；未通过不建设它的业务适配器，也不宣称已选型 |
| T1 资料入口 | 工作区成员/文件版本API与最小页面 | 三人可上传/读/下载；第四人拒绝；原件不覆盖，失败状态清楚 |
| T2 解析完整性 | DOCX段落/表格按顺序输出，PDF页定位、可读取状态、正文搜索 | 用对照样本核对，扫描件不假就绪，当前表格漏失复现转为通过 |
| T3 任务账本 | 创建任务、输入快照、消息去重、持久job/租约、状态API | 重复消息只有一个run，worker中断终态明确，旧worker不能提交 |
| T4 Python执行服务 | 通过官方SDK领取/续接/停止/保存产物 | 任务ID与原生会话固定，执行目录受控，真实文件上传成功，不访问销售数据 |
| T5 飞书接入 | 专用团队bot路由、成员映射、任务选择、回执/状态/完成投递 | 三人同任务接续；未授权群/成员拒绝；执行超过200秒仍可完成并回传 |
| T6 成果修订 | 不可变版本、基准检查、模块合并、确认/下载 | 人工改稿与Agent改稿冲突返回409；非目标模块hash不变 |
| T7 联调与试用 | 三人真实项目记录、失败演练、备份恢复记录 | 下列验收逐条出证据，再决定是否投入长期使用 |

可并行准备T1/T2的数据契约和样本，但G0失败时不投入T4/T5的DSH专属实现。若后续必须换执行器，保留资料、任务和成果契约，只重做适配层；不承诺迁移原生会话内部状态。

### 10.8 G0所需输入与首轮验收

同事提供一个**独立Skill包**：`SKILL.md、实际引用的scripts/references/assets、依赖及版本、一次成功输入和期望输出`。不需要导出其全部个人配置、历史聊天或凭证。引用个人绝对路径、专属APP工具、浏览器登录态的地方单独列为迁移问题；不能将课程内容专业性用通用演示Skill替代。

执行还需要：验证用Linux环境、获授权的模型API与预算、飞书测试应用及三名成员身份（T5）、若干已授权样本文件。当前尚未提供这些运行条件，不将其假定为已经可用。SDK与模型必须从可访问的发行渠道安装验证，不能仅据master文档给出“已锁定版本”。

验收条目（记录输入、run/session ID、版本、文件hash、状态和人工判断）：

1. 指定资料检索命中与原文定位正确；DOCX表格内容保留。
2. 用真实Skill生成符合期望结构的大纲和至少一个详细模块，有实际文件。
3. 同任务连续约20轮修改，保留受众/时长/禁用内容；明确引用早期意见时能够读回对应记录。
4. 实际触发一次上下文压缩并继续修订，原始记录和确认要求仍可追溯；不能只把触发阈值设大而避开验证。
5. B接手A的任务后无需复制全部聊天；成员发言身份保留，当前版本明确。
6. 任务运行超过200秒，飞书仍有回执和最终状态；HTTP/IM断线不自动重生成。
7. 成功后重启服务，已保存文件hash一致、会话可接续；运行中重启标interrupted，不能假完成或静默重复脚本。
8. 同消息投递三次只调用一次模型；同任务并发修改排队，基准过期不覆盖。
9. 模型失败不发布完整稿；成果已保存但飞书投递失败时补投递而不重生成。
10. 未授权成员/群、其他工作区文件路径、符号链接产物访问均拒绝；备份可恢复到独立目录并读取。

G0优先覆盖2—4及7的执行器部分；其余随T1—T7逐项验收。人工课程质量另由团队按实际业务样例确认，模型“任务完成”或程序退出码不是专业质量金标。
