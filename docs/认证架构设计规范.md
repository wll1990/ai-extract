# 多应用认证架构设计规范

## 适用场景

同一个后端服务同时支撑多个前端应用（如管理后台 + 用户端平台），
各应用有独立的用户体系和身份凭证，但共享同一域名。

## 核心原则

> **每个应用独立掌控自己的身份凭证，不存在隐式的跨应用认证通道。**

```
❌ 错误：Cookie(token) → JwtAuthFilter → SecurityContext  ← Bearer 和 Cookie 共用一个认证入口

✅ 正确：Cookie("token") → middleware → 路由门禁（仅 B 端页面入口）
         Bearer header     → JwtAuthFilter → 身份认证（所有 API 唯一通道）
```

## 一、问题清单（踩过的坑）

| # | 现象 | 根因 | 严重度 |
|---|------|------|:--:|
| 1 | 平台端游客看到 B 端用户的对话历史 | JwtAuthFilter Cookie 兜底把 B 端身份带入了 C 端请求 | 高 |
| 2 | 游客发证拿到 B 端用户的 userId | Cookie 认证污染 SecurityContext → currentUserIdOrNull 返回 B 端 userId | 高 |
| 3 | 平台端专家名片页跳到登录 | middleware 白名单缺 `/skill/`，之前靠 Cookie 泄露混过 | 中 |
| 4 | 平台端 API 调用全断 | 撤 Cookie 后 apiClient 无 Bearer 回退，之前靠 Cookie 兜底 | 高 |
| 5 | 多处原生 fetch 硬编码 credentials:'include' | 不走统一 apiClient，各自裸调 fetch | 中 |
| 6 | 游客剩余额度显示不一致 | 两个地方用了不同的计次方法（当日 vs 全量） | 低 |
| 7 | 游客拦截逻辑双份实现 | QueryGate 迁移后 ChatStreamService 旧代码未清理 | 低 |

## 二、架构设计

### 2.1 Token 职责分离

```
┌─────────────────────────────────────────────────────┐
│                    Token 体系                        │
├──────────────┬──────────────────┬───────────────────┤
│   B 端 JWT   │   C 端 JWT       │   合作方 JWT       │
│ role: admin  │ role: c_guest    │ role: c_partner   │
│ companyId    │ (无 companyId)   │ appId claim       │
├──────────────┼──────────────────┼───────────────────┤
│ localStorage │ localStorage     │ URL ?token=       │
│ key: "token" │ key: "c_auth"    │                   │
├──────────────┼──────────────────┼───────────────────┤
│ Bearer 传输  │ Bearer 传输      │ Query param 传输  │
└──────────────┴──────────────────┴───────────────────┘
```

### 2.2 认证过滤器设计

```java
// JwtAuthFilter.extractToken() — 只认显式传递的 token
private String extractToken(HttpServletRequest request) {
    // 1. Authorization: Bearer <token> — API 调用唯一通道
    String authHeader = request.getHeader("Authorization");
    if (authHeader != null && authHeader.startsWith("Bearer ")) {
        return authHeader.substring(7);
    }
    // 2. ?token= — SSE/WebSocket 等无法设 header 的场景
    return request.getParameter("token");
    // ❌ 不再有 Cookie 分支
}
```

### 2.3 Cookie 的定位

```
Cookie 仅用于 Next.js middleware 做路由门禁（"有没有登录"），
不进入后端认证流程（"你是谁"）。

登录 → setTokenCookie()  ← 保留，种 Cookie 给 middleware 用
退出 → logout()          ← 保留，清 Cookie
API  → JwtAuthFilter     ← 不读 Cookie，只认 Bearer
```

## 三、前端规范

### 3.1 统一 API 客户端

```typescript
// apiClient.ts — 所有 API 调用的唯一入口
export async function apiClient<T>(path: string, options: RequestInit = {}): Promise<T> {
  const headers: Record<string, string> = {};
  // ... Content-Type ...

  // 自动从 localStorage 补齐 Bearer token
  if (!headers['Authorization']) {
    const token = getToken();  // localStorage.token || localStorage.c_auth
    if (token) headers['Authorization'] = `Bearer ${token}`;
  }

  const res = await fetch(`${API_BASE}${path}`, { ...options, headers });
  // ❌ 没有 credentials:'include'
  // ... 统一错误处理 ...
}
```

### 3.2 禁止事项

```typescript
// ❌ 禁止：原生 fetch + credentials:'include'
fetch('/api/xxx', { credentials: 'include' })

// ❌ 禁止：原生 fetch 不设 Authorization header
fetch('/api/xxx')

// ✅ 正确：走 apiClient，自动带 Bearer
apiClient('/api/xxx')

// ✅ 正确：特殊场景（FormData/Blob）手动带 Bearer
fetch(url, {
  method: 'POST',
  body: formData,
  headers: { Authorization: `Bearer ${getToken()}` },
})
```

### 3.3 登录/注册页

```typescript
// 登录成功后同时做两件事：
// 1. 存 localStorage（给 apiClient Bearer 用）
// 2. 后端种 Cookie（给 middleware 路由门禁用）
const resp = await fetch('/api/v1/auth/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ account, password }),
  // ❌ 没有 credentials:'include'
});
const data = await resp.json();
localStorage.setItem('token', data.data.token);  // 存给 apiClient
// setTokenCookie 在后端 AuthController 中完成
```

### 3.4 middleware 配置

```typescript
// 公开路径：任何人都能访问
const PUBLIC_PREFIXES = ['/', '/discover', '/skill/', '/s/', '/h5/'];

// 需要登录的路径：检查 Cookie（仅路由门禁，不含身份信息）
export function middleware(request: NextRequest) {
  if (PUBLIC_PREFIXES.some(p => pathname.startsWith(p))) {
    return NextResponse.next();  // 公开页面放行
  }
  const token = request.cookies.get('token');
  if (!token?.value) {
    return NextResponse.redirect('/login');
  }
  return NextResponse.next();
}
```

## 四、代码审查检查项

新增或修改认证相关代码时，逐项检查：

| # | 检查项 | 说明 |
|:--:|------|------|
| 1 | `credentials:'include'` | 项目全局 grep，必须为零 |
| 2 | 原生 `fetch()` 调用 | 是否设了 Authorization header？不走 apiClient 就必须手动带 Bearer |
| 3 | `extractToken()` 是否读 Cookie | 后端认证过滤器禁止从 Cookie 取 token |
| 4 | 新增 permitAll 路径 | middleware 白名单是否需要同步更新？ |
| 5 | 游客/c_user 接口 | 是否通过 Bearer 正确传递 userId？验证不会串到 B 端身份 |
| 6 | 登录/注册响应 | response body 是否包含 token？前端是否正确存入 localStorage？ |
| 7 | 重复逻辑 | 是否有迁移后遗留的旧代码（如双份拦截）？ |

## 五、部署后验证

```
1. B 端登录 → 页面刷新 → 所有功能正常
2. B 端登录后，同一浏览器打开平台端分享页 → 游客聊天 → 看历史对话 → 只有游客自己的
3. 游客聊满额度 → 弹注册 → 注册成功 → 历史继承 → 额度重置
4. 平台端发现页 → 专家名片 → 可正常浏览（无需登录）
5. H5 移动端页面 → 登录/注册/聊天 → 全部正常
6. grep -rn "credentials.*include" frontend/src/ platform/src/ → 零结果
```

## 六、一句话总结

**Cookie 管"能不能进这扇门"，Bearer 管"你是谁"。门口和身份认证分了家，两个应用就永远不会串。**
