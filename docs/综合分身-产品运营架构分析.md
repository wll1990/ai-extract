# 综合分身（组织分身）— 产品·运营·架构分析

> 2026-07-28 · 高级产品经理 + 高级运营 + 高级架构师联合评估
> 基于最新代码核实（SkillController / ChatStreamService / RagPipelineService / GrainRetriever / enterprise_system.md）

---

## 一、功能定义

**综合分身**：面向企业内某个职能部门/岗位，聚合该部门所有销冠的个人分身颗粒，形成可对话的"部门 AI 大脑"。

典型场景：
- "华东销售部的通用方法论是什么？" → 打开「华东销售部」综合分身
- "张经理个人怎么处理价格异议？" → 打开「张经理」个人分身
- "B2B 和 SaaS 销售在这个部门有什么不同做法？" → 综合分身对比回答

## 二、当前系统能力盘点（代码核实）

### 2.1 已有的

| 能力 | 代码位置 | 说明 |
|------|---------|------|
| 跨空间 RAG（全公司） | `ChatStreamService.enterpriseChat()` | 加载全公司 500 条颗粒→关键词匹配→top 20 |
| 企业调度员角色 | `prompts/enterprise_system.md` | "你是企业{domain.name}智慧的调度员" |
| `Skill.department` 字段 | `Skill.java:98` | 自由文本，发布时填写，仅用于展示 |
| 分身广场 tab 切换 | `skills/page.tsx` | `'published' \| 'mine'` 双 tab |
| pgvector 语义检索 | `GrainRetriever.java:49-55` | `WHERE g.space_id = ?` 单 space |
| 单分身 RAG 管道 | `RagPipelineService.java` | 查询改写→向量检索→分层标记→缺口记录 |

### 2.2 缺失的

| 能力 | 说明 |
|------|------|
| Organization 实体 | 无部门/岗位表 |
| 综合分身概念 | `Skill` 无 `orgType`/`isComposite` |
| 跨 space 向量检索 | `GrainRetriever` 只接受单个 `spaceId` |
| 部门维度查询 | `department` 不参与任何 `WHERE`/`GROUP BY` |
| 聚合统计（部门级） | 只做了单分身统计 |

### 2.3 两条现有聊天管道的差异

| | 个人分身聊天 | 企业调度聊天 |
|---|---|---|
| 端点 | `POST /skills/{id}/chat` | `POST /skills/enterprise/chat` |
| 范围 | 单个 space | 全公司所有 space |
| 检索方式 | pgvector 语义检索 | 关键词匹配（非向量） |
| topK | 5 条 | 20 条 |
| AI 角色 | "我是张经理" | "我是企业销售智慧调度员" |
| 溯源 | 颗粒→素材 | 无 |
| 鉴权 | `authenticated()` | `SUPER_ADMIN/COMPANY_ADMIN/EMPLOYEE` |

> 综合分身应该走**个人分身聊天的管道质量**（pgvector + RAG + 溯源）+ **企业调度的跨空间能力**。

## 三、产品分析

### 3.1 交互设计

**分身广场改为双 Tab：**
```
┌─────────────────────────────────────────┐
│  [🏢 组织]  [👤 个人]                    │
├─────────────────────────────────────────┤
│  ┌───────────────────────────────────┐  │
│  │ 🏢 华东销售部                     │  │
│  │ 综合 3 位销冠 · 128 条经验         │  │
│  │ 💬 1,240 次 · 👍 93% · 👤 89      │  │
│  │ [张经理] [李总监] [王主管]          │  │  ← 成员头像
│  │ [价格谈判] [异议处理] [大客户经营]   │  │
│  └───────────────────────────────────┘  │
│  ┌───────────────────────────────────┐  │
│  │ 🏢 华南大客户部                    │  │
│  │ 综合 2 位销冠 · 67 条经验          │  │
│  │ ...                               │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

**综合分身详情页：**
- Hero 区：部门名 + 聚合统计 + 成员头像行 + 所有成员标签并集
- QA/Talk/Practice 三种模式与个人分身一致
- 聊天时 RAG 检索范围 = 该组织所有成员的 space 列表
- 溯源标注来源销冠名（区别于个人分身的素材溯源）

### 3.2 关键产品决策

| 决策 | 建议 |
|------|------|
| 谁创建？ | 企业管理员在后台创建，选部门 + 匹配规则（department 文本匹配或 tags 匹配） |
| 成员变动？ | 动态聚合，新成员发布分身后自动纳入 |
| 颗粒去重？ | 同一场景多个销冠有不同做法→都展示，标注来源 |
| 综合分身有自己的颗粒吗？ | 没有。纯虚拟，所有颗粒来自成员个人分身 |
| MVP 范围？ | "组织"tab + QA 模式（Talk/Practice 延后） |

## 四、运营分析

### 4.1 商业化定位

| 维度 | 个人分身 | 综合分身 |
|------|---------|---------|
| 定价单位 | 按分身 | 按组织（一个部门一份订阅） |
| 目标客户 | 中小企业（1-5 人） | 中大企业（多部门） |
| 核心卖点 | 个人 IP | 组织知识资产 |
| 续费动力 | 销冠离职=失效 | 团队知识持续沉淀 |

### 4.2 与 enterprise chat 的关系

| | enterprise chat | 综合分身 |
|---|---|---|
| 范围 | 全公司 | 按部门/岗位 |
| 检索 | 关键词 top 20 | pgvector 语义 top 5 |
| 适用问题 | "整个公司怎么看" | "这个部门的最佳实践" |
| 入口 | 企业端顶部 | 分身广场"组织"tab |

两者互补而非替代。

### 4.3 推广节奏

- **Phase 1**：已有 3+ 人分身的企业免费试用
- **Phase 2**：企业版付费功能（"从个人经验到组织智慧"）
- **Phase 3**：数据反哺——"华东部综合分身本月回答 200 次，热门话题 Top 3"

### 4.4 风险与缓解

| 风险 | 缓解 |
|------|------|
| 低质量颗粒拖累 | 只纳入 quality_score ≥ 3 的颗粒 |
| 销冠抵触 | 溯源清晰标注来源，尊重贡献者 |
| 回答不好归咎部门 | 在开场白说明"由多位销冠的经验聚合而成" |

## 五、架构分析

### 5.1 数据模型（最小改动）

```sql
-- 不新建 Organization 表，复用现有 Skill + department 字段

-- Skill 加 2 列
ALTER TABLE skill ADD COLUMN org_type VARCHAR(10) DEFAULT 'personal';
-- 'personal' = 个人分身, 'organization' = 综合分身

ALTER TABLE skill ADD COLUMN match_rule JSONB;
-- 综合分身用，如 {"department": "华东销售部", "tags": ["B2B"]}
-- 个人分身为 NULL
```

综合分身也是一条 `Skill` 记录，区别在于 `org_type = 'organization'` + 无自己的 `spaceId`（或 `spaceId` 指向一个空的占位 space）。

### 5.2 RAG 检索改造

**当前**（`GrainRetriever.java:49-55`）：
```sql
WHERE g.space_id = ? AND g.status = 'active' AND g.embedding IS NOT NULL
ORDER BY g.embedding <=> ?
LIMIT ?
```

**改造后**：加一个多 space 版本：
```sql
WHERE g.space_id IN (:spaceIds) AND g.status = 'active' AND g.embedding IS NOT NULL
ORDER BY g.embedding <=> ?
LIMIT ?
```
pgvector 的 `<=>` 操作符在 HNSW 索引下支持 `WHERE ... IN` 过滤，性能可接受。

**检索流程**：
```
综合分身 → 解析 match_rule
  → SkillRepository.findByDepartment("华东销售部")
  → 收集 spaceId 列表
  → GrainRetriever.retrieveWithScores(query, spaceIds, topK)
  → tier 标记 + 溯源附加 ownerName
  → 复用现有 enterprise_system.md prompt
```

### 5.3 聚合统计

综合分身的 stats 是其所有成员 stats 的 SUM：
- `conversationCount` = 成员之和
- `userCount` = 成员 `userCount` 之和（近似，可能重复）
- `satisfactionRate` = 成员满意度的加权平均
- `grainCount` = 成员颗粒数之和
- `sceneCount` = 成员场景标签去重后的数量

可在 `SkillStatsScheduler` 中增加综合分身的统计聚合逻辑。

### 5.4 改动量评估

| 层 | 文件 | 改动类型 | 工作量 |
|------|------|---------|--------|
| DB | migration | skill 加 2 列 | 小 |
| 后端-实体 | `Skill.java` | 加 2 字段 | 小 |
| 后端-检索 | `GrainRetriever.java` | 加多 space 查询方法 | 中 |
| 后端-管道 | `RagPipelineService.java` | 支持 spaceId 列表参数 | 中 |
| 后端-Service | `SkillService.java` | 综合分身 CRUD + 成员查询 | 中 |
| 后端-Scheduler | `SkillStatsScheduler.java` | 综合分身聚合统计 | 小 |
| 后端-API | `SkillController.java` | 综合分身创建/编辑端点 | 小 |
| 前端-广场 | `skills/page.tsx` | 双 tab + 综合分身卡片 | 中 |
| 前端-详情 | `skill/[id]/page.tsx` | 综合分身 Hero（已有基础） | 小 |

**总估：约 2 周，12-15 个文件。**

### 5.5 技术风险

| 风险 | 缓解 |
|------|------|
| 多 space 向量检索性能 | `WHERE space_id IN (...)` 可走 HNSW 索引，topK 不变 |
| 颗粒候选池膨胀 | 候选 pool 变大但 topK 不变，只影响召回质量不影响性能 |
| 成员变动检索一致性 | 动态查成员列表，无缓存过期问题 |
| 溯源 ownerName 为空 | Skill.ownerName 发布时必填，回退用 displayName |

## 六、建议

- **产品**：MVP 只做"组织"tab + QA 模式，验证价值后扩展 Talk/Practice
- **运营**：优先在已有 5+ 人分身的试点企业跑数据，再定定价
- **架构**：复用 Skill 实体（`org_type` 字段区分），聊天管道走个人分身的高质量路径（pgvector + RAG + 溯源），搜索范围扩展到多 space
